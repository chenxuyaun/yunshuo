## 二、事实

### 2.1 不对称的真实形状：不是"一处内联"，是"两处各自为政"

网关侧只有嵌入的一半（`packages/model-gateway/src/index.ts` 导出四个模块：`secret`、`embedding-client`、`embedding-providers`、`embedding-cost`）；chat 调用完全内联在应用侧，且**已经分叉成两条**：

| | 提案路径 `ai-service.ts` `executeAttempt`（`:1114`） | 账本路径 `ledger-suggestion-service.ts` `callModel`（`:551`） |
| --- | --- | --- |
| 流式 | `stream: true` + SSE 解析（`iterateSseEvents`/`parseChatSseData`） | `stream: false` + 单次 JSON |
| temperature | 0.8 | 0.2 |
| 超时 | 由调用方 deadline 推导（整段 `AI_TIMEOUT_MS = 120_000` 覆盖全部 failover 尝试） | `AbortSignal.timeout(45_000)` 单发 |
| 错误处理 | `GenerationFailure` 类 + 归一化码 + 两段式流选项降级 | 就地返回 `{code, message, retryable}` 对象 |
| 重试 | failover 循环（`MAX_ATTEMPTS_PER_PROVIDER = 2`、`MAX_TOTAL_ATTEMPTS = 4`、退避） | 无 |

两个超时常量的口径见 D5 拍板材料 §2.1，**本文不动它们**。

另有一条方向性事实：`redactSecret` 已经住在网关侧（`apps/api/src/services/provider-service.ts:19-24` 从 `@yunshuo/model-gateway` 导入并转出，ai-service 再用）。所以抽取**不是引入新的依赖方向**，是把缺失的那一半补上，让网关对 chat 和 embedding 对称。

### 2.2 `executeAttempt` 已经是一块干净的边界——抽取主要是搬运，不是重写

逐项核对（读 `:1114-1270` 全文）：**不碰 `sql`**（函数体内零 SQL 模板；全仓 `model_calls` 四个写点都在函数外，见 2.4）、**不碰预算**、**不推进状态**。输入是 `{provider 三字段, run.messages, maxTokens, includeStreamOptions, deadline, signal, onDelta}`，输出是 `AttemptResult`（`ok`/`code`/`message`/`retryable`/`streamOptionsUnsupported`/`aborted`/`timedOut`/`content`/`usage`）。

随函数一起进包的辅助件（全仓 grep 确认**无其他消费方**，也无测试导入）：

- `parseSseEventBlock`（`:683`）、`iterateSseEvents`（`:696`）、`parseChatSseData`（`:736`）及 `SseEvent`/`ChatSseData` 类型；
- `GenerationFailure`（`:103`）、`failureCode`（`:802`）、`failureMessage`（`:797`）、`upstreamErrorRetryable`（`:1035`）、`RETRYABLE_HTTP_STATUS`（`:58`）、`MAX_OUTPUT_CHARS`（`:49`）——这些只被 `executeAttempt` 及其 catch 使用；
- `truncate`（`:793`）**例外**：调用方（`insertBlockedCall`/`markCallFailure`）也在用，不搬；包内自备一份（`embedding-client.ts` 已有同样的先例，包内本来就自带 `truncate`/`redact` 副本）。

### 2.3 failover 循环为什么必须留在调用方（ADR-0010 第 41 行问的那个归属）

循环体（`:1359` 起）逐次读写的全是调用方概念：

1. **钱**：每次尝试前过 `budgetMaxTokens`（`:1365`）与 `reserveGenerationCall`（`:1384`），失败后按真实成本扣减（`:1469-1480`）。若循环进包，包需要回调应用侧预算与写库——依赖倒挂，或者把回调塞进包签名，两者都更差。
2. **写点**：`insertBlockedCall`/`markCallFailure`（`:1285`/`:1306`）是每次尝试的 `model_calls` 记账，全部在循环里。
3. **deadline 是整段概念**：`deadline = run.startedAt + AI_TIMEOUT_MS`（`:1327`）横跨全部尝试与退避；单次尝试只是拿剩余时间（`:1134`）。

对 L2b 的直接影响（ADR 关心的"一个 step 内部仍可 failover 是不是好实现"）：**是**。step 执行器调用的就是"单次尝试"函数，failover 仍是调用方围着它转的同一只循环——L2b 不需要为"step 内 failover"另写机制，也避免把预算回调打进包里。

| 不变量（ADR-0010） | 代码锚 | 现有断言 | 判定 |
| --- | --- | --- | --- |

| `model_calls` 写入位点与时机 | 四个写点：`:608` 弃锁回收、`:861` 成功收尾、`:1285` 预检阻断、`:1306` 尝试失败 | `:511`（成功写 token 成本）、m3b（`AI_ABANDONED`）、`:636`（并发阻断） | 已覆盖；断言方式 = 四处全部留在 `ai-service.ts`（抽取后 grep 核查） |

结论：**ADR 的"一样都不能变"清单里，四条已有测试钉住，唯一需要新增的是请求体全字段那一条**——这是 (a) 低风险的直接根据，也是交付物里"行为等价"的核查清单。

### 2.5 接缝处的三个坑（实现时必须处理）

1. **超时文案用的是整段常量，不是本次剩余毫秒。** 消息里写 `${Math.round(AI_TIMEOUT_MS / 1000)} 秒`（`:1244`），而实际中止用的是 `deadline - Date.now()`（`:1134`）——failover 第二跳时真实剩余可能只有几十秒，文案仍说 120 秒。这是今天的既有行为；抽取时这两个值必须**分开传**（`deadline` 用于中止计算，`timeoutLabelMs` 仅用于文案），不要合并成一个。
2. **文案带产品词，等价优先。** `OUTPUT_TOO_LARGE` 的"提案未完成"（`:1153`）、`EMPTY_OUTPUT` 的"未生成提案"（`:1234`）、`AI_TIMEOUT` 的"提案未完成"（`:1244`）——这些字符串会进 `model_calls.error_message` 与 API 响应。v1 保持字节等价；通用化措辞是后续独立改动，不混进这次重构。
3. **`streamOptionsUnsupported` 探测靠字符串匹配。** 判定条件是 `message.includes('HTTP 400')` 且 `includes('stream_options')`（`:1254-1260`）——错误文案在这里是协议的一部分，归一化时不能顺手改字。

### 2.6 行号口径

本文行号按**当前工作树**（含 L1a 未提交改动）。ADR-0010 的 `:1166`（fetch）/`:1356`（循环）是 HEAD 口径、同一位置；L1a 合并后整体 +3（`:1169`/`:1359`）。实现与复核一律以函数名/常量名为稳定锚，行号只作辅助。

## 三、建议

### ① 抽，作为独立小重构

- **时序**：L1a 合并后、L2b 开工前。L1a 正在改 `ai-service.ts`（已 +3 行），同文件并发改会把"等价基线"搅浑；L2b 会在请求体里加 `tools`/`tool_choice`，若先做 L2b 再抽，抽取就变成"带着新功能抽"——"行为等价"没有干净基线可证。
- **反面代价（不抽）**：L2b 的 tools 逻辑会在同一个文件里再写一遍；之后任何时候要抽，都得先读完一整份"上下文装配 + 预算 + failover + 写库 + SSE 解析"混住的文件，等价断言无从下手。ADR-0010 的判断（供应商细节与运行状态机不同模块）在这里被代码证实：`executeAttempt` 已经是那块该搬走的干净积木。
- **一个 PR 只做这件事**（硬规则 13）：只动 `apps/api/src/services/ai-service.ts` 与 `packages/model-gateway/`。

### ② 边界：建议的签名形状（命名可在实现时定）

```ts
// packages/model-gateway/src/chat-client.ts
export interface ChatProviderConfig { baseUrl: string; model: string; apiKey: string | null }

export interface ChatAttemptInput {
  provider: ChatProviderConfig;
  messages: { role: string; content: string }[];
  maxTokens: number;
  includeStreamOptions: boolean;   // 两段式降级的第二段
  deadline: number;                // 绝对毫秒时间戳；剩余 = deadline - Date.now()
  signal: AbortSignal;             // 客户端中止信号
  onDelta: (text: string) => void; // 流式增量
  timeoutLabelMs: number;          // 仅用于超时文案（传 120_000），见 2.5 坑 1
}

export type ChatAttemptOutcome = /* 今天的 AttemptResult 原样搬迁 */;

export async function chatStreamAttempt(input: ChatAttemptInput): Promise<ChatAttemptOutcome>;
```

包内不出现 `sql`、预算、run 状态；包外保留循环与记账（清单见 2.3）。**账本路径本次不动**——它形状已分叉（单发、45 秒、0.2、另一套错误词汇），一起抽会让等价面翻倍；包 API 不做成 streaming-only 即可（输入里有 `messages`/`maxTokens`，将来账本路径要迁移不需要第二次重写），但**不承诺日期**。

### ③ 等价证据：四件套

1. `pnpm typecheck` + `pnpm test` 全绿（m3-runtime / m3b / m6 是主覆盖）；
2. **新增一条请求体断言**：fake provider 已把每次请求解析后的 body 收进 `requests` 数组（`m3-runtime.test.ts:263-279`），补一条断言钉住字段集合与值（`stream: true`、`temperature: 0.8`、`max_tokens`、`stream_options` 两段行为）**并断言不含 `tools`/`tool_choice`**；
3. **写点核查**：抽取后 `grep -n "UPDATE model_calls\|INSERT INTO model_calls" apps/api/src/services/ai-service.ts` 仍恰好是 `:608`/`:861`/`:1285`/`:1306` 四处（除机械位移）；
4. **一次真实调用**（ADR-0010 的交付物要求）：记录 tokens/cost/请求形状。**该证据依赖 Atria 凭据，目前是外部阻塞项**（L0 探测未拿到凭据）。若拍板后仍无凭据：如实标注"未做真实调用，等价证据为测试 + 表征断言"，**不伪造**（硬规则 4）。

### ④ 回滚与风险

回滚 = 把函数搬回 `ai-service.ts`，无迁移、无契约变化。真正的风险只有一个——**以为等价、实际不等价**；所以等价证据本身就是交付物，不是附属品。

## 四、拍板后的动作

1. 等 L1a 合并进 `main`（当前在 `feat/l1a-tool-surface`，未提交改动含 `ai-service.ts`）；
2. 开独立分支，按 ② 的边界搬运，按 ③ 补齐证据；
3. 合并后在 ADR-0010 上标"已实施 + 落点函数名 + 证据位置"；
4. L2b 开工时，`tools`/`tool_choice` 的请求体改动预期只落在 `chat-client.ts` **一处**——如果发现要动两处，说明边界划错了，回头复核本文 2.3；
5. 若拍板为 (b) 不抽：把本文 2.4 的覆盖表并入 L2b 的前置检查（L2b 加 tools 时必须自己补请求体断言），并接受 ADR-0010 里"四件事挤一个文件"的代价继续。
