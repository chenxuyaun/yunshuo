# ADR-0008：L1 拆 a/b 是否接受

- **状态**：待拍板（Proposed）
- **来源**：分层设计 D8
- **阻塞**：L1
- **建议**：接受 a/b 拆分（即设计文档已改成的形状）

## 背景

L1 是"工具面"——把已有的读能力用一份定义描述清楚，让模型可以"再取一次"。它有 5 个候选工具，设计文档把它们拆成两批：

| 批次 | 工具 | 依据 |
| --- | --- | --- |
| **L1a（先做 2 个）** | `search_canon`（`search-service.ts` 的正典通道 + `coverage`/`reason` 降级口径）、`get_chapter_plan`（`plan-service.ts` 五键章纲） | 一个给"跨章证据"，一个给"本章意图"，这两个足够让 L2b 的循环产生真实的"再取一次"决策 |
| **L1b（L2b 之后补 3 个）** | `search_ledger`、`get_character_state_as_of`（保留"防剧透裁剪"与过期标记）、`list_open_foreshadowing` | 这三个的价值要用真实循环才能判断（模型到底会不会去查角色状态、查了有没有用） |

支撑这个拆分的关键设计是：**注册表结构按 5 个工具设计，实现只做 2 个**（设计文档 `:99`）。也就是说 L1b 是纯追加——加 handler 与契约用例，不动注册表形状。这一条让"拆"的代价变得可控。

## 选项

### (a) 接受 a/b 拆分（推荐）

- **L1a 交付后系统行为零变化**（设计文档 `:104`：这层仍然一次模型调用都不发），但"边界可以被程序化调用"已经成立。这是一个干净的中间住人状态。
- L1b 的三个工具按**实测调用分布**排优先级——先看循环真的调了什么，再决定补哪个。避免"给一个没人调的工具花掉一轮工程量"。
- 代价：L2b 首次跑通时工具面只有 2 个。如果循环的真实需求恰好落在那 3 个上，会在 L2b 之后暴露出来，届时 L1b 才补。

### (b) 把 L1b 拉回 L1，L2 顺延

- 一次性做全 5 个工具再放循环，"工具面一次到位"。
- 代价一：**循环开工时间后移**——L2 与 L2b 都排在 5 个工具之后。
- 代价二：**那 3 个工具的价值判断没有实测调用分布可依**。在没有循环的情况下决定 `list_open_foreshadowing` 该返回多少条、`get_character_state_as_of` 的防剧透裁剪按哪个时间点，只能靠猜。猜出来的接口在循环跑通后大概率要改，而**改一个已经被测试钉住的工具契约比新增一个贵**。

## 建议与理由

选 (a)。理由不是"先做少一点省力"，而是**顺序决定信息**：

- 走 (a)：先有循环 → 观测真实调用分布 → 按数据补工具。工具契约定型时手里有证据。
- 走 (b)：先定 5 个工具契约 → 再跑循环。契约定型时手里只有推测。

设计文档把这条写成"**如果你更认同'工具面一次做全再放循环'**"，意味着这是价值取向问题而非对错问题——(b) 换到的是"循环首次开跑时工具齐备"，代价是那些契约缺证据。**若你更看重"首次跑通时不留缺口"，选 (b) 是成立的**，但要把上面两条代价记进 README 的诚实边界，尤其是"这 3 个工具的入参形状是推测的，L2b 跑通后可能返工"。

## 如果采纳 (a)，影响面

- L1a 是一个独立可停的交付：1 个新包（见 ADR-0002）+ 1 个注册表 + 2 个 handler 适配 + 契约类型 + 约 8–12 个用例。
- 验收不依赖任何模型：纯函数 + 服务层用例，跑 `pnpm typecheck` + 全量测试 + 覆盖筛子。
- 每个工具至少 1 条"给的参数能跑通 + 缺参数被拒 + 跨工作区被拒"的契约用例（设计文档 `:102`）。
- L1a 明确不做：不写循环、不加 `tool_calls` 解析、不开任何写类工具。

## 回退

(a) 的回退就是 (b)——把 L1b 提到 L2 之前，只是顺序变了，已交付的 L1a 不作废（注册表按 5 个设计，追加不返工）。这也是选 (a) 的风险可控之处：**它不烧掉任何选项**。

反之 (b) 若发现推测错了，回退代价是改已定型的工具契约与对应用例。
