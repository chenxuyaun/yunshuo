# ADR-0003：循环要不要流式

- **状态**：待拍板（Proposed）
- **来源**：分层设计 D3
- **阻塞**：L2b
- **建议**：v1 非流式

## 背景

现有单发生成是**流式**的：`ai-service.ts` 按 SSE 逐块读 `choices[0].delta.content` 并推给前端，用户能看到文字逐段长出来。循环（L2b）引入 `tool_calls` 后，流式会立刻变复杂：工具调用参数在流里是按 **delta 拼接**的（一个 JSON 对象可能被拆成任意多块），要正确处理得维护增量缓冲、处理跨块边界、以及在"这一轮是文本还是工具调用"之间分流。

## 选项

**(a) v1 非流式。** 循环的每一轮都是一次完整的请求-响应，拿到完整 `tool_calls` 再执行。

**(b) 一上来就流式。** 保持与现有单发一致的逐字体验。

## 建议与理由

**(a)**。理由：**复杂度是实打实的，而收益是体验性的**。流式带来的正确性风险（增量拼接、部分工具调用、中途断流后的半截状态）会直接落到 L2b 最不该出问题的地方——终止判定与成本记账。先把"循环能收敛、钱能控住、轨迹能审计"做对，再谈逐字体验。

**代价要如实写下来**：长 run 期间界面只能显示"第 N 步"这类进度，不能显示正在生成的文字。这是用户可见的体验回退，得在 README 的诚实边界里写清楚。

## 如果采纳，影响面

- L2b 会**新增**一条非流式路径，而不是替换现有单发路径。现有单发（流式）在 L2b 塌了的时候是常驻降级档（`tool_choice='none'` + `max_steps=1`；今天的提案请求体不含 `tools`/`tool_choice`（`apps/api/src/services/ai-service.ts:1160-1167`），所以它不是原样复用今天的单发请求体——这两个字段的接入位点与口径待拍板），所以**流式代码不能删**。
- 界面要新增"第 N 步"进度显示，这与现有的逐字流式是两套展示逻辑。

## 回退

若非流式导致界面不可接受（比如单步耗时过长、用户以为卡死），可单独为"最后一步的文本生成"恢复流式——那时工具调用已经结束，流式拼接的复杂度不再存在。
