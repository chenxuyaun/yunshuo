# ADR-0009：Run Engine 是延长 `automation_jobs` 还是新建表

- **状态**：待拍板（Proposed）
- **来源**：分层设计 D9
- **阻塞**：L2
- **建议**：(a) 新建 `runs` / `steps` / `tool_calls`，`automation_jobs` 继续当它自己的事——**形状照抄它，但不改它**

## 背景

L2 是 Run Engine（任务生命周期，不含模型循环）。设计文档的第一条关键发现是：

> **我们不是从零建 Run Engine，是延长一台已有的**：`automation_jobs.status` 有 CHECK 合法集、`heartbeat_at` 有索引（崩溃认领）、`automation_job_chapters` 是逐章状态检查点、`automation_mandates` 带 `max_chapters`/`target_words 300–4000`/`budget_limit` 三重上限（`0008_m4b_automation.sql`）；另有 `ai_generation_locks`（`0005`）与 outbox。**所以 L2 的工程量主要在"把 run/step 抽象出来"，不在"新造状态机与认领机制"**（`:119`）

于是问题变成：既然已经有了这台引擎，是**把它泛化**成通用 run，还是**在旁边再建一套**？

## 选项

### (a) 新建 `runs` / `steps` / `tool_calls`，`automation_jobs` 不动（推荐）

- 作业表已有 CHECK 枚举、心跳认领、逐章检查点，以及**一堆围绕它的测试**（回顾审计报告里那 84 枪）。动它等于把已验证的无人值守链路重新推上赌桌。
- 新表与旧作业表**互不引用**——这正是 (a) 的本意（`:233`）。
- 最坏情况可控：`runs` 只服务 AI 一类调用方，无人值守链路一字不动。

### (b) 把 `automation_jobs` 泛化成 run

- 一套表、一套状态机，概念上更整齐，长期没有"两套 run"的分裂。
- 代价：**作业表的每次改动都会落在无人值守链路上**。那条链路是当前唯一"真金白银、无人值守、已验证"的部分，它的价值恰恰来自"没人再动它"。为概念整齐而把它推上赌桌，收益是审美，风险是可用性。

## 建议与理由

选 (a)。核心理由是一条不对称性：

- 走 (a) 的最坏结果是**多了一套表**（结构冗余，可以日后合并）。
- 走 (b) 的最坏结果是**无人值守链路回归**（可用性损失，且出问题时"是基座改坏的还是本来就有"难以归因）。

冗余可以事后消除，回归不能事后假装没发生。**"形状照抄它，别自创一套"**（`:220`）是 (a) 的配套纪律——不碰它的表，但抄它的做法：CHECK 合法状态集、`heartbeat_at` 索引做崩溃认领、逐章检查点对应到逐 step 检查点、部分唯一索引做幂等（照 `0019_ledger_suggestion_generating_unique.sql` 抄形状，别手工判重）。

## 一个需要同时确认的关联选择

D9 拍完之后，**§七 的"L2 可以先停在确定性 run"这一档才算可选**（`:264`）：

> L1a → **L2 可以先停在"确定性 run"**——把 M6-7 的单发建议改造成"一个 run、两个 step（装配上下文 → 生成）"，零循环、零新增成本，但 `run_id`、状态机、检查点、取消与恢复全部就位，L2b 只是往里加一种步骤产生器。

这是"要不要走这一档"的判断，不是 D9 本身。但它与 D9 强相关：**只有当 `runs` 是独立新表时，这一档才便宜**——如果是泛化 `automation_jobs`，这次重构就要动那条链路，"零新增成本"不成立。

## 影响面

- **新对象**（`:120`）：`Run`（归属 workspace/work/chapter、模板与版本、允许工具集快照、预算与步数上限、状态、终止原因、累计用量与成本、依据的 `canon_version_id`/规则集版本）、`Step`（序号、类型、状态、检查点）、`ToolCall`（参数、校验结果、返回摘要与大小、错误类型）、`Trace`（关联 `run_id`/`step_id`/`tool_call_id`，与 `model_calls` 成对）。
  - 设计文档口径是"只建 4 个"（`:120`、`:247`），D9 表里写的是 3 张表名。**实际表数是 3 还是 4（`Trace` 是否独立成表）留到 L2 开工时按投影需要定**——这不改变 (a)/(b) 的选择。
- **不新建**：`Task`（与 `Run` 一比一）、`Artifact`（正文与提案已各有归属：`canon_versions` / `ai_proposals` / `ledger_suggestions`）、`Approval`（已有豁免 + 建议采纳/拒绝两步确认）。
- **生命周期先定义再写码**（`:121`）：合法转移集 + 超时 + 终止态；幂等用部分唯一索引；取消只终止后续步骤、已发生的 `model_calls` 保留真实用量与成本（延长已验证的 `CLIENT_ABORTED` 口径，不抹账）；恢复按 step 检查点续跑，服务重启靠 stale 回收（M6-7 的 `generating` > 10 分钟回收是现成形状）；单 run 单执行权。
- **一条已踩过的坑要带着**：outbox 一直是"至少一次 + 幂等消费"，不是 exactly-once。**别因为建了 run 表就以为副作用自动可靠**（`:122`）。
- **验收**：① 状态机用例（非法转移被拒 + 合法转移逐条钉）；② 三条运行期行为：重复提交、崩溃后回收并续跑、取消后不产生后续步骤但账不动；③ 每条运行事件都带 `run_id`（机械闸）。
- **明确不做**：不做队列与分布式执行器（worker 已有认领机制），不做跨服务事务补偿。

## 回退

新表与旧作业表互不引用，所以回退是"删掉新表、回到今天"——无人值守链路一字不动（`:233`）。这是 (a) 最值钱的地方：**它的失败不会外溢**。
