# ADR-0001：L0 能力元数据存哪

- **状态**：待拍板（Proposed）
- **来源**：分层设计 D1
- **阻塞**：L0
- **建议**：选项 (a)

## 背景

架构师要求为模型记录"工具调用能力、结构化输出能力、上下文限制、单次成本/延迟/错误率"。本仓现状只有嵌入侧的探测（`probeEmbedding`），**chat 侧什么也没有**——连"是否支持严格 JSON 输出"都是靠真实失败样本反推的（M6-7 实测到 1 次非 JSON）。

L0 的产出物因此从"一个布尔"升级为一份**可持续更新的资产**：不是"Atria 支持 tools 吗"，而是"哪个服务商的哪个模型、在什么时间点、哪些能力是探过的"。

## 选项

**(a) 新建 `model_capabilities` 小表**，按 `provider_id + model` 一行：`tools` 四态、`structured_output`、`context_limit`、探测时间。

**(b) 在 `model_providers` 上加 JSONB 列。**

**(c) 只在 `model_calls` 里留 `purpose='probe'` 记录。**

## 建议与理由

**(a)**。理由：能力要**可展示**（界面上给出一行状态）、要**能在生成前阻断**（不支持 tools 就别把循环挂上去）、要**能按模型区分**（同一服务商不同模型能力不同）。选项 (c) 只留痕迹，不能当配置用——它会变成第二个"看起来是真相、实际没人读"的东西。选项 (b) 把能力塞进服务商行，但能力是**按模型**的属性，服务商改一个模型就要改整行 JSON，且没法对单模型建约束。

## 如果采纳，影响面

- 新增一次迁移（迁移只追加，不修改已执行的迁移）。
- 写入方：L0 探针。读取方：L2b 生成前的准入判断、界面状态行。
- `packages/db/src/schema.ts` 要同步登记，并跑 `pnpm check:schema-drift`。

## 回退

若 L0 探到 `rejected_field`（服务商不吃 `tools`），整条循环路线改道、L2 起全不开工，**损失止于一个探针**。此时这张表可留着不填（零运行时成本），也可在同一次迁移里连同其它改动一起回滚。
