# ADR-0006：MCP 要不要做、做几类

- **状态**：待拍板（Proposed）
- **来源**：分层设计 D6
- **阻塞**：L6（可选层，可永远不做）
- **建议**：需求驱动；做的时候是 Tools + Resources + Prompts 三类

## 背景

L6 是"对外只读 MCP server"，把云说的能力抬出去给外部代理用。分层设计把 L6 排在 L5 之后且标注"可选，可永远不做"，理由是**它解决的问题今天不存在**：L1 的进程内工具面已经够支撑产品自己的需求。

## 触发条件（不是时间点）

**只有当"别人家的代理要读我们的账本"是真实需求时才做。** 这是一个需求判据，不是排期判据——不能因为"到 L6 了"就做，也不能因为"别人都有 MCP"就做。

`AGENTS.md` 的防漂移清单里有一条直接对应：**不为了"有 MCP"而做 MCP。**

## 如果做，范围是什么

**Tools + Resources + Prompts 三类，不是只做 Tools。** 这是分层设计明确点出的一条：MCP 的完整形状是三类原语，只做 Tools 会把"账本条目作为可读资源"和"提示模板"这两块能力丢掉，做出来是个残废的 server，还得再改一次。

## 做的时候必须同时处理的安全面

**外部服务商的工具描述与 annotations 一律不可信。** MCP 规范原文（`../云说-模型侧基座研究-2026-10-26.md:28`）：

> clients MUST consider tool annotations to be untrusted unless they come from trusted servers

这条对本仓的意义是双向的：

- **我们是 server 时**：我们写出去的工具描述会被别人当成不可信输入——所以我们自己也不能指望对方"读懂我们的意图"。
- **将来我们若接别人的 server**：对方的描述能藏指令，不能直接拼进提示词。

L1a/L1b 的自有工具不受此限（自己写的），**信任边界在 L6 才第一次被打破**。所以 L6 的回退不是"过滤一下描述"，而是**关闭对外 server，回到进程内**（分层设计 `:239`）。

## 回退

关闭对外 server。进程内工具面不受影响——L6 是外接层，不承载任何内部依赖（依赖方向是 L6 依赖 L1，不是反过来）。
