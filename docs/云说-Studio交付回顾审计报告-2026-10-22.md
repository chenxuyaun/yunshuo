## 二、发现与修复

### 1. 高：Studio worker 缺少模型密钥，索引无法解密服务商 API Key

- 现象：`docker-compose.studio.yml` 的 worker 只注入 `NODE_ENV / DATABASE_URL / LOG_LEVEL`。worker 的管线在没有 `MODEL_KEY_SECRET` 时会回退到开发默认值或 `SESSION_SECRET`，与 API 加密密钥不一致，导致配置了嵌入服务商后也无法解密其 API Key。
- 影响：界面可以正常保存服务商并显示启用，但导入章或提交章的实际索引会失败；此前的 Studio 验收没有配置嵌入服务商，因此没有暴露。
- 修复：worker 显式注入 `${STUDIO_MODEL_KEY_SECRET}`；worker 在 `NODE_ENV=production` 且缺少该变量时，在连接数据库前打印错误并退出 1。
- 证据：Compose 配置解析确认 worker 的 `MODEL_KEY_SECRET` 已注入；缺少该变量启动 worker 实际退出 1；全栈验收中 worker 正常轮询。

### 2. 高：API 可能在 bootstrap 失败后仍对外启动

- 现象：API 只等待 `migrate` 成功，不等待 `bootstrap`。bootstrap 失败时，Compose 会留下一个可公开访问但没有所有者的 API/Web。
- 影响：全新部署出现“能打开登录页但没有任何可用账号”的半启动状态，且不易从表面判断初始化失败。
- 修复：API 的 `depends_on` 增加 `bootstrap: condition: service_completed_successfully`；bootstrap 不成功时 API/Web 不启动。
- 证据：Compose 配置解析确认 API 依赖 migrate 与 bootstrap；全栈验收中 API 在 bootstrap 退出 0 后才变为 healthy。

### 3. 中：bootstrap 重启校验顺序会导致已有部署无法重启

- 现象：原实现先校验 `BOOTSTRAP_OWNER_PASSWORD` 长度并执行 scrypt 哈希，再检查邮箱是否已是所有者。首次部署后运维若清空密码，后续每次启动都会失败，尽管不需要创建任何账号。
- 影响：密码成为永久的启动依赖，增加密钥长期留在 `.env.studio` 的压力；Compose 也曾强制要求该变量。
- 修复：进入事务并取得 advisory lock 后先查已有账号；只有确认需要新建账号时才校验密码、称呼、工作区名称并哈希。Compose 将密码改为可选，`.env.studio.example` 注明首次必需、之后可留空。
- 证据：测试库中首次创建成功；第二次使用过短密码并改名，bootstrap 仍退出 0、日志显示跳过，用户密码哈希与称呼均未改变；真实 Studio 栈移除密码后二次 bootstrap 同样退出 0。

### 4. 中：配置了嵌入服务商时，导入章仍被标为“未配置”且永不排队

- 现象：旧章导入无条件把 `index_status.status` 写成 `not_configured`，也不写 outbox。即使工作区已有启用的 `embedding` 服务商，导入章也不会进入索引队列。
- 影响：用户看到“未配置嵌入服务”的错误提示；导入章无法被检索，且没有明显入口说明需要手工逐章重建。
- 修复：导入事务内查询工作区已启用的 `embedding` 服务商。存在时把索引状态置为 `pending`，写入去重键为 `index:<versionId>:reindex` 的 `index.chapter` outbox；不存在时保持 `not_configured`。前端补充“自动排队可能产生嵌入费用”的提示。
- 证据：新增集成测试创建独立工作区与启用的嵌入服务商，导入后断言 `index_status.status='pending'`、outbox 事件类型/去重键/workspaceId 正确；未配置服务商的原有测试仍断言 `not_configured`。

### 5. 中：非 UTF-8 旧稿被静默替换为乱码

- 现象：前端使用 `file.text()` 读取文件，浏览器会按 UTF-8 解码并把非法字节替换为 U+FFFD，旧稿（如 GBK/GB18030）可能带着乱码进入预览与导入。
- 影响：正文内容在入库前已经损坏，且界面不会报错；这是数据完整性问题，不是显示问题。
- 修复：改用 `TextDecoder('utf-8', { fatal: true })`；解码失败时明确提示“文件不是有效的 UTF-8 编码，请先转码”，并清空文件输入，不发起导入请求。
- 证据：TypeScript 检查通过；前端文件选择说明改为“支持 UTF-8 的 .md / .txt”。该路径仍无自动化测试，已列入残留风险。

### 6. 中：卷号相同但卷名不同被静默忽略

- 现象：导入到已有卷号时，代码复用旧卷并忽略请求中的新卷名，不告知用户。
- 影响：用户以为新卷已创建，实际章节被并入同号旧卷，卷名与预期不符。
- 修复：已有卷标题与请求不一致时返回 409 `VOLUME_TITLE_MISMATCH`，整批不写入，并在错误信息中给出已有标题与请求标题。
- 证据：导入测试在复用卷的场景中增加错误卷名请求，断言 409、章节数不变；服务商启用场景与并发场景也通过。

### 7. 中低：生产模式没有强制模型密钥独立，worker 也会静默回退

- 现象：文档要求生产使用独立 `MODEL_KEY_SECRET`，但 API 代码在缺失时回退到 `SESSION_SECRET`；worker 还会回退到 `dev-only-change-me`。
- 影响：错误配置不会在启动时失败，可能用会话密钥加密服务商密钥，或让 worker 无法解密 API 加密的数据；问题延迟到索引或模型调用时才出现。
- 修复：API 在 `NODE_ENV=production` 下要求 `SESSION_SECRET` 与 `MODEL_KEY_SECRET` 同时存在且不相等；worker 在生产模式缺少模型密钥时直接退出 1。
- 证据：实际命令验证缺失模型密钥、两密钥相同均退出 1，不同则加载成功；worker 缺少密钥退出 1。

### 8. 低：`/api/health` 向公开调用方返回数据库原始错误

- 现象：数据库不可达时，健康检查响应包含底层错误的完整 `message`。
- 影响：该接口经 nginx 对外暴露，错误文本可能泄露内部主机、端口或驱动细节；健康检查只需要可用性结论。
- 修复：错误详情写入 API 日志，响应只保留 `status=degraded`、`database=unreachable`、服务名与时间。
- 证据：类型检查与全量测试通过；未新增故障注入测试，属小型边界改动。

### 9. 覆盖缺口：并发、自动索引、卷名冲突与 outbox 清理

- 原测试只有 6 个导入用例，未覆盖同一作品并发导入、配置嵌入服务商后的排队、卷名不一致，且 `afterAll` 只清用户/工作区，不清无工作区外键的 outbox。
- 修复：导入测试增至 8 个用例；`afterAll` 按 payload 的 `workspaceId` 清理 outbox；新增并发测试断言两个请求状态为 `[200, 409]` 且作品/卷/章节各只有一份；新增自动索引测试断言状态、outbox 事件与去重键。
- 证据：全量 151 项通过，API 104 项；测试库 outbox 残留为 0。

## 四、残留风险与未验收项

- **前端无自动化测试**：导入对话框的编码拒绝、18MB 文件上限、20MB JSON 预检与费用提示只经过类型检查和人工验收。
- **未做容量压测**：1000 章 / 20MB 上限没有实际边界压测；大事务的锁持有时间、内存与前端预览性能未知。
- **只支持 UTF-8 与阿拉伯数字章节号**：GBK/GB18030 需要用户先转码；`第一章` 这类中文数字标题不会被解析。
- **自动索引没有二次确认**：配置嵌入服务商后，导入会直接排队并可能产生费用；界面只有提示，没有逐次确认或费用预估。
- **Studio 复验未接真实外部嵌入服务**：自动排队与 outbox 已由集成测试覆盖，worker 的真实嵌入调用沿用 M4-A 的真实嵌入验收；本次未在 Studio 栈中复验完整导入 → 嵌入 → 检索闭环。
- **bootstrap 非所有者降级仍会跳过**：若 bootstrap 邮箱已存在但不是任何工作区所有者，服务只告警并继续，API 仍会启动。这是为避免运维误重置账号而保留的行为，但会造成“没有所有者”的部署，需要在运维手册中人工确认日志。
- **既有平台边界不变**：无内置 TLS/WAF、多副本、零停机、自动备份或数据库 RLS；API/worker 镜像含开发依赖并用 `tsx` 运行；worker 无 HTTP 健康端点；真实 SMTP、真实 IdP、Linux 主机与外部 HTTPS 反代未实测。
- `dev-v0` 仍是演示规则集，不是生产门禁；导入章门禁“未评估”，不能当作质量通过。
