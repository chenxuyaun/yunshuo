# 云说 模型侧基座研究（2026-10-26）

> 性质：资料收集 + 现状对齐。**本轮不改任何代码、不建迁移、不动测试**。目的是把"模型侧基座"四件事（工具面 / 循环 / 技能 / 可审计轨迹）的权威口径抄清楚，并对齐到本仓已有的零件与缺口，供方向裁决。
> 所有行号与数字均为本轮实测或本次引用，可复核；凡外推都标了"外推"。

## 一、先确认"基座确实没有"

本轮复扫（`grep -rniE "tool_calls|function_call|tool_choice|agent_run|agent_step" apps packages scripts docs` 覆盖 `.ts/.tsx/.sql/.md`）：**零命中**；`.ts` 里也没有 `mcp` 字样。结合读到的代码，模型在本仓的形态是"一次性文本函数"：

| 事实 | 位置 |
| --- | --- |
| 请求体固定 `{stream, temperature: 0.8, max_tokens, stream_options?, messages}`，没有 `tools` / `tool_choice` | `apps/api/src/services/ai-service.ts:1159-1163` |
| `messages` 类型只允许 `role: 'system' \| 'user'` | 同文件 `:87`、`:181` |
| 响应只解析 `choices[0].delta.content`，没有 `tool_calls` / `finish_reason` 分支 | 同文件 `:747-772` |
| `while (providerIndex < run.providers.length && totalAttempts < MAX_TOTAL_ATTEMPTS)`（`MAX_TOTAL_ATTEMPTS = 4`）是**服务商故障转移**，不是代理循环：一次尝试 = 一次完整生成，模型中途拿不到任何回读 | 同文件 `:1356`、`:50` |
| 上下文由人类代码预先装配：正文 6000 字上限、条目快照 800 字，超出只写 `truncated` | M6-7 账本建议生成约束（README 同名片段） |

所以"让模型能调用这套边界"目前不是差一个接口，而是差整个底座：**没有工具定义与分发、没有多轮循环与终止、没有作为数据的技能模板、没有步级轨迹持久化**。M6-7 的"AI 建议 → 人工确认 → 只写草稿"已经是这个模式的天花板。

## 二、四块基座的权威口径与落点

### 2.1 工具面（tool surface / MCP）

**MCP 的 Tool 形状**（`2025-11-25` 版规范字段清单）：`name`、`title`、`description`、`icons`、`inputSchema`、`outputSchema`、`annotations`、`execution`。生命周期：`tools/list` 发现（cursor 分页、`notifications/tools/list_changed`）→ `tools/call` 调用 → 结果 `content`（text / image / audio / resource_link / embedded resource）或 `structuredContent`；错误分**协议错误**与**执行错误**（`isError: true`，把失败作为内容回灌给模型）。安全口径两条：`name` 是标识符、唯一作用域是 server；**description/annotations 属不可信输入**——规范原文 "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"。

**`annotations` 四个 hint 与默认值**：`readOnlyHint`（默认 false）、`destructiveHint`（默认 true）、`idempotentHint`（默认 false）、`openWorldHint`（默认 false）。规范明确它们只是"提示"，**不是安全保证**。

**`2026-07-28` 版方向**：MCP 转向 stateless——无握手、无会话，请求自描述、可缓存、按 header 路由；旧的 sampling / roots 被弃用。含义：远程 MCP server 的运维形状正在变轻，但规范本身仍在动。

**我们服务商实际走的线格式**（OpenAI 兼容 function calling）：请求 `tools: [{type: 'function', name, description, parameters: <JSON Schema>, strict}]`，`tool_choice` 可取 `'auto'` / `'required'` / 指定函数名；助手侧返回 `tool_calls`（带 call id）并以 `finish_reason` 表明"要调工具"；随后把工具结果按 id 作为 tool / `function_call_output` 消息回送；支持一次并行多个调用；流式下参数以 `*arguments.delta` 增量下发。

**描述质量是资产，不是文案**（arXiv 2602.14878 对 MCP 工具面的实测）：被调查的工具 **97.1% 存在"异味"、56% 缺明确用途**；只增强描述就把调用成功率抬高 **5.85%**，但**步数 +67%**。→ 工具面真正的成本在"契约写得准不准"，而不是"接口开没开"。

**本项目落点**（全部是既有服务能力的再包装，不新造数据通路；先把只读面做扎实）：

| 提案工具 | 背后已有实现 | 语义 hint（照 MCP 词汇） |
| --- | --- | --- |
| `search_canon` / `search_ledger` | `search-service.ts` 的 `results` / `ledgerResults` 双通道 + `coverage` / `reason` 降级口径 | `readOnlyHint=true`、`idempotentHint=true` |
| `get_chapter_plan` | `plan-service.ts` 的章纲五键文档与规范化 | 同上 |
| `get_character_state_as_of` | `ledger-service.ts` 角色上下文（"当前章及之前最新状态" + 过期标记 + 防剧透裁剪） | 同上 |
| `list_open_foreshadowing` | `ledger-service.ts` 伏笔提醒/报告（窗口内与逾期优先） | 同上 |
| `get_canon_excerpt` | `packages/retrieval/excerpt.ts` + `canon_versions`（带版本身份） | 同上 |
| `get_gate_spec` | `dev-v0` 规则集 + `gate_evaluations`（结论仍由服务端算，模型只读规则） | 同上 |

设计要点：**MCP 的 annotations 词汇几乎是为我们的权限模型量身定做的，但它只能当描述性提示用**。真正的保证仍是服务端校验（`assertCanManageStructure`、AI 主体禁写、只写未发布草稿），这条不能因为"标了 readOnly"就松。

### 2.2 循环（agent loop）

Anthropic 的口径把两件事分开：**workflow = 预定义代码路径编排模型；agent = 模型自己动态决定用哪个工具、什么时候停**。并且明确建议"能用 workflow 就别上 agent"；上 agent 必须配 guardrails、最大迭代次数，并**像对待 API 一样测试工具接口**。

OpenAI Agents SDK 的运行语义（可当循环形状参照）：一个 *turn* = 一次模型调用（含它触发的工具调用）；runner 反复循环直到判定为 final output 或发生 handoff；`max_turns` 超限与超时都属于**运行期失败**（不是"结果不好"）；状态可选 `result.history` / `session` / `conversationId` / `previousResponseId`。

**本项目已有的可复用零件**——这是好消息，基座不是从零：

- **钱的维度已闭环**：调用前 `budgetMaxTokens`（`ai-service.ts:1045-1090`：币种不一致直接阻断、按预估输入扣减、剩余预算不足以覆盖预估输入则阻断、可输出 tokens 低于 `MIN_GENERATION_COMPLETION_TOKENS` 则阻断）；`reserveGenerationCall`（`:1381`）；每次尝试后按**真实**成本扣 `budget.remaining`（`:1466-1475`）。预估输入 token 用 `estimatePromptTokens`（`:1040`，字符数×系数，注释里写明"中文正文约 1–2 token/字，按 2 倍预留"）。
- **归属与用量已落表**：`model_calls` 有 provider / chapter / model / prompt_tokens / completion_tokens / cost / latency_ms / status（`packages/db/migrations/0000_init.sql:240-252`），M5-B 又补了作业归属与预留成本（`0012_m5b_billing.sql`）。
- **写入安全与幂等已闭环**：租约、单事务提交、outbox、幂等键、`prompt_version`（如 `m6s-v1`）、审计与 `events` 的人类归因。

缺的三件：**循环本身**（多次模型调用 + 工具结果回灌）、**步维度上限与终止原因**（今天只有尝试次数，那是故障转移语义）、**记录工具调用的表**。

### 2.3 技能（skills = 提示即数据）

`agentskills.io` 规范要点：`SKILL.md` + YAML frontmatter；必填 `name`（1–64 字符、小写、仅连字符）、`description`（1–1024 字符）；选填 `license`、`compatibility`（≤500 字符）、`metadata`、**`allowed-tools`**；目录 `skill-name/SKILL.md` + 可选 `scripts/ references/ assets/`；**渐进披露三级**：元数据 ~100 tokens（启动时全部加载）→ 正文 <5000 tokens（决定用时才读）→ 资源按需读；用 `skills-ref validate ./my-skill` 校验。

Anthropic 的工程叙述把这层定位成"给代理装现实世界能力"的打包单位，靠渐进披露维持上下文信噪比。

**本项目落点**：把"章纲 → 正文 → 门禁 → 提交"这类动线做成**版本化的数据**（任务模板 + 允许的工具集 + 预算 + 终止条件 + 输出契约），这就是今天 `prompt_version` 的延长线，不是新发明。特别注意 `allowed-tools`：**技能自带工具白名单**，天然对上"AI 只读、写要人确认"的既有边界。

### 2.4 可审计轨迹（这才是"思维链"的可用替代）

OTel GenAI 语义约定（**状态仍为 Development**）：span 名 `invoke_agent {gen_ai.agent.name}`、kind CLIENT；`gen_ai.operation.name` 取 `chat` / `execute_tool` / `invoke_agent`；工具参数与结果作为属性记录；用量走 `gen_ai.usage.input_tokens` / `output_tokens`。一个 trace 的形状是：顶层 `invoke_agent` 之下挂多次 `chat` 与多次 `execute_tool`。

**思维链本身的现实**：Claude 的 extended thinking 由 `thinking.type = "enabled"` + `budget_tokens` 开启，但 API 返回的是 **"summarized thinking blocks"**——官方口径就承认交付的是摘要，不是原始推理序列（manual 模式下思考预算由调用方设定；与工具交替使用需要额外的 beta 开关）。

→ **产品结论（也是诚实边界）**：不要把"思维链"当成可审计资产。可审计的是**动作轨迹**：每一步请求了哪个工具、参数是什么、返回的是**哪个版本的哪条数据**、据此得到什么结论、花了多少 token 与多少钱。这与本仓已有的"证据绑定 `content_hash`""建议绑定 `basis_canon_version_id`""门禁结论按上下文哈希失效"是同一套哲学，只是粒度从"一次生成"细化到"一次工具调用"。

中间形态可参考 Anthropic 的 "think 工具"：一个**只写草稿本、不改数据、不取新信息**的显式记录步骤——它的价值正是把推理变成可持久化的动作，而不是指望模型吐出真实思维过程。

## 三、地基盘点：已有 vs 缺口

| 能力 | 已有 | 缺口 |
| --- | --- | --- |
| 读侧证据 | 混合检索双通道 + 降级原因、账本三分区上下文 + `L#` 引用 + 逐条截断、角色状态按当前章截断防剧透 | 这些只能由人类代码预装配，模型不能自己按需取 |
| 判定 | `dev-v0` 规则集 + `gate_evaluations` + 上下文哈希失效 | 模型读不到规则本身，无法解释"为什么会挂" |
| 写入安全 | 租约、单事务提交、幂等键、豁免链、AI 主体禁写、建议→草稿→人发布 | 不需要改；工具面必须完全落在这套权限之内 |
| 成本 | 调用前预算阻断 + 真实成本扣减 + `model_calls` + 作业归属 | **只有"次"的粒度，没有"步"的粒度**；无 run 级预留 |
| 轨迹 | 审计 + `events` + `prompt_version` | **无工具调用级持久化**（无 `agent_runs` / `agent_steps` 类表） |
| 模板 | 硬编码提示 + `m6s-v1` 版本号 | **无作为数据的技能/工具白名单/终止条件** |

## 四、三条候选路径（只比较，不实施）

**A. 进程内 tool loop**：在 API/worker 内实现 OpenAI 兼容 `tools` + 多轮回灌，配 run 级预算与步数上限。改动面最小，预算/审计/权限全部现成复用。代价：又一条长循环路径要管中断与回收（M6-7 已有 `generating`>10 分钟、`applying`>5 分钟的回收先例可沿用其形状）。

**B. 只读 MCP server**：把同一批工具按 MCP 暴露给外部代理（本机的编码/写作代理可直连云说的账本与检索）。不新增任何写入面，最能验证"边界可被调用"这件事的价值。代价：多一个进程与鉴权链路；2026-07-28 规范仍在演进，OTel 约定未 stable。

**C. 技能/模板层**：纯数据层（模板 + 允许工具集 + 预算 + 终止）。**依赖 A 或 B 先存在工具面**，单独做没有落点。

共同前提：**工具定义一处写、两处服务**（A 与 B 共用同一份 schema 与描述文本），否则描述质量会被那两个实测数字同时惩罚（成功率 +5.85% / 步数 +67%）。

我倾向的次序（**待你裁决，不启动**）：A 的最小闭环（3–5 个只读工具 + 2–3 轮上限 + 步级轨迹表）→ 在**真实规模正文**（2500–3500 字/章）上测一次质量、延迟与成本 → 再决定是否做 B 与 C。

## 五、诚实边界与未验证清单

1. **Atria 是否支持 `tools`/`tool_calls`：未测。** 本仓对它的真实实测只有 chat 与失败样本（README 的 M6-7 验收记录：10 条 `model_calls` 中 4 成功 / 4 超时 / 1 无可响应内容 / 1 中断清算）。任何"能循环"的假设都必须先用一次真实探测坐实，才配写进实施计划。
2. **成本乘数是外推，不是实测**：一次代理运行 = N 次模型调用 + N 次工具。按 M6-7 单条建议 592/501 tokens 的实测量级推，3 轮上限最坏约 3 倍；这要求预算逻辑从"按次预留"改成"按 run 预留、按 step 扣减"。**3 倍是算术外推。**
3. **吞吐不可类比**：账本投影 24.87 条/分钟、正典投影 28.33 章/分钟都是本机 `bge-m3` 嵌入的串行节奏（且采样显示当时不止一个 worker 在领任务），不能用来推断 chat 循环的延迟；循环的真实延迟未测。
4. **轨迹落地选型未定**：OTel GenAI 约定仍是 Development；自建表 vs 导出 OTLP 是两条路，本研究不预设。
5. **千章规模下的读放大没测**：`/timeline` 每次请求全量扫描当前正典（700 万字中位 126ms；并发 8 时中位 628ms、吞吐卡在约 10 req/s）。一个 run 内多次调用会把这条曲线乘上步数——这正是"工具面"引入的新性能问题，必须先测再吹。
6. **质量评估集仍为空**：建议质量没有评估集；检索质量那组数字（词法 hit@1 80.0% / 自动 MRR 0.889、5 条无答案对照仍返回 2/4 条）明确只用于回归对比。工具循环改变的是"模型能否自己找依据"，不改变"我们知不知道它找得对不对"。
7. **本轮未做**：未跑类型检查与测试（无代码改动）；未建任何迁移；未启动任何长任务。
