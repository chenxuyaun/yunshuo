## 二、先摆事实：这个仓里的"服务商行"就是"模型行"

**`model_providers` 一行一个模型**（`packages/db/migrations/0000_init.sql:230-238`）：建表时 `base_url text NOT NULL` 与 `model text NOT NULL` 同列；后续迁移在这行上加的是 `purpose`（`0006_m4_retrieval.sql:1-6`）、价格与优先级（`0005_m3_runtime.sql:1-21`）、密钥与 `last_test_*`（`0001_model_provider_secrets.sql:1-12`）。面板上"加一个服务商"就是"加一行模型"。这个仓里**不存在**"一个服务商行挂着多个模型"的形状。

这直接影响 ADR-0001 的选项对照。它反对 (b) 的原文是（`docs/adr/0001-model-capabilities-storage.md:24`）：

> 选项 (b) 把能力塞进服务商行，但能力是**按模型**的属性，服务商改一个模型就要改整行 JSON，且没法对单模型建约束。

**这句在本 schema 里不成立**：行本身就是模型，"按模型"与"按行"是同一件事；改一行的 `model` 字段本来就是改这一个模型。分层设计 L0 行内同族的担心——"元数据按服务商存就废了"（`docs/云说-模型侧基座分层设计-2026-10-26.md:80-91`，"为什么要按模型而不是按服务商"一段）——担心的是一种本仓不存在的存法。

ADR 的三条正面理由（可展示 / 能在生成前阻断 / 能按模型区分）在 (b) 下全部成立：面板读的是本行、生成准入拿到的也是本行。所以它们区分不了 (a) 与 (b)，这道题需要重新划线。

顺带一处细节：ADR 写的 (a) 键是 `provider_id + model`——在本 schema 里 `model` 已经在这行上，卫星表再存一份就是**两份拷贝**，两处不一致就是漂移（本仓在 AGENTS.md §四.1 点过名的缺陷类）。真做 (a)，键只能取 `provider_id`（严格 1:1 子表）。

## 三、真实的分界线：三条证据

### 证据 1：`last_test_*` 是"探测结果落列"的现成先例，整条链都在

`0001_model_provider_secrets.sql:1-12` 加的 `last_test_status`（CHECK `ok`/`failed`）/ `last_test_message` / `last_test_latency_ms` / `last_tested_at`，就是一次探测的快照落在这行上。配套三个点全都现成：

- 写点：`testProvider`（`apps/api/src/services/provider-service.ts:739` 起）尾部一次 UPDATE。
- 清理点：`updateProvider` 的 `connectionChanged`（`:369-370`，base_url / model / 密钥任一变化）在同一个 UPDATE 里清空四件套（`:384-387`），审计里记 `clearedTest`（`:403`）。
- 展示点：`listProviders` 用 `SELECT *`（`:252` 起），但每行过 `mapProvider` 显式白名单（`provider-service.ts:147-173`，`lastTest` 手映射 `:161-169`）——新列**不会**自动进面板；要可见需同时扩白名单与契约 `ModelProviderView`（`packages/contracts/src/index.ts:849-865`），契约加可选字段不触发 TS 报错，运行时该键为 `undefined`。

能力元数据与 `last_test_*` 是同一物种：一次探测、覆盖式更新、随连接变化失效。抄它就等于零新形状。

### 证据 2：chat 侧今天只落连通性测试快照（`last_test_*`），嵌入侧只有审计——(c) 缺的不是历史，是配置

- `discoverModels`（`:591-646`）完全无状态：模型列表即时返回，不落库。
- `probeEmbedding`（`:648-737`）的探测结论只进审计：`writeProbeAudit`（`:234-250`）写 `audit_log`（action `model_provider.probe_embedding`，metadata 带 baseUrl/model/dimensions/latency/promptTokens/errorKind），`model_providers` 行上什么都不写，界面刷新即失。

也就是说，**历史通道已经存在**（`audit_log`）。(c) 的问题不是"没留下痕迹"，而是"留下的痕迹不能当配置用"——ADR 这句判断是对的，保留。同时它也说明：(a) 相对 (b) 的"可审计、可存历史"优势**不存在**——审计与快照是两条通道，任何方案下都应并存：**审计存证据，行内存结论**。

### 证据 3：1:1 卫星表有先例，但近亲是 `last_test_*`

仓里确实有 1:1 子表：`index_status`（`0000_init.sql:216-222`）、`chapter_metadata`（`:224-228`）。它们的共同点是**写方为派生流水线**（索引构建、字数统计），读方是全站。而"探测结果"这个物种的写方是面板上的一个动作、读方是同一面板与生成准入——近亲是 `last_test_*`，不是 `index_status`。

## 四、建议：取 (b) 的逐列版本（不是 JSONB）

```sql
ALTER TABLE model_providers
  ADD COLUMN tools_capability text NOT NULL DEFAULT 'unknown'
    CHECK (tools_capability IN ('supported_and_called','supported_ignored','rejected_field','unknown')),
  ADD COLUMN structured_output text NOT NULL DEFAULT 'unknown'
    CHECK (structured_output IN ('supported','rejected','unknown')),
  ADD COLUMN context_limit integer,
  ADD COLUMN capability_probed_at timestamptz,
  ADD COLUMN capability_probe_message text;
```

（列名与粒度可按评审改；关键是"逐列 + 库级 CHECK + 行内快照"这个形状。）

**要人确认的那一句**：既然 `model_providers` 一行就是一个模型，能力快照就落在这行上——"配置行里放探测状态"这条纪律是否接受（先例：`last_test_*` 已经这么住了）。

理由：

1. **抄先例抄的是写点与清理点**：这两处是现成的（证据 1），DB 层零新增结构、零新增查询；但展示点要扩 `mapProvider` 白名单才可见（`provider-service.ts:147-173`），准入点今天不存在——`loadGenerationProviders`（`provider-service.ts:537-587`）只按 `is_enabled`/`purpose` 过滤，按能力阻断的代码要新写。
2. **CHECK 在列上**：ADR 的 (b) 字面写的是 JSONB——那确实差（四态合法集只能靠 Zod 守，库里没有约束）；**逐列是它没列出的第三形状**，与 `last_test_status` 一样由库守。
3. **(a) 会多三笔账**：多一次 JOIN 或第二次查询（面板与 L2b 准入都在热路径）；多一个 FK 删除语义（`deleteProvider` 是硬删，`:411` 起）；多一个必须记得同步的清理点——`connectionChanged` 清 `last_test_*` 时还得跨表清能力行，"两处要改、忘了一处"正是本仓点过名的缺陷模式。
4. **可逆性**：两个方向都是一次迁移，决策不沉重。

**代价如实标注**：行继续变宽（现在已约 20 列）；"配置"与"探测状态"同住一行（先例已在）；`purpose='embedding'` 的行上能力列永远是 `unknown`（无害，面板显示"未探测"即可）；若未来要"探未配置的模型"（比如先探 8 个再决定加哪个），(b) 表达不了——今天没有这个排期，这是 (a) 唯一真实的长期优势。

**若拍板人仍取 (a)**：不是错的选择，需接受三笔配套账：① 键只取 `provider_id`（严格 1:1，不重复存 `model`）；② `connectionChanged` 清理跨表（同一个事务里清空/删除卫星行）；③ `deleteProvider` 的 FK 语义取 `ON DELETE CASCADE`（与 `last_test_*` 随行消失一致）。同时 ADR-0001 的理由段要按 §二 更正。

## 五、口径三条（拍板时一并签）

1. **四态含义照分层设计（`:86`），不改名**：`supported_and_called` 是唯一"可用"态；`supported_ignored`（吃了 `tools` 字段但不调用）与 `rejected_field`（400 拒绝字段）都算"这条路暂时不能用"；`unknown` = 未探测。**不美化**（硬规则 4）：面板对 `unknown` 显示"未探测"，不显示"支持"。
2. **`structured_output` 用三态**（`supported` / `rejected` / `unknown`），且 `supported` 的口径是"**接受 `response_format` 并返回过合法 JSON**"，不是"永不失败"——M6-7 实测到过 1 次非 JSON（`LEDGER_SUGGESTION_NOT_JSON`，`ledger-suggestion-service.ts:1044`），它证明"支持"与"稳定"是两个词。真实失败率留在 `model_calls` 里看，不塞进这一列。
3. **`context_limit` 空值 = unknown**，不猜。探测方法的边界写进实现注释：一次性最小请求探不出真实上下文上限，v1 只记"探到就填，探不到留空"。
