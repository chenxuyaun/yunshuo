> **用途**：D5 单独一场拍板。读本文 + [ADR-0005](adr/0005-termination-defaults.md) + 文内代码位点即可，不必先读分层设计全文。

> **与 ADR-0005 的关系**：三个数都按 ADR 的方向落，但其中两个的**依据要换**——`max_steps=3` 这次有可推导的硬约束（不是"保守起见"），墙钟从"未标定"升级为"上界可推导"。另更正分层设计 L2b 行三处文本，其中一处（"45 秒"）与代码不符。

## 一、这一场要拍的三件事

| # | 问题 | 本文建议 |
| --- | --- | --- |
| ① | `max_steps` 取几 | **3**。10 分钟 stale 回收形状下，可推导的硬上限是 4，3 留余量（§三①） |
| ② | 单 run 成本上限怎么落 | **不设 run 级数字**：每步每次尝试过两道现有闸门，`runs` 上只累计 `spent`；"run 级预留、step 扣减"不采纳为 v1（§三②） |
| ③ | 墙钟上限 | **不新造数字**：上界可推导 ≈ 6 分钟（提案路径）；拍的是**不变量**，不是数字（§三③） |

## 二、事实（全部来自代码，2026-10-27）

### 2.1 两条生成路径，两个超时常量——分层设计把它们混成了一条

| 路径 | 常量 | 值 | 语义 |
| --- | --- | --- | --- |
| 提案生成 | `AI_TIMEOUT_MS`（`apps/api/src/services/ai-service.ts:48`） | **120 秒** | `:1327` `deadline = run.startedAt + AI_TIMEOUT_MS`；`:1134` 每次尝试的超时 = `deadline − now` → **120 秒是整个调用（含全部 failover 尝试）的硬截止**，不是"每次尝试各 120 秒" |
| 账本建议（M6-7 单发） | `GENERATION_TIMEOUT_MS`（`ledger-suggestion-service.ts:40`） | **45 秒** | `:576` 直接作 `AbortSignal.timeout` 的单次尝试超时；该路径自带提供方 failover（`:923` `for (const provider of routing.providers)`、`:41` `MAX_TOTAL_ATTEMPTS = 2`、`:981-985` canRetry），每次尝试各自 45 秒超时 |

分层设计 L2b 行 ③ 写"单次调用 **45 秒**超时沿用"——45 秒属账本建议路径；L2b 的前置小重构（抽 `ai-service.ts:1169` 的 chat 调用（`const response = await fetch(…)`；`:1166` 只是请求体里的 `messages: run.messages,`））落在提案路径。**run 装到哪条路径上，沿用哪个数**，设计文档必须先把这一点说清，否则"沿用"一词本身没有指向。这是要更正的文本（§四·1）。

### 2.2 钱：两道闸门已经都在，且都挂在"每次尝试"上

- **外层授权（mandate 预算）**：`automation-runner.ts:302-320` 读 `automation_mandates.budget_limit` 减去已花，作为 `ProposalBudget`（`ai-service.ts:78`、`:493` `runtime.budget`）传进生成调用；`budgetMaxTokens`（`:1049-1094`）**每次尝试前**判（`:1365`），拦下即 `BUDGET_INSUFFICIENT` / `BUDGET_GUARD_UNAVAILABLE`，**失败后**（`:1464` `markCallFailure` 之后）按真实用量扣 `remaining`（`:1469-1480`；`remaining` 在全文件的唯一写入点是 `:1478`）。预算存在调用方、不存 run——**这就是状态机 §十一 Q3 说的"外层授权"，它已经在**。
- **工作区月度（全局上限）**：`reserveGenerationCall`（`billing-service.ts:530`）**每次尝试前**预留（`ai-service.ts:1384`）；`workspace_budgets` 未配置时放行但仍记 `model_calls`（`streaming`、`reservedCost: null`）；先清算过期预留再判。
- 两道是嵌套关系（"这个任务最多花多少" × "这个工作区这个月最多花多少"），每步都过。**ADR-0005 的"每步都过已有闸门"与代码现状完全一致，落地零新机制。**

### 2.3 墙钟：上界可推导，且与 stale 回收阈值之间有一条不变量

- 推导式：**单 run 墙钟上界 = `max_steps` × 单次调用硬截止 + 工具执行时间**。提案路径代入：3 × 120 秒 = **360 秒 ≈ 6 分钟**。
- 工具时间这一项不是零：v1 工具里检索可能触发一次查询嵌入，该路径生效的超时是 `apps/api/src/services/search-service.ts:29` `QUERY_EMBED_TIMEOUT_MS = 10_000`（`:468-470` 传给 `embedBatch`；`packages/model-gateway/src/embedding-client.ts:144` 是 `options.timeoutMs ?? DEFAULT_TIMEOUT_MS`，故 10 秒覆盖 20 秒）；`:465` 在候选服务商上串行循环、候选上限 3（`packages/model-gateway/src/embedding-providers.ts:7` `MAX_EMBEDDING_PROVIDERS = 3`、`:73` slice），超时项上界 3 × 10 秒 = 30 秒。每步工具调用数上限 L2b 未定，推导时按实际工具集累加。
- 仓库里有两个既有 stale 回收常量：账本建议路径 `ledger-suggestion-service.ts:47` `STALE_GENERATING_MINUTES = 10`（`:1163-1173` 按 `created_at < now() − 10 分钟` 回收）；作业/run 形状路径 `automation-runner.ts:31` `STALE_AFTER_MS = 5 * 60_000`（`:847` 按 `heartbeat_at` 回收），状态机 §八 的回收 UPDATE（`:113-117`）用的也是 `interval '5 minutes'`。L2 沿用哪一个尚未定；沿用其中任一个，都必须满足：
  **`stale 回收阈值 > max_steps × 单次调用硬截止 + 工具时间上界`**。
  10 分钟下，`max_steps` 的硬上限是 **4**（4 × 120 = 480 秒，余 2 分钟）；**5 会贴边**（5 × 120 = 600 秒 = 10 分钟整，任何工具开销都会让活着的 run 被判 stale）。分层设计"3–5"里的 5，**不是口味问题，是撞不变量**。

### 2.4 DDL 落点（状态机候选 DDL `:153-155`）

- `:153` `max_steps integer NOT NULL`（无 DEFAULT）：值由 run 创建处的一个程序常量写入，循环从 run 行读。**不设 DB 默认**（DB 默认会变成第二个来源，且改默认要迁移）；v1 不开放给请求方传（模型无权改，调用方也不该能调松）。将来若由模板/mandate 决定，属 L3 授权模型。
- `:154` `budget_limit`：按 [D9 材料](云说-模型侧基座-D9拍板材料-2026-10-27.md) §5.3 从候选 DDL 删除；`:155` `budget_spent` 改名 `spent`。D9 §5.3 只是该材料的建议（自述「材料，未拍板」），本场不重复展开，只确认 §三② 与它一致。

## 三、建议（逐条）

### ① `max_steps` = 3——这次是可推导约束下的选择

- 硬约束（§2.3）：10 分钟回收形状下 `max_steps ≤ 4`。
- 在 ≤4 内取 3：完成"检索 → 再检索 → 生成"最小证据链足够；留 4 分钟 stale 余量；不给注入留长链（分层设计 L2b 的威胁口径）。
- **口径**：3 是"约束内的保守选择"，不是"测出模型需要 3 步"。界面与 README 上必须能看出它是暂定的——硬规则原话：**"阈值要么可推导要么如实标'未标定'，不许拍脑袋当能力。"**
- 若 L2 选的 stale 阈值不是 10 分钟，按 §2.3 的不变量重算，不照抄 3。

### ② 成本上限：不设 run 级数字，每步过两道闸门

理由三条：

1. 两道闸门已经在每次尝试上（§2.2），零新机制；
2. "run 级预留"会引入第三个钱数。状态机 §十一 Q3 把这一点列为拍板时要回答的问题（`:205`，未裁）"两者不能同时存在，否则'谁有最终否决权'说不清"；现有两道是"外层授权 × 全局上限"的嵌套，语义清楚，再加一层就浑了；
3. D9 §5.3 **建议**把 `budget_limit` 从 `runs` 删掉（该材料自述「材料，未拍板」：`云说-模型侧基座-D9拍板材料-2026-10-27.md:4`），本场再引入 run 级预留，是同批拍板内自相矛盾。

**代价如实标注**：v1 没有"单 run 最多花 X"这个数字。极端情况（无 mandate 授权、工作区当月预算充裕）下，一个 run 最多消耗 `max_steps × 每次尝试` 各自允许的余额，上界是"当月剩余预算"，不是一个小数。若要收紧，唯一不拍脑袋的做法是把外层授权接上（mandate 的 `budget_limit` 已是现成形状），属 L3。

### ③ 墙钟：不新造数字；拍"上界推导 + stale 不变量"

- 上界可推导（§2.3），按硬规则"可推导"优于"未标定"：材料与界面写**推导式与代入值**，不写拍出来的分钟数。
- **不设独立的 run 级定时器**：单次调用硬截止已把每次尝试、每次 failover 关进 120 秒；步数上限把调用次数关进 3；乘积即上界。再加一个 run 级定时器不改变上界，只引入"它和单次超时谁先触发"的语义问题。
- **L2 验收钉一条不变量测试**：`stale 回收阈值 > max_steps × 单次调用硬截止`（两个常量都在代码里，用测试钉关系，防未来单边调参）。这是本场对"墙钟"这一格真正的拍板物。

### ④ 超限语义：沿用状态机，不新增

三种越界（步数/钱/墙钟）都进 `failed` 并记终止原因（状态机 `:59`），不是 succeeded 的降级——"**超限是运行期失败，不是'结果一般'**"（分层设计原话）。取消（`CLIENT_ABORTED` 口径）与超限是两回事：取消只停后续步骤、已发生的账不动（L2 行是候选设计，未拍板）。

## 五、本文没做的事

- 没定每步的工具调用数上限与工具执行时间预算——v1 工具以本地只读查询为主（检索可能带一次查询嵌入，超时项 ≤10 秒 × 最多 3 个候选服务商 = 30 秒）；**若将来有外部 HTTP 工具，这一格必须补**，否则墙钟上界推导不成立；
- 没定 `max_steps` 将来由模板还是 mandate 决定（L3）；
- 没有改任何代码、DDL、ADR。
