## 二、先摆事实

### 2.1 流式在本仓的接触面清单（全在，且都是"降级档的承重件"）

- 请求侧：`stream: true` 写死在提案请求体里（`apps/api/src/services/ai-service.ts:1162`，body `:1160-1167`），流式专有字段 `stream_options` 条件拼装（`:1165`）。
- 解析侧：SSE 三件套 `parseSseEventBlock`（`:683`）、`iterateSseEvents`（`:696`）、`parseChatSseData`（`:736`，至 `:786`）＋ `executeAttempt` 里的 SSE 消费分支（`:1213-1231`）。
- 降级探测：`streamOptionsUnsupported` 靠字符串匹配 `HTTP 400` + `stream_options`（`:1254-1260`）——流式专有的一道缝。
- 路由层：`reply.hijack()` + `text/event-stream`（`apps/api/src/routes/ai.ts:36-38`）、断开即 abort（`:49`）、心跳（`:54`）。
- 前端：事件分发 `apps/web/src/api.ts:540-558`（delta/attempt/done/error）、逐字预览 `apps/web/src/components/AiProposalPanel.tsx:148`。

### 2.2 关键事实：这套解析器对工具调用是"看不见"的

`parseChatSseData` 只读 `choices[0].delta.content`（`ai-service.ts:775`）——**没有任何 `tool_calls` / `finish_reason` 分支**。ADR-0003 指出的复杂度（工具调用参数按 delta 拼接、跨块边界、文本/工具调用分流）在这套代码里一处都还没有；循环要流式，就必须把它从"逐块读文本"改写成"增量累积器"，而这份代码正是降级档要原样复用的那份（见 §三.1）。

### 2.3 非流式在本仓不是"新造的路"，今天已有真实服务商验收实测（`README.md:405`；「可对外生产使用」按 `docs/云说-M6规划与阶段回顾-2026-10-22.md:19` 仍「未达成」）

账本建议路径就是非流式：`stream: false`（`apps/api/src/services/ledger-suggestion-service.ts:570`，`callModel` 起于 `:551`），一次完整请求-响应，`AbortSignal.timeout(45_000)`（`GENERATION_TIMEOUT_MS:40`）。服务端 `executeAttempt` 也已有非 SSE 响应分支（`ai-service.ts:1191-1212`，按 content-type 分流后 `parseChatSseData(JSON.stringify(payload))` 复用同一解析入口）。L2b 的"非流式循环"是走一条已有形状的路。

### 2.4 "第 N 步"进度今天零实现

全仓没有步数进度 UI；最接近的是 `AiProposalPanel.tsx:149` 的 `onAttempt`（"第 N 次调用失败"重试提示，事件来自 `api.ts:546`）。注意："非流式"约束的是**模型调用**，不是浏览器侧事件通道——进度事件仍可走现有 SSE 通道（`routes/ai.ts:36-54`）推给界面。

### 2.5 L0 能力结论是非流式口径

`docs/云说-L0探测结果-2026-10-27.md` 全文 0 处提及 stream/SSE——"3B 支持 tools/json/tool_choice"的结论全部在非流式下取得。而"流式 + tool_calls"这个组合，仓里没有一行证据（哪个服务商在流式下怎么返回工具调用，未验证）。

## 三、真实的分界线

ADR-0003 已摆的两条理由（复杂度是实打实的、收益是体验性的；正确性风险会落到终止判定与成本记账）不再重复。补充三条本仓事实：

1. **流式解析器是降级档的承重件。** ADR 已写明"流式代码不能删"（`docs/adr/0003-loop-streaming.md:26`）：L2b 塌了的时候降级档就是今天的单发（`tool_choice='none'` + `max_steps=1`）。如果 v1 循环顺手把解析器改成增量累积器，降级档就不再是"出事前验证过的同一份代码"。非流式先行，解析器一行不动。
2. **能力元数据与循环形态同口径。** L0 的 tools 能力四态是非流式口径（2.5）。先非流式，循环与能力元数据同口径；将来要补流式工具调用，那是一次**新增探测**，不是推翻旧结论。
3. **体验回退是真的，但可以隔离。** 非流式唯一的真实代价是长 run 期间无逐字输出。界面仍可用 SSE 推步数（2.4），把"卡住"与"在跑"区分开；ADR 已给回退路径：将来可只对"最后一步的文本生成"恢复流式（`0003-loop-streaming.md:31`），那时工具调用已结束，拼接复杂度不再存在。

## 四、建议：取 (a) v1 非流式（与 ADR 一致）

**要人确认的那一句**：接受"长 run 期间界面只能显示步数、不能显示正在生成的文字"——这是用户可见的体验回退，拍板后写进 README 诚实边界。

**代价如实标注**：

- 体验回退（上句）；界面要新增一套步数展示逻辑，与现有逐字流式并存（两套展示逻辑）。
- 非流式下单步耗时全部暴露为静默等待：生成 2500–3500 字的一步可能几十秒，界面必须用真实状态文案（"正在生成，需等待完整响应"），不伪造进度条（硬规则 4）。
- 将来"最后一步恢复流式"是**新增**而非回退——展示逻辑要再做一次，这笔账现在先记下。

## 五、口径两条（拍板时一并签）

1. **进度显示的下限**：至少显示 `第 N / max_steps 步`；是否显示工具名（如"正在检索正典"）留给 L2b 实现评审。**不显示模型正在生成的文字**是硬口径（否则等于把流式偷偷做回来）。
2. **流式代码冻结**：L2b 期间 `stream: true` 路径与 SSE 解析器不动；任何"顺手清理/改写流式代码"的改动都视为改动降级档，单独评审。
