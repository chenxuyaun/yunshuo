## 二、第 1 件：二选一

**建议 (a)：新建 `runs` / `steps` / `tool_calls`，`automation_jobs` 一字不动。**

论证在 [ADR-0009](adr/0009-run-engine-storage.md) 里，核心是一条不对称性，不重复：

- 走 (a) 最坏是**多一套表**（可事后合并）。
- 走 (b) 最坏是**无人值守链路回归**（当前唯一"真金白银、无人值守、已验证"的部分，它的价值恰恰来自没人再动它）。

配套纪律是"形状照抄它，别自创一套"——**抄做法，不碰它的表**。第 4 件要更正的正是"抄"这件事本身抄错了的地方。

## 三、第 2 件：L2 是否先停在"确定性 run"

分层设计 §七 给了这一档（`：264`）：把 M6-7 的单发建议改造成"一个 run、两个 step（装配上下文 → 生成）"，零循环、零新增成本，但 `run_id`、状态机、检查点、取消与恢复全部就位。

它与第 1 件强相关但不是同一件事：

- 只有 (a) 成立时这一档才便宜。若泛化 `automation_jobs`，这次重构就要动那条链路，"零新增成本"不成立。
- 反过来，(a) 成立也不自动意味着该走这一档——那是"要不要现在就把 L2 落到线上路径"的判断。

**建议：走这一档。** 理由：它把 L2 的状态机、幂等键、检查点、取消/恢复全部拉到**真实流量**上验证一次，而验证成本只有一次 M6-7 单发调用的重构；若停在纸面直接上 L2b（循环），状态机的第一份证据将出现在"已经在循环里花钱"的路径上，出错代价高一个量级。

## 四、第 3 件：三个问题

### 问题 1：状态集要不要再删减（`paused` 是否必要）

**建议：不删减，8 个状态全保留，v1 就实现 pause/resume。**

- 抄 `automation_jobs` 的形状是第 1 件的配套纪律；单独砍掉一个状态就是自创一套。
- `stopped` 是终态。若删掉 `paused`，人对 run 的唯一控制就是**不可逆终止**——而 run 会花钱。
- 删减省下的只是两条转移用例；代价是 L2b 加循环时必须回来改 CHECK 合法集、runner 认领条件与已有用例。仓库自己的历史已经证明这个方向更贵：状态机文档 §一 记载 `automation_jobs` 的 `paused`/`stopped`/`interrupted`/`precheck_failed` **都是后来补的**，"每次补都牵动 runner 的认领条件、前端轮询口径与一堆用例"。

### 问题 2：`interrupted` 的恢复次数上限

文档要求这个数"必须是可推导的，不能拍脑袋"。给两条可推导的候选：

| 候选 | 推导依据 | 缺点 |
| --- | --- | --- |
| (α) 由工作区月度预算推导：不设独立次数，余额不足时恢复自然失败 | 每次恢复都要再花钱，而金额闸门已经存在且每次调用前都过一遍 | 不是"次数"界，撞上时 run 会以预算不足而非"恢复耗尽"结束 |
| (β) `max_recoveries = max_steps` | 恢复的最坏代价是**把整个 run 从头重跑一遍**，那正好是 `max_steps` 次 | 与金额闸门各管一头，两者不冲突 |

**建议：取 (β)，金额那一头交给既有月度闸门，不在恢复准入里再写一遍。** 准入条件写成：

```
interrupted → running  当且仅当  recovery_count < max_steps
```

`max_steps` 是建 run 时的必填，没有引入新的魔数；"钱够不够"由 `reserveGenerationCall` 在每一步的真实调用前回答（它本来就会拒），在恢复准入里重复一遍就是第二个真相源——正是 D5（[ADR-0005](adr/0005-termination-defaults.md)）禁止的"另造一套"。超出即 `failed`。

**这条同时给了一个需要人确认的口径**：`recovery_count` 必须落列——否则"恢复了几次"无法审计，也就无法回答"这次 run 为什么被判 `failed`"（`max_recoveries` 本身可以不落列，由 `max_steps` 现算）。

### 问题 3：`budget_limit` 在不在 `runs` 表上

先把**已有的金额闸门**摆准——它们决定了这道题的真实选项：

| 闸门 | 范围 | 位置 | 未配置时 |
| --- | --- | --- | --- |
| `reserveGenerationCall` | 工作区**月度**（`workspace_budgets.monthly_limit`，一工作区一行） | `billing-service.ts:530` | **整条闸门跳过**，调用照发（`billing-service.ts:544`） |
| `automation_mandates.budget_limit` | 单张授权**累计** | `automation-runner.ts:302` / `:400` / `:431` | 该授权无上限 |
| 单次调用预留 | 单次调用 | `model_calls.reserved_cost` | — |

**关键事实：今天没有任何一处是"单 run 上限"。** `automation_jobs` 也只记 `spent` / `cost_currency` / `cost_unknown`，**不设 `budget_limit`**——预算是外层授权的属性，而 `mandate_id` 是 `NOT NULL`，每个作业必然有外层授权。

但状态机文档 §二 已决定 `runs` **不抄 `mandate_id`**（"Run 的授权来自调用方的会话"）。所以 v1 的 run 没有外层授权载体，能依靠的就是上表第一行。

**建议：不放 `budget_limit`，照抄 `automation_jobs` 的 `spent` / `cost_currency` / `cost_unknown` 三件套。** v1 的成本上限由**工作区月度预算**承担——它是当前唯一被签过、且每次真实调用前都过一遍的金额闸门。

- 这条与"形状照抄 `automation_jobs`"一致：它本身就没有 `budget_limit`。把 `budget_limit` 加到 `runs` 上会让 `runs` 成为**第二个可以改预算数字的地方**，而"谁有最终否决权"正是文档要避免的模糊。
- 与 D5（[ADR-0005](adr/0005-termination-defaults.md)）一致：那里已定"成本上限不新定一个数，已有闸门在每次调用前都过一遍，循环里每步都过即可，不需要另造一套"。
- **代价要如实标注**（这两条是本题真正的风险，不是可以省略的脚注）：月度闸门是**工作区级**的，一次 run 可以把当月剩余额度一次吃掉；且工作区**未配置** `workspace_budgets` 行时整条闸门不生效。第 2 件若选"走确定性 run"，v1 的 run 只有两个 step，爆炸半径是 2 次调用，可接受；**一旦有循环（L2b），这两个缺口必须重新过一遍**——届时才轮到"给 `runs` 加 `budget_limit`"或"给工作区加单次上限"，而不是现在先建一个没人读的列。

**要人确认的那一句**：接 `automation_mandates` 之后，run 的上限来自外层授权，`runs` 仍不设 `budget_limit`——即"预算永远不在 run 表上"这条纪律是否接受。若接受，文档担心的"两者并存、否决权说不清"就不存在了。

## 五、第 4 件：对照 ADR、分层设计与候选 DDL 时发现的三处缺陷（更正，不需选）

### 5.1 幂等索引的谓词：三份文本两种口径，真正的分歧在"键的构成"（必须更正文本）

三处说法，两种口径：

- [ADR-0009](adr/0009-run-engine-storage.md) `：36`："**部分唯一索引**做幂等（照 `0019_ledger_suggestion_generating_unique.sql` 抄形状，别手工判重）"。
- 分层设计 L2 行 `：121`："同 `(chapter, 模板版本, canon_version_id)` 只允许一个**在途** run，用部分唯一索引（照 `0019…` 抄形状）"。
- 状态机文档 §八 `：125`："唯一性**无条件**，不按状态过滤。同一幂等键重试必须返回同一次 Run（200 + 原 `id`）。" 候选 DDL `：119` 给的是无 `WHERE` 的唯一索引；同节还引 `commit_intents` 作先例。

初看像"两票对一票"，实际是**两个不同的问题被写成了同一个句子**：

| | 键 | 谓词 | 语义 | 谁在用 |
| --- | --- | --- | --- | --- |
| 并发互斥 | 目标键（`entry_id` / `(chapter,模板,正典)`） | **非终态集** | 同一目标同时只有一个在跑；终态后允许再来一次 | `0019` / M6-7 今天；分层设计 |
| 一目标一次 | **带新鲜元素的键**（`commit-${staged.id}`） | 无条件 | 同一目标永远只有一条 | `commit_intents` / 回滚 |

第二行在 `commit_intents` 成立，不是因为它选了"无条件"，而是因为它的**键里带了每次真实意图都会变的新鲜元素**（`CommitDialog.tsx:21` 的 `commit-${staged.id}`、`RollbackDialog.tsx:38` 的 `rollback-${chapter}-${version}-${target}`），且"提交同一草稿两次"本来就是无意义的重复——它必须返回既有结果。状态机 §八 把它的**谓词**照搬，却配了一个**没有新鲜元素的键**（`suggest:<chapter_id>:<plan_revision>`）——后果是同一章同一版纲**只能生成一次建议，拒绝后无法再生成**。这与 M6-7 今天的已交付行为直接冲突：

- 今天的谓词是 `(entry_id) WHERE status='generating'`，错误文案自己写着"同一条目**同时**只发起一次模型调用"（`ledger-suggestion-service.ts:912-915`）——口径是并发互斥；
- 终态之后同一条目**可以再次生成**（建议列表保留历史多条，接受/拒绝只作用于单条）。

若按 §八 的无条件唯一建 `runs`，把 M6-7 改造成确定性 run 的那一刻，"拒绝后重生成"这个今天存在的能力会**静默消失**（同键提交返回 200 + 原 run id，用户拿到的是那条被拒绝的旧建议）。

**建议：`runs` 用部分唯一索引，谓词取"非终态集"**——即 §三 四个终态（`precheck_failed` / `stopped` / `completed` / `failed`）的补集：

```sql
CREATE UNIQUE INDEX runs_one_active_per_goal_idx
  ON runs (workspace_id, idempotency_key)
  WHERE status IN ('queued', 'running', 'paused', 'interrupted');
```

- `queued` 必须在谓词里：两笔并发提交之间，赢家的行还停在 `queued`；谓词若只写 `running`，第二笔会漏过去。
- `interrupted` 必须在谓词里：它是**非终态、可恢复**（§三）。若排除它，一笔 `interrupted` 的行会与"同键新建的第二条"同时存在，之后前者被恢复成 `running`——同一目标两条在跑，"同一目标同时只有一个在跑"在库层失效。
- 终态后同键提交 = **再生成**，不是重复请求；新建一条 run 是正确行为，与今天一致。ADR 验收② 的"重复提交"用例应钉**在途期间**重复提交不产生第二条 run / 不产生第二次模型调用，而不是"永远只有一条"。

这一档还有一笔要在 L2 开工时落地的账：**`interrupted` 占着目标不放**，而它转 `failed` 需要"恢复次数耗尽"，若没有任何 runner 去尝试恢复，目标会被永久占住。今天 M6-7 的回收是**直接判 `failed`**（终态，立即释放，`0019` 与 `reclaimStaleSuggestions` 都是这个口径），状态机选了 `interrupted`（可恢复），两者对"目标多久释放"的影响不同。可选口径（留到 L2 实现时定）：同键提交撞上一笔 `interrupted` 时，服务端**把它当作恢复触发**（继续它，而不是报错）——这正好就是 ADR 验收② 的"重复提交"用例。

**要抄 `0019` 的是构建过程，两份文本都对**：先按租约口径回收陈旧行 → 再建索引 → 真并发残留时直接报错、不静默丢行（状态机 §八 `：109` 自己写对了）。

**这一处需要人过一眼**，因为三份待拍板文件对同一件事给了两种谓词，改哪一份、留哪一句，属于拍板人的签署范围。建议的落点是：分层设计与 ADR 的说法**保留**（谓词对），状态机 §八 的"无条件"与候选 DDL **改成"非终态集"**，并把"终态后同键 = 再生成"写进口径；§五 规则 5（不能回到 `queued`）的理由句以"一目标一次"为前提，改谓词时一并把理由改成"重开会伪造执行区间"。

### 5.2 候选 DDL 漏了 `cost_currency`

`automation_jobs` 有 `cost_currency text NOT NULL DEFAULT 'CNY'` 加 CHECK（`IN ('CNY','USD')`）；候选 DDL 的 `runs` 只有 `budget_limit` / `budget_spent` / `cost_unknown`，**没有币种列**。

"形状照抄"的纪律下这是漏抄。而且它会咬到硬规则 4：金额字段没有币种，跨币种时"成本显示未知"这条兜底就无从判断——是币种不明，还是金额本身算不出。

**更正**：`runs` 补 `cost_currency text NOT NULL DEFAULT 'CNY'` + CHECK。

### 5.3 候选 DDL 的 `budget_limit` / `budget_spent` 应删改（与问题 3 联动）

问题 3 若按建议取"不放 `budget_limit`"，候选 DDL 里那两列要一起改：

- 删 `budget_limit numeric(12,4)`。
- `budget_spent` 改名为 `spent`，与 `automation_jobs` 逐名一致（`spent numeric(12,4) NOT NULL DEFAULT 0`）。

保留 `budget_limit` 的代价不只是多一列：它是裸的 `numeric(12,4)`（`automation_mandates` 上那列有 `CHECK (budget_limit IS NULL OR budget_limit > 0)`，候选 DDL 没有），**写 0 就会让恢复准入条件恒假**——即 run 一旦中断就必然 `failed`，且原因显示不出来。删列比补 CHECK 更干净：本题的结论本来就是"预算不在这张表上"。
