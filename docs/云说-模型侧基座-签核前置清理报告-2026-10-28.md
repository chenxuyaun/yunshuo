- 门禁**只在存在 high 时阻断**；覆盖不完整本身不阻断（`INCONCLUSIVE` 走失败开放）。
- 引擎**没有守卫/净化器模型**：任何由请求输入派生的值——哪怕经过完整、正确、已覆盖全部私网段的校验函数——仍被判为受污；只有把 sink 实参换成字面量才能清。该发现是「HTTP 请求输入 → 同一源码树内 fetch」这一**功能形状的固有产物**：保留「用户自带端点」的能力就无法清除。
- 发现项自身定性（密封产物 `findings.json`）：`finding:951b51d6f34c26dc7615fa61`、`kind: cross-file`、`severity: high`、**`advisory: true`**、`evidenceState: static-finding`、**`verdictEffect: "none"`**，proofGap 原文「静态 advisory 需要人工确认真实数据流和可利用性」——即工具自己标注该类发现应由人工确认。
- 门禁口径是**文档化行为，不是工具缺陷**：插件 README 明写「提交前分级安全门：高危拒绝、中危确认、低危提示」与 `MIMOSA_GIT_GATE_MODE=graded`（默认）「high=强制拒绝」；CLI 的「跨文件/预测属『告警』，只提示不阻断；退出码=2 只看本文件直检的高危」是**另一套口径**，两者不一致属设计如此。
- 工具**没有「接受/豁免」态**：ledger 只在「完整扫描证明发现缺席」时闭环；`backlog triage` 最多到 `confirmed_candidate`，不会自动 dismissed；`validate` 仅覆盖 readDoc 白名单 Oracle。因此「登记接受该发现」这条路径不存在。

**可清除该发现的形状都不可接受**：只剩 (a) 让 URL 不再来自请求（如 `discover-models` 改 providerId-only、读库里的 `base_url`——`testProvider` 正是这种形状且未被报）；(b) 把 fetch 挪进另一个 workspace 包（`probeEmbedding` 的 sink 在 `packages/model-gateway`，跨包对引擎不可见，故未被报）。前者是产品/UX 变更，后者是靠降低扫描可见性换放行——两者都不能由代理单方面做。
