# 云说-模型侧基座 L2：Run 状态机定义（候选）

> 依据：`docs/云说-模型侧基座分层设计-2026-10-26.md` §二 L2「生命周期要先定义再写码」。
> 状态：**候选定义，未拍板。** 本文只定义生命周期与不变量，不建表、不写迁移。
> 与 D9 的关系：D9（新建 `runs` 还是泛化 `automation_jobs`）决定**落在哪张表**，不改变**生命周期本身**。所以本文在 D9 拍板前后都成立。

## 一、为什么必须先在纸上定完

`automation_jobs` 那套状态集是踩出来的：它先有 `queued/running/completed/failed`，`paused`、`stopped`、`interrupted`、`precheck_failed` 都是后来补的，每次补都牵动 runner 的认领条件、前端轮询口径与一堆用例。状态机一旦写进代码，改变它等于改所有读它的地方。

模型驱动的 Run 比无人值守作业**多一类失败**：循环可能不收敛、成本可能在中途越界、工具可能被伪指令驱动去调不该调的。这些都需要在状态集里有位置，否则只能塞进 `failed` 的 `last_error` 里，等于没有。

## 二、形状从哪里抄

设计文档要求「形状照抄 `automation_jobs`，别自创一套」。逐列对照：

| 沿用 | 理由 |
| --- | --- |
| `status text NOT NULL` + CHECK 列合法集 | 同款；非法值在库层就被拒，不靠应用层记得 |
| `runner_id text` | 谁持有这次运行；恢复时要判断"上一个持有者是不是真死了" |
| `heartbeat_at timestamptz` | 崩溃判定的唯一依据（`automation_jobs` 是同款） |
| `pause_requested` / `stop_requested` 两个布尔 | 协作式停止：请求与生效分离，runner 在步骤边界响应 |
| `last_error text` | 终态原因；不替代审计，只做快速归因 |
| `started_at` / `completed_at` | 终态必须带 `completed_at` |
| `created_by uuid NOT NULL REFERENCES users(id)` | 谁发起 |

| 不抄 | 理由 |
| --- | --- |
| `mandate_id` | 那是无人值守的授权载体；Run 的授权来自调用方的会话，v1 只读不需要额外授权对象 |
| 逐章计数字段（`total_chapters` / `committed_chapters` …） | Run 的进度单位是 **步**（`steps`），不是章 |
| `current_chapter_id` | 同上，Run 的游标是 `current_step_id` |

## 三、Run 状态集

| 状态 | 含义 | 终态 | 谁能进入 |
| --- | --- | --- | --- |
| `queued` | 已创建、幂等键已落库，等 runner 认领 | 否 | 创建时 |
| `precheck_failed` | 认领时前置不满足：无预算、无可用服务商、模型不支持 `tools`、工具未注册 | **是** | 认领时由 runner 写入 |
| `running` | 持有租约，正在推进 | 否 | 认领成功 / 从 `paused` 恢复 / 从 `interrupted` 恢复 |
| `paused` | 人请求暂停且已在步骤边界生效 | 否 | 从 `running` |
| `stopped` | 人请求停止且已生效 | **是** | 从 `queued` / `running` / `paused` |
| `completed` | 正常结束 | **是** | 从 `running` |
| `failed` | 非预期失败（模型错误、步数耗尽、恢复次数耗尽） | **是** | 从 `running` / `interrupted` |
| `interrupted` | 心跳过期或进程退出，**可恢复** | 否 | 从 `running`（由外部判定写入） |

两点说明：

- **`stopped` 与 `failed` 分开**，与 `automation_jobs` 一致。人主动停的不是故障，混进 `failed` 会让"失败率"这个指标永远不可信。
- **`interrupted` 不是终态**。这是 `automation_jobs` 已有的口径（心跳认领），Run 沿用。它只有两条出路：被另一个 runner 恢复成 `running`，或恢复次数耗尽后判 `failed`。

## 四、合法转移

| 从 | 事件 | 到 |
| --- | --- | --- |
| `queued` | runner 认领且前置通过 | `running` |
| `queued` | runner 认领且前置失败 | `precheck_failed` |
| `queued` | 人请求停止 | `stopped` |
| `running` | 步骤循环正常结束 | `completed` |
| `running` | 步数 / 成本 / 墙钟越界，或模型与工具报错且不可重试 | `failed` |
| `running` | 人请求暂停，在步骤边界生效 | `paused` |
| `running` | 人请求停止，在步骤边界生效 | `stopped` |
| `running` | 心跳超时（外部判定） | `interrupted` |
| `paused` | 人请求恢复 | `running` |
| `paused` | 人请求停止 | `stopped` |
| `interrupted` | 另一个 runner 恢复，且恢复次数未耗尽 | `running` |
| `interrupted` | 恢复次数耗尽 | `failed` |

## 五、必须被拒的转移

这一节是"非法转移必须被拒"那条机械化闸的判据来源，每一条都要有对应用例：

1. **终态不可再进入任何状态**：`completed` / `failed` / `stopped` / `precheck_failed` 四个状态没有任何出边。终态被改写就等于"结论被伪造"。
2. **`paused` 不能直接到 `completed`**：必须先 `running`。否则"暂停中的运行完成后写入的结果"没有对应的执行区间。
3. **`interrupted` 不能到 `completed`**：中断的运行不知道自己在哪一步，必须经 `running` 重新确认。
4. **`queued` 不能直接到 `paused`**：还没开始跑，没有可暂停的东西——要停就是 `stopped`。
5. **任何状态都不能回到 `queued`**：回到 `queued` 等于把幂等键所指的那次运行"重开"，与幂等语义冲突。

## 六、Step 状态集与检查点

Step 是 Run 的最小推进单位，形状照 `automation_job_chapters`：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已规划、未开始 |
| `running` | 正在执行 |
| `succeeded` | 完成 |
| `failed` | 本步失败（是否让整个 Run 失败由 Run 层决定） |
| `skipped` | 因前置条件跳过 |
| `interrupted` | 本步执行中进程退出 |

与 `automation_job_chapters` 的差别：那里有 `committed` / `staged` / `gate_failed` / `no_output`，都是"提交链"的领域状态；Step 不承载领域结论，领域结论留在 `ai_proposals` / `canon_versions` 等既有归处。**Step 只回答"这一步跑没跑、跑成什么样"。**

## 七、不变量（每条都要能被机械验证）

| # | 不变量 | 验证方式 |
| --- | --- | --- |
| 1 | 终态必须带 `completed_at`，非终态必须不带 | CHECK 约束 |
| 2 | `running` 必须带 `runner_id` 与 `heartbeat_at` | CHECK 约束 |
| 3 | 同一 Run 同时最多一个 `running` 的 Step | 部分唯一索引 |
| 4 | `steps` 的 `(run_id, index)` 唯一 | 唯一约束 |
| 5 | 每条运行事件必须带 `run_id`（L1a/L2b 验收里那条闸） | 写入路径 + 用例 |
| 6 | 工具 handler 必须收 `AuthContext`（同上） | 类型签名 + 用例 |
| 7 | 非法状态转移必须被拒 | 服务层断言 + 用例 |

第 1、2 条写成 CHECK 而不是应用层断言，理由与 `automation_jobs` 相同：应用层漏一处就是脏行，而脏行不会让任何测试变红。

## 八、幂等键

形状照 `0019_ledger_suggestion_generating_unique.sql`：**先回收陈旧行，再建索引**，索引创建时若有真并发残留就直接报错，不静默丢行。

```sql
-- 先按租约口径把中断的 running 回收为 interrupted（这些行本就该被回收）
UPDATE runs
SET status = 'interrupted',
    last_error = '运行未正常结束（进程退出或心跳过期）'
WHERE status = 'running'
  AND heartbeat_at < now() - interval '5 minutes';

CREATE UNIQUE INDEX runs_workspace_idempotency_idx
  ON runs (workspace_id, idempotency_key);
```

口径：

- 唯一性**无条件**，不按状态过滤。同一幂等键重试必须**返回同一次 Run**（200 + 原 `id`），而不是新建一条。
- 幂等键由调用方给（例如 `suggest:<chapter_id>:<plan_revision>`），服务端不替你编——编出来的键等于把"重复请求"判成"新请求"。
- 与 `commit_intents` 的幂等键语义保持一致：重复键返回既有记录，不重复产生副作用。

## 九、一条必须写在显眼处的边界

**有状态存储 ≠ 可靠恢复，≠ 恰好一次的外部副作用。**

`runs` / `steps` 落库之后，能保证的是"我们知道上次走到哪"。它保证不了：

- 一个已经发出的模型调用真的只发生一次（供应商侧没有幂等键）；
- 一个已经写出去的外部动作能被撤回。

L2 的 v1 全部只读，这条边界不咬人；**一旦有了会写外部状态的工具，这条就必须重新过一遍**——届时要问的不是"状态机写对没"，而是"重放一次这个 run 会多花钱或多写一行吗"。

## 十、候选 DDL（未执行，仅供拍板时评审形状）

```sql
CREATE TABLE runs (
  id uuid PRIMARY KEY,
  workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  idempotency_key text NOT NULL,
  status text NOT NULL,
  runner_id text,
  heartbeat_at timestamptz,
  pause_requested boolean NOT NULL DEFAULT false,
  stop_requested boolean NOT NULL DEFAULT false,
  current_step_id uuid,
  max_steps integer NOT NULL,
  budget_limit numeric(12,4),
  budget_spent numeric(12,4) NOT NULL DEFAULT 0,
  cost_unknown boolean NOT NULL DEFAULT false,
  last_error text,
  created_by uuid NOT NULL REFERENCES users(id),
  started_at timestamptz,
  completed_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT runs_status_check CHECK (
    status IN (
      'queued', 'precheck_failed', 'running', 'paused',
      'stopped', 'completed', 'failed', 'interrupted'
    )
  ),
  CONSTRAINT runs_terminal_completed_at_check CHECK (
    (status IN ('precheck_failed', 'stopped', 'completed', 'failed'))
      = (completed_at IS NOT NULL)
  ),
  CONSTRAINT runs_running_lease_check CHECK (
    status <> 'running' OR (runner_id IS NOT NULL AND heartbeat_at IS NOT NULL)
  )
);

CREATE TABLE steps (
  id uuid PRIMARY KEY,
  run_id uuid NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  index integer NOT NULL CHECK (index >= 0),
  kind text NOT NULL,
  status text NOT NULL DEFAULT 'pending',
  started_at timestamptz,
  completed_at timestamptz,
  last_error text,
  UNIQUE (run_id, index),
  CONSTRAINT steps_status_check CHECK (
    status IN ('pending', 'running', 'succeeded', 'failed', 'skipped', 'interrupted')
  ),
  CONSTRAINT steps_terminal_completed_at_check CHECK (
    (status IN ('succeeded', 'failed', 'skipped', 'interrupted'))
      = (completed_at IS NOT NULL)
  )
);

CREATE UNIQUE INDEX steps_one_running_per_run_idx
  ON steps (run_id) WHERE status = 'running';
```

## 十一、拍板时真正要回答的三个问题

1. **状态集要不要再删减。** 本文给了 8 个状态；如果 L2 的 v1 只跑"一个 run、两个 step"的确定性路径，`paused` 是否必要？（无人值守那边它是必需的。）
2. **`interrupted` 的恢复次数上限。** 本文没有定数，只写了"耗尽即 `failed`"。这个数必须是可推导的，不能拍脑袋。
3. **`budget_limit` 在不在 `runs` 表上。** 放在这里等于 run 自带预算；放在调用方（如 `automation_mandates`）则是外层授权。两者不能同时存在，否则"谁有最终否决权"说不清。
