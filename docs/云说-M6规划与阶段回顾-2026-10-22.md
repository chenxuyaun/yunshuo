# 云说阶段回顾与 M6 规划

- 日期：2026-10-22
- 范围：M1–M5-B、Studio 交付、开源与 CI 之后的阶段性回顾，以及下一阶段（M6）的功能规划。
- 性质：**规划文档，不是已实现说明**。文中所有“未实现/未验收”项在完成前都保持原状，不以计划代替交付。

> **实施进度更新（2026-10-22）**：M6-0 至 M6-5 已完成并通过测试；M6-4 已完成浏览器验收，M6-5 完成回顾审计、低风险修复、文档更新与残留数据清理。设定库、角色档案与伏笔台账已可用于检索、AI 上下文与门禁提示。第一至十四节保留为规划原文，实际状态与已知限制见文末“十五、实施进度”。

## 一、结论摘要

云说已经完成“单章正典生产 + AI 辅助 + 检索 + 多用户 + 计费 + 无人值守 + 单机部署”的主流程闭环，并通过开源仓库对外发布。

但需要区分三件事：

| 维度 | 状态 | 说明 |
| --- | --- | --- |
| 计划内主流程 | **已完成** | M1–M5-B 阶段四与 Studio 收尾均已实现并验收 |
| 开源交付基础 | **已完成** | AGPL-3.0、README、CI、SECURITY、CONTRIBUTING、分支保护 |
| 可对外生产使用 | **未达成** | Studio 是单机试点；无 TLS/WAF、自动备份、HA、RLS；真实 SMTP/IdP/Linux 未验收 |
| 产品纵深 | **关键缺口** | 设定集、角色档案、伏笔台账仍未建库；AI 上下文只有正典片段 |
| 自动化纵深 | **部分完成** | 仅 `continue` 单作业；无 dry-run、扩展写、定时调度、多 runner |
| 协作纵深 | **未开始** | 无实时协作；跨作者协同仍靠租约与审计 |

下一阶段建议做 **M6：设定与连续性账本**，同时在邀请外部作者前完成一组“上线闸门”硬化项。两者不是同一件事，不能互相替代。

### 2.2 当前能力盘点

- **正典与门禁**：单章从租约到提交的链路完整；门禁失败不入库；提交幂等；版本、审计、回滚可追溯。规则集 `dev-v0` 明确标注为非生产。
- **AI 辅助**：AI 只产出提案，不能直接写草稿或正典，不能申请或批准豁免；人工采用后才进入同一条保存/门禁/暂存/提交链。
- **检索**：正典片段支持词法 + 向量混合检索；无嵌入服务或相似度过低时如实降级并给出原因；引用带章节、版本与段落范围。
- **无人值守**：授权、预检、逐章执行、预算上限、暂停/恢复/停止/撤销；单工作区同时只允许一个活跃作业；API 重启会中断章节，需人工恢复。
- **多用户**：密码与 OIDC 两条登录路径；邀请一次性、可撤销；角色边界在 API 与服务层校验；会话绑定工作区。
- **计费**：预算预留与清算、按用途/成员/作业/章节归属、未知费用单列、供应商账单对账；账单金额不回写预算。
- **部署与导入**：单机 Compose；旧章导入保留“未评估”口径；导入章在配置嵌入服务商后可自动排队索引。
- **开源**：公开仓库、许可证、CI、安全策略、贡献指南与分支保护均已就位。

## 三、做得对的地方

1. **先立不变量，再写功能**：AI 不能写正典、AI 不能批准豁免、导入章“未评估”、未知费用不猜、未接入就显示“未接入”。这些约束在多轮迭代中没有被功能进度侵蚀。
2. **正典链路是单一路径**：手工写作、AI 采用、无人值守最终都走同一条保存、门禁、暂存、提交链，没有为自动化另开旁路。
3. **数据库承担一致性**：租约、唯一提交链、幂等键、outbox、预算行锁、审计都在事务内完成，避免把关键一致性交给前端或内存。
4. **每阶段做回顾审计**：M5-A、Studio 等阶段都做了独立的复审、修复与清理，而不是以“测试通过”收尾。
5. **诚实边界写进文档**：`dev-v0`、单机试点、未知费用、未验收外部服务都明确标注，没有用演示数据冒充生产能力。
6. **开源基础扎实**：CI 使用独立测试库与服务容器，分支保护强制检查，安全与贡献指南齐全。

## 四、自省：真实问题与教训

这一节只列已经发生或已经确认的问题，不做泛泛而谈。

| 问题 | 影响 | 处理 | 教训 |
| --- | --- | --- | --- |
| Studio worker 未注入模型密钥 | 界面保存服务商成功，但导入/提交后的索引无法解密 API Key | 已修复：worker 显式注入密钥，生产缺失时退出 1 | “界面显示启用”不等于链路可用；启动守卫要覆盖每个进程 |
| API 未等待 bootstrap 成功 | 全新部署可能留下“能登录但无所有者”的半启动状态 | 已修复：API 依赖 bootstrap 成功 | 部署顺序必须写进编排，而不是运维记忆 |
| 导入章无条件标为“未配置”且不排队 | 已配置嵌入服务商时仍无法检索 | 已修复：导入事务内检查服务商并写 outbox | 功能开关要在真实链路里验证，不能只看单章重建 |
| 前端 `file.text()` 静默替换非法字节 | GBK/GB18030 旧稿可能带着乱码入库 | 已修复：严格 UTF-8 解码，失败即拒绝 | 数据完整性错误不能以“能显示”掩盖 |
| 同卷号不同卷名被静默忽略 | 用户以为新建卷，实际并入旧卷 | 已修复：返回 409，整批不写入 | 冲突必须显式失败，不能替用户做决定 |
| 早期集成测试误连开发库 | 测试数据写入开发库，污染演示状态 | 已清理并加库名守卫 | 破坏性测试必须在连接层硬拒绝非测试库 |
| 把 0.4 相似度下限当成“无答案判断” | 近域负例与正例重叠，6/8 对照仍返回章节 | 已澄清：它只是噪声下限，不是分类器 | 不要用一个阈值包装检索能力 |
| 前端无自动化测试 | 导入编码、文件上限、费用提示等只靠人工验收 | 未解决，列入残留风险 | 151 项测试不等于功能正确；关键 UI 路径需要 E2E |
| 未做容量压测 | 1000 章 / 20MB 的锁持有时间、内存与预览性能未知 | 未解决 | 上限是产品承诺，不是压测结论 |
| 真实外部服务未验收 | SMTP、IdP、Linux、外部 HTTPS 反代、远程嵌入都未实测 | 未解决 | 本地模拟通过不能推导生产可用 |
| 开源仓库含无关调研与内部审计文档 | 外部读者可能误以为都是云说内容 | 未决定是否移除 | 公开仓库的内容边界需要主动管理 |
| “生产环境”口径偏松 | Studio 实际是单机试点，不是高可用生产平台 | 文档已改为试点 | 对外沟通必须区分“可运行”与“可对外生产” |

### 4.1 最需要记住的一条

**文档承诺必须由可执行的守卫或验收脚本兜底。** 本轮发现的多个高影响问题，都不是算法错误，而是“文档说应该这样，代码/编排没有做到”。后续每个阶段收尾时，应优先检查：启动顺序、密钥注入、空状态、失败路径与清理，而不是只增加功能用例。

## 五、为什么下一阶段是设定与连续性账本

当前 AI 上下文的正典来源只有章节片段。系统能检索“过去写过什么”，但不知道：

- 这个世界的规则、地点、组织与禁忌是什么；
- 角色当前知道什么、在哪里、与谁是什么关系、是否已经死亡；
- 哪些伏笔已经埋下、计划何时回收、是否已经逾期。

这带来三个直接后果：

1. **生成质量受限**：AI 只能模仿前文，容易写出与设定冲突的内容，人工复核成本高。
2. **门禁缺少结构化依据**：核心实体与因果律门禁主要依赖章节文本，无法引用稳定的设定/角色/伏笔账本。
3. **导入旧稿后没有整理入口**：用户可以导入章节，却没有地方沉淀世界观、角色与伏笔，产品闭环缺一块。

目标架构早已把“设定与账本”列为一等公民（世界观、阵营、地锁、裁定、伏笔、角色状态、事实验证态）。M6 是把这块从设计变成可用功能，而不是临时加一个设定文本框。

## 六、M6 目标与边界

### 6.1 目标

建立**工作区级、可版本化、可审计、人类拥有最终写入权**的设定与连续性账本，并让它进入检索、AI 上下文与门禁提示。

一句话：让“设定”从散落在章节里的文本，变成可引用、可追溯、可回滚的结构化资产。

### 6.2 非目标

- 不做 AI 自动提取整本旧稿并直接写入账本；AI 只能提出建议，必须人工确认。
- 不做实时协同编辑、评论系统或跨作者草稿共享。
- 不做数据库级 RLS、多副本、多 runner 或零停机升级。
- 不把 `dev-v0` 升级为生产门禁；M6 只增加“提示/引用”，硬门禁需要独立规则集与校准。
- 不做全品类设定模板；先覆盖通用小说创作需要的核心类型。
- 不做自动回收伏笔；只做记录、提醒与报告。

## 七、功能与流程

### A. 设定库（世界观、地点、组织、规则、物品/能力）

**条目字段（功能层面）**

- 类型、名称、别名、一句话摘要、详细说明、标签；
- 状态：草稿 / 生效 / 归档；
- 来源章节与关联章节；
- 版本历史、最后编辑人、最后编辑时间。

**流程**

1. 创建草稿 → 编辑 → 查看差异 → 发布生效。
2. 已发布版本不可原地改写；修改产生新版本，旧版本可查看、可回滚。
3. 归档不删除历史；归档条目不再进入默认检索与 AI 上下文。
4. 同名、别名冲突、空摘要、来源章节不存在等做显式校验。
5. 所有写入记录审计：谁、何时、改了什么、前后差异。

**权限**

- 所有者/主笔/作者可创建与编辑；审阅者可读；计费管理员不可见正文与设定。
- AI 只能提出“建议条目/建议修改”，不能发布、归档或回滚。

### B. 角色档案与状态时间线

**角色卡**

- 身份、外貌、性格、目标、关系、阵营、能力、语言风格；
- 首次登场、最近登场、关联章节；
- 状态时间线：存活/死亡/未知、所在地点、已知信息、持有物、关系变化。

**流程**

1. 角色卡与设定条目一样走草稿 → 发布 → 新版本。
2. 状态变更必须绑定“截至第 N 章”，不能出现没有章节依据的全局状态。
3. 写作台按“截至上一章”展示角色状态，避免剧透后续章节。
4. 发现矛盾时给出显式警告（例如已死亡角色再次登场、地点跳变、关系冲突），默认不阻断；是否硬阻断由规则集版本决定。
5. AI 可以建议状态变更，但必须由人类确认后才进入账本。（已由 M6-7 实现：AI 只生成建议，人工采纳后仅写入未发布草稿，仍需人工发布才进入账本。）

### C. 伏笔台账

**条目**

- 伏笔描述、埋设章节、计划回收窗口（章节范围）、重要度；
- 状态：已埋设 / 已强化 / 已回收 / 已放弃；
- 关联章节、回收说明、逾期标记。

**流程**

1. 从章节计划或写作台手动登记伏笔；AI 可建议，但人类确认后才创建。
2. 写作进入计划回收窗口时，在章节计划与写作台显示提醒。
3. 回收必须写明回收章节与说明；放弃必须写明原因。
4. 提供未回收、已逾期、无埋设来源的回收等报告。
5. 不自动把“逾期”判为失败，也不自动改写章节。

### D. 检索、上下文与门禁集成

- 设定、角色、伏笔作为独立文档类型进入索引；检索结果必须带类型、名称、版本与来源。
- 混合检索只使用生效版本；归档版本、未来章节状态默认不进入上下文。
- AI 上下文包增加“设定/角色/伏笔”分区，逐条显示引用、使用字符数、是否截断。
- 未配置嵌入服务时，仍可词法检索设定条目，并如实显示降级原因。
- 核心实体门禁可引用角色别名与设定名称；因果律门禁可展示相关伏笔与设定提示。首版只做提示，不改变 `dev-v0` 的硬门禁结论。
- 导入章可以人工关联设定/角色/伏笔，但导入本身不生成“已评估”结论。

### E. 界面与空状态

- 新增“设定库”入口，按类型、状态、标签、章节筛选。
- 角色详情展示状态时间线与关联章节；伏笔详情展示埋设/回收链路。
- 所有空状态明确说明“尚未建立”，不显示伪造的示例账本。
- 删除、归档、回滚都给出影响范围与确认。

## 八、规则与不变量

M6 必须延续现有诚实约束：

1. 账本按工作区隔离；跨工作区读写一律拒绝。
2. 人类拥有最终写入权；AI 只能建议，不能发布、归档、回滚或批准。
3. 已发布版本不可变；回滚产生新版本，不删除历史。
4. 审计只追加，不覆盖；每条审计包含 actor、时间、对象、前后差异。
5. 角色状态必须有时点（截至第 N 章），不能存在无来源的全局状态。
6. 伏笔的回收/放弃必须有人类说明，不能由 AI 自动完成。
7. 检索与上下文只使用生效版本；未配置/降级状态如实展示。
8. `dev-v0` 仍是演示规则集；M6 的门禁提示不等于生产门禁通过。
9. 导入章仍为“未评估”；关联账本不改变章节评估状态。
10. 测试、验收产生的临时账本、版本、审计与索引必须清理。

## 九、验收标准

### 功能

- 设定条目：创建、编辑、发布、归档、回滚、搜索、筛选、差异查看。
- 角色：角色卡、状态时间线、截至章节视图、矛盾警告、关联章节。
- 伏笔：登记、强化、回收、放弃、逾期报告、章节计划提醒。
- 集成：检索引用、上下文分区、门禁提示、导入章人工关联。

### 正确性与隔离

- 跨工作区读取/写入返回 403/404，且不泄露对象是否存在。
- 并发编辑同一账本条目返回明确冲突，不静默覆盖。
- 已发布版本不可变；回滚后历史完整；审计前后差异正确。
- 权限矩阵覆盖 owner / lead / author / reviewer / billing / AI 主体。

  - **两处由真实验收暴露的诚实性问题已修**：其一，界面把“有用量但缺价表条目”和“本次没有上报用量”混成同一句“未计价（本次没有上报用量）”，而 `model_calls` 里其实有 592/501；现按两种原因分别显示。其二，`failSuggestion` 原先丢掉已完成调用的用量与费用，导致输出不可用的建议显示“用量未上报”，而这次调用真的花了 token；现在把实际用量、费用与耗时留在建议行上，并在文案里注明“本次已发起调用，用量与费用已按实际记录”。
  - **另修一项计费残留**：`expireStaleReservations`（>15 分钟仍 `streaming` → `failed / CALL_STALE`）原先只在预算已配置时被调用，未设预算或没有预算行的工作区里，进程中断留下的 `streaming` 行会永远显示成在途。现把它移到预算判断之前，报表读取、门禁预检与下一次生成预留都会清算；开发库里那行真实的 `streaming` 中断记录已由新代码清算为 `CALL_STALE`，非手工删改。`m5b-billing.test.ts` 新增“未配置预算时也会清算超时未完成的调用”用例。
  - **真实验收（非 mock）**：用工作区里既有的 Atria 服务商（无价表条目）生成角色状态建议 → `ready`，用量 592/501 tokens、成本如实显示未计价 → 人工采纳写入草稿 v2，此时 `current_version_id` 仍是 v1、`outbox` 无行 → 人工发布后生效版本才成为 v2 并入队 `index.ledger`；草稿状态绑定建议存下的 `basis_chapter_id`，角色档案其余字段在合并后保留。对第 4 章（2383 字）的真实调用返回非 JSON，按 `LEDGER_SUGGESTION_NOT_JSON` 失败并保留 2161/700 的实际用量。验收条目、版本、别名、建议、审计、事件与 outbox 已删除，开发库账本六张表 + `chapter_ledger_links` + `index.ledger` outbox 复核为 0；4 条 `model_calls` 作为真实花费记录保留（`suggestion_id` 随建议删除置空）。
  - **仍不宣称完成**：拒绝分支只在 API 用例覆盖，未在浏览器实跑；较长章节的 JSON 合规只实测到上面那一次失败，没有多章验证；采纳瞬间当前版本被他人改动 → `LEDGER_CURRENT_VERSION_CHANGED` 由行锁与 `expectedCurrentVersionId` 兜底，但没有专门用例；`m6s-v1` 提示质量、建议命中率/错编率与 token 估算系数（每字 2 token）没有评估集或标定；无前端 E2E。验收期间本机 Ollama 嵌入服务不可达，`index.ledger` 任务停在 `pending` 并留下“无法连接嵌入服务”的失败记录，属于环境状态而非通过结论。

### 15.2 已知限制（不得当作已完成）

1. **地点跳变未自动检测**：当前只实现死亡复活、死亡后仍出场、关系冲突三类警告。地点是否属于合理转场需要人工判断，未做规则化检测。
2. **人工确认未留痕**：警告会提示“需人工确认”，但不记录确认人、结论或时间，也不阻断发布；不能据此宣称“人工确认流程已完成”。（M6-7 的账本建议采纳/拒绝是另一回事：那条路径有 `decided_by`/`decided_at`/`decision_note` 与人类 actor 的审计留痕，但这些警告本身仍然不留痕。）
3. **账本检索质量未独立评估**：M6-4 的账本检索复用正典的词法/向量、RRF 与相似度阈值，但尚无独立的账本查询集，验收只覆盖命中、隔离、权限与降级口径；无嵌入时仅词法片段的召回质量同样未评估。门禁提示只作提示，不改变 `dev-v0` 结论。
4. **AI 建议的质量未评估**（流程本身已由 M6-7 落地）：“AI 生成角色状态变更/伏笔回收建议 → 人工确认 → 只写入草稿”已实现，并用真实 Atria 服务商跑通生成、采纳与后续人工发布；但建议命中率与错编率没有评估集，`m6s-v1` 提示与 token 估算系数未标定，拒绝分支未在浏览器实跑，较长章节的 JSON 合规只实测到一次非 JSON 失败，采纳瞬间当前版本被改的 `LEDGER_CURRENT_VERSION_CHANGED` 有数据库兜底却无专门用例。AI 始终没有任何写入权限，也不能发布或批准任何结论。
5. **出场扫描性能未测**：每次时间线请求扫描整部作品当前正典，未做长篇小说或大章节压测。
6. **无前端 E2E 自动化**：本次为浏览器人工验收，Playwright 覆盖仍列在 P1。
7. **逾期与提醒只是提示**：逾期按当前正典最大章号与计划结束章比较，不改变伏笔状态、不判定失败，也不会自动回收；提醒只出现在账本和写作台，未接入自动作业或通知。M6-4 后检索与门禁提示可引用伏笔，但不会自动改变状态、回收或改写门禁结论。草稿的逾期标记会标“草稿”，但草稿不进入提醒、检索与报告。
8. **两侧嵌入模型不同不代表向量可比**：M6-6 后正典与账本各自生成查询向量、各自做向量检索，模型或维度不再互相顶替；但两套向量之间不做跨侧归一或混合排序，统一嵌入模型并重建索引仍是推荐做法。账本侧停用嵌入服务时只降级账本向量通道，`ledgerReason` 如实说明。
9. **预算内整条丢弃的条目没有引用记录**：逐条裁剪已由 `AiLedgerCitationView.truncated` 标记（M6-6），但因分区预算耗尽而完全没进入上下文的条目不产生引用，只能在分区级 `truncated` 上体现——引用列表无法列出“没出现的条目”。单条预算（设定/伏笔 700、角色 900）与分区预算均未做参数验证。

以下三项原列在本节，已由 M6-6 实现并从已知限制移除：正典与账本不同嵌入模型时不自动双查、别名唯一性只在应用层校验、引用级截断未单独标记。第 4 项原本的口径是“B.5 建议流程未实现”，M6-7 已实现流程本身，该项现只保留“质量未评估”的部分。
