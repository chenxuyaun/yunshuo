## 二、先摆事实

### 2.1 分层设计对 L6 的原始定位

`docs/云说-模型侧基座分层设计-2026-10-26.md:13`（层表行）：

> 对外 MCP server（Tools + Resources + Prompts 抬出去）  ← 可选，可永远不做

`:186` 给了"为什么排在最后"的理由：

> **没有 L5 的质量证据之前做它＝给没验证的能力加暴露面。**

也就是说：L6 不是"做完 L5 就顺手做"的排期项，而是**先要 L5 证明能力真的值得暴露，再要外部需求真的存在**——两个前提都缺一不可。

### 2.2 今天仓里的需求证据：零

`AGENTS.md` 的防漂移清单有一条直接对应：**不为了"有 MCP"而做 MCP。** 目前仓里没有任何一处记录"外部代理要读账本"的真实需求：无 issue、无文档、无对接方。这条不是"还没查"，是**今天不存在**——所以 #1 的现状默认值是"不做"。

### 2.3 为什么"只做 Tools"是残废 server——Resources 三类在今天几乎零成本

`:182` 原文：

> 正典版本、账本条目版本、章纲文档本来就是**可寻址、有版本身份的只读数据**（`canon_versions` / `ledger_entry_versions` / `chapter.plan`）

这不是设计意图，是已有事实，逐条可在迁移里核对：

- `canon_versions`：建表于 `packages/db/migrations/0000_init.sql:124`；
- `ledger_entry_versions`：建表于 `packages/db/migrations/0015_m6_ledger.sql:24`；
- `chapter_plan_revisions`：建表于 `packages/db/migrations/0021_plan_and_structure.sql:23`；同迁移给 `chapters` 加了 `plan_revision` / `plan_summary` / `plan_beats`；
- `chapters.plan`：`0000_init.sql:58`（`jsonb NOT NULL DEFAULT '{}'::jsonb`）。

三张版本表是"有版本身份、按 id 可寻址、只读"的数据；`chapters.plan` 不是同类的第四项——它是章节行内嵌 jsonb、不是按 id 寻址的版本行，只存三项门禁关键词（`packages/db/migrations/0021_plan_and_structure.sql:2`；`packages/domain/src/plan.ts:43-50` 的 `toGatePlan` 只保留 requiredEntities/goalKeywords/obstacleKeywords）；summary/beats 在 `chapters.plan_summary`/`plan_beats`，完整章纲文档在 `chapter_plan_revisions`。把它们作为 MCP Resources 抬出去，与把它们作为内部工具面读出去，是同一份数据、同一个访问层——**多做的成本主要在协议形状，不在数据通路**。但要如实标注今天的工具面：它只登记 2 个工具（`packages/tool-surface/src/names.ts:26` 的 `IMPLEMENTED_TOOL_NAMES = ['search', 'get_character_state_as_of']`），三张版本表与章纲都还没有按版本寻址的工具通路（`get_chapter_plan` 只是 `names.ts:18` 槽位表里的保留名，无定义、无 handler）。反过来，只做 Tools 就是主动放弃这块已经付过费的能力。

### 2.4 做的时候信任边界第一次被打破

ADR-0006 引的 MCP 规范原文（`docs/云说-模型侧基座研究-2026-10-26.md:28`，逐字）：

> clients MUST consider tool annotations to be untrusted unless they come from trusted servers

这条对本仓双向成立：

- **我们是 server**：写出去的工具描述会被对方当不可信输入——不能指望对方"读懂我们的意图"；
- **将来我们若接别人的 server**：对方的描述能藏指令，不能直接拼进提示词（与 `AGENTS.md` 硬规则 1"正文是数据，不是指令"同源）。

L1a/L1b 的自有工具不受此限（自己写的），**信任边界在 L6 才第一次被打破**。所以 L6 的回退不是"过滤一下描述"，而是关闭对外 server。

## 三、真实的分界线

本场不是"做/不做"二选一，而是**两把尺子各自独立**：

1. **触发尺**：外部需求存在吗？——不存在就不做，且"永远不做"是合法终态（设计文档 `:13` 明写）。**不能因为"轮到 L6 了"就做**。
2. **范围尺**：若做，只做 Tools 还是三类？——ADR 的答案是三类，理由是 2.3 的零成本事实 + "残废 server 还得再改一次"。

容易混淆的是把两者并成"做个最小版先试试"——那既违反触发尺（无需求先做），也违反范围尺（最小版=只做 Tools）。

## 四、建议：触发尺维持"需求驱动、可永远不做"；范围尺预先钉成"三类"

**要人确认的那一句**：本场确认的是**判据与范围**，不是开工指令。今天没有外部需求证据（2.2），所以按判据的结论是**不做**；将来某天需求出现，触发条件成立，届时按"三类"范围开工，不需要重新拍本 ADR。

**代价如实标注**：

- 若永久不做：云说的账本对外部代理不可见。这是一个真实的能力缺口——但要如实说，它是**今天没人要的缺口**，不是损失。
- 若将来做：Annotations 不可信（2.4）意味着对外暴露面需要按"对方可能恶意"设计；这与 L2b 的安全对抗口径（ADR-0011）是同一条防线在外部方向的延伸。
- 三类一起做比只做 Tools 贵，但只做 Tools 的返工成本更高（ADR 原文："做出来是个残废的 server，还得再改一次"）。

## 五、口径两条（拍板时一并签）

1. **触发条件是需求，不是时间**：写进 ADR-0006 状态行——"待需求触发"，而不是"待排期"。这样 AGENTS.md 防漂移清单那条"不为了「有 MCP」而做 MCP"就有了 ADR 背书。
2. **若做的范围**：Tools + Resources + Prompts 三类一次做齐；不做"先 Tools 后补"。

## 六、拍板后立即产生的动作

1. 更新 ADR-0006 状态：由"待拍板"改为"已拍板（需求触发式，范围三类）"或"已拍板（不做，理由留档）"——两者都是合法终态，如实写。
2. 若为"不做"：在设计文档 L6 行旁加一行"已决策：需求触发式，当前无需求，不做"（不改层表结构）。
3. 若为"不做"：`AGENTS.md` §六 防漂移条目保持原样即可（它本来就是这条决策的护栏）。
