未发现高危或中危缺陷。确认并修复 **5 项低风险问题**，均不改变 `dev-v0` 硬门禁结论、权限边界或既有 API 语义：

## 二、修复明细

### 2.1 归档提示不再指向不存在的“恢复”

账本归档是终态：README 与界面都明确“当前不提供取消归档”，但服务层三处错误仍写“请先恢复”。用户无法执行这个建议，按恢复操作只会再次失败。

修复位置：

- [ledger-service.ts:830](../apps/api/src/services/ledger-service.ts#L830)（编辑）
- [ledger-service.ts:951](../apps/api/src/services/ledger-service.ts#L951)（发布）
- [ledger-service.ts:1121](../apps/api/src/services/ledger-service.ts#L1121)（回滚）

统一改为“已归档条目不能编辑/发布/回滚；归档不可撤销，请新建条目重新登记”。错误码仍为 409 `LEDGER_ENTRY_ARCHIVED`，既有客户端分支不受影响。

### 2.2 工作区级设定的来源章节可正确标注

worker 原先只加载 `work_id` 等于条目所属作品的章节。工作区级设定（`work_id = NULL`）即使已绑定来源章节，也拿不到章节映射，索引文本会写成“来源章节：未登记章节”。这不会泄露数据，但会让检索命中与 AI 上下文中的来源描述失真。

修复：

- [pipeline.ts:704](../apps/worker/src/pipeline.ts#L704) 新增 `ledgerReferencedChapterIds`，从快照收集来源章节、角色状态章节、伏笔埋设/回收章节 ID。
- [pipeline.ts:1108](../apps/worker/src/pipeline.ts#L1108) 按这些 ID 查询当前工作区内的章节，不再依赖条目自身 `work_id`。

回归：[ledger-pipeline.test.ts:317](../apps/worker/src/ledger-pipeline.test.ts#L317) 创建工作区级设定并绑定第 7 章，断言切块内容包含“来源章节：第 7 章《北门夜雨》”，且不再出现“未登记章节”。

### 2.3 已结束伏笔不再进入“回收窗口”提示

门禁提示的窗口分支原先只看章号区间，不看伏笔状态。已回收或已放弃的伏笔，只要计划窗口覆盖当前章，仍会以“处于计划回收窗口”出现。提示不改变门禁结论，但语义错误。

修复：[ledger-context-service.ts:514](../apps/api/src/services/ledger-context-service.ts#L514) 仅在 `state` 不是 `paid_off`/`abandoned` 时进入窗口提示；“正文提及”“本章埋设”“本章回收”等直接关联分支保持不变。

回归：[m6-integration.test.ts:914](../apps/api/src/m6-integration.test.ts#L914) 创建窗口覆盖当前章、状态为 `paid_off` 的临时伏笔；[m6-integration.test.ts:967](../apps/api/src/m6-integration.test.ts#L967) 断言它不出现在因果提示条目中，同时原有“黑潮预兆”窗口提示仍存在，硬门禁结果仍逐字段等于直接求值。

### 2.4 并发名称唯一冲突映射为 409

创建条目已捕获 PostgreSQL `23505` 并返回 409，但发布与“无当前版本的草稿回滚”还会更新 `ledger_entries.name/aliases`。两个并发请求都通过应用层名称检查时，后提交者会撞上唯一索引并把 500 暴露给客户端。

修复：

- [ledger-service.ts:1009](../apps/api/src/services/ledger-service.ts#L1009) 发布更新捕获唯一冲突。
- [ledger-service.ts:1164](../apps/api/src/services/ledger-service.ts#L1164) 草稿回滚更新捕获唯一冲突。

两处均返回 409 `LEDGER_NAME_CONFLICT`，事务回滚，不会留下半发布状态。该并发窗口未做自动化并发复现，属于代码审查级修复；别名当时仍未由数据库约束保证，见第四节第一项与第五节 5.2。

### 2.5 无索引原因不再默认归咎于嵌入配置

[search-service.ts:873](../apps/api/src/services/search-service.ts#L873) 原先写“配置嵌入服务并重建索引后可在检索中命中”。当索引只是排队中或失败时，这句话会把原因指错方向。现改为“请查看账本索引状态，必要时配置嵌入服务并重建索引”，不声称具体失败原因。

## 五、残留加固（M6-6，2026-10-22 同日追加）

范围：只处理第四节中可落地的三项，不引入新表语义变更以外的功能。

### 5.1 正典与账本各自解析向量目标

原实现用“正典优先、账本兜底”的单一目标，一次查询只生成一个向量；两侧模型或维度不同时，账本向量通道为空且不说明原因。

- [search-service.ts:680](../apps/api/src/services/search-service.ts#L680) `vectorTargetOf()` 分别从 `coverage` 与 `ledgerCoverage` 解析目标；模型与维度完全一致时共用一次嵌入调用，不同则并行生成两个查询向量，各自服务自己的向量通道。
- 语义原因 `semanticReason` 仍只描述正典通道，保持 M4 既有断言与界面口径不变；账本通道新增独立原因：查询嵌入失败时输出“账本向量通道未执行：…”，账本向量命中全部低于阈值时输出“账本向量最高相似度低于阈值 …，本次账本仅用词法检索”。
- 每次实际使用的模型都写入独立的 `purpose='embedding_query'` 调用与成本记录，不再用一个模型的调用冒充两侧。
- 测试：[m6-integration.test.ts:645](../apps/api/src/m6-integration.test.ts#L645) 用两个不同模型的嵌入桩断言两侧各有向量排名、`embedCalls` 恰好包含两个模型、并按价表分别记账；停用账本侧服务商后断言正典向量命中保留、账本 `vectorRank` 全为 `null` 且 `ledgerReason` 指出模型不一致。

保留边界：两侧模型不同只是“都能向量检索”，不代表两套向量可比；跨侧排序仍不做混合归一。统一模型并重建索引仍是推荐做法。

### 5.2 别名唯一性由数据库兜底

`ledger_entries.aliases` 是 `text[]`，名称唯一索引不覆盖数组元素，并发写入可产生同范围重复别名。

- 新增迁移 [0017_ledger_alias_unique.sql](../packages/db/migrations/0017_ledger_alias_unique.sql)：`ledger_entry_aliases` 存规范化投影（`lower(trim(alias))`、按 `workspace_id / kind / COALESCE(work_id, 零UUID) / alias_key` 建唯一索引），`ledger_entries_sync_aliases` 触发器在增删改时重建投影，归档条目不落投影即释放别名，同条目内重复别名先聚合去重；空别名忽略；迁移末尾回填既有条目。
- 回填使用 `INSERT ... GROUP BY`，**历史重复别名会让迁移显式失败而不是静默丢弃**；本地 `yunshuo` 与 `yunshuo_test` 回填前探测均为 0 条重复，迁移直接通过。
- [ledger-service.ts:912](../apps/api/src/services/ledger-service.ts#L912) 草稿更新同样捕获 `23505`，与创建/发布/回滚一致返回 409 `LEDGER_NAME_CONFLICT`，不再出现 500。
- 测试：[m6-ledger.test.ts:638](../apps/api/src/m6-ledger.test.ts#L638) 并发写入同一别名，断言状态码恰为 200 + 409、失败方 `LEDGER_NAME_CONFLICT`、`ledger_entry_aliases` 只留一条且属于成功方、失败方别名为空，并在清理后按 `alias_key` 断言投影为 0。
- 已验证行为：冲突拒绝、归档释放、大小写与首尾空格归一、空别名忽略、同条目内去重（直接在 `yunshuo_test` 用 SQL 复现）。

保留边界：`ledger_entries.aliases` 仍是权威存储列，投影表只用于约束；触发器不改写用户输入，展示仍以原数组为准。

### 5.3 引用级截断标记

分区级 `truncated` 只能说明“这一区被裁过”，无法指出是哪一条引用被截断。

- 契约 [index.ts:805](../packages/contracts/src/index.ts#L805) `AiLedgerCitationView` 新增 `truncated: boolean`，与既有 `chars`（含截断省略号的实际长度）并列。
- [ledger-context-service.ts:360](../apps/api/src/services/ledger-context-service.ts#L360) 逐条裁剪结果写入 `truncated`；分区级 `usedChars/truncated` 行为不变。
- 界面 [AiProposalPanel.tsx:431](../apps/web/src/components/AiProposalPanel.tsx#L431) 在被截断的引用后追加“· 本条截断”。
- 测试：[m6-integration.test.ts:876](../apps/api/src/m6-integration.test.ts#L876) 发布 900 字详细说明的设定，断言该条引用 `truncated === true` 且 `chars === 701`（700 字预算 + 省略号），同区未超预算的条目 `truncated === false`，分区仍标记截断。

保留边界：**因分区预算耗尽而被整条丢弃的条目不会产生引用**，只在分区级 `truncated` 上体现——引用列表无法列出“没出现的条目”。单条预算仍为设定/伏笔 700 字、角色 900 字，未做调参验证。

### 7.1 环境与口径

独立 API 实例监听 3101，数据库指向 `yunshuo_test`，`AUTOMATION_RUNNER=0`，索引 worker 未启动；该库没有任何启用的服务商（`enabled=0 embedding_enabled=0`），所以整轮**零模型调用、零成本**，`index_status` 全部停在 `not_configured`。正文由 8 句固定 filler 拼接，角色名/别名按构造每 11/17/23 章出现一次——**合成、可重复，但也因此不真实**。单请求段每个端点取 3 次请求的中位数；并发段另算：并发 1/4/8、每级 3 轮，**每轮等全部请求返回才开下一轮（批量并发，不是恒定到达率）**，全部请求复用同一个登录会话、由同一台机器上的同一个 Node 进程发起。报告只留派生计数（出场章数、警告数、条目数、响应字节），不留接口原文。脚本还单独测量 `docker exec psql` 的进程启动开销（156–192ms），避免把客户端启动读成数据库查询耗时。同一配置重复运行的抖动约 ±10–15%（两次分批导入 805/1382/2031ms 与 802/1153/2239ms，时间线 16/21/35ms 与 23/17/30ms），所以十几毫秒级别的差异不构成结论。

### 7.2 数据

- 分批增长（每章约 2000 字）：以 200/300/500 章增量导入，累计正典 12.0/30.0/60.0 万字（请求体 0.34/0.52/0.86MB）单事务 805/1382/2031ms；正典时间线中位 16/21/35ms（出场 200/500/1000 章，警告 0）；再加一章 500,000 字（契约单章上限）后，该章导入 112ms、时间线 45ms。
- 载荷上限（单批 1000 章 × 6500 字 = 送出 6,499,914 字，请求体 18.15MB，路由 `bodyLimit` 20MiB）：单事务 4939ms，同一配置此前两次独立运行分别 4413ms 与 4735ms，三次都没有超时、没有 500；该规模（650 万字）下时间线中位 126ms（样本 126/109/133，出场 1000 章）。
- 不扫描正典的端点几乎不随规模变化：角色上下文 12–16ms、伏笔提醒 15–32ms、伏笔报告 15–17ms、章节列表 15–23ms（响应 59→293KB、202→1002 条）。作为对照，同一时窗 `psql` 直取整部正文、扣掉进程启动后的净耗时为 28/43/73ms（0.3→1.7MB），650 万字那一轮是 167ms / 17.6MB——时间线的那几十毫秒里含“把整部正典搬进 Node”，不只是应用侧 `indexOf`。
- 并发读（最大语料那份：1000 章 + 一个 50 万字长章，正典 7,000,021 字）：扫描整部正典的时间线在并发 1/4/8 下中位 113/347/628ms、p95 128/408/800ms，而吞吐 8.85/10.06/9.79 req/s——**并发买到的是排队，不是产出**；同机同一会话读不扫描正文的角色上下文，同期 83.33/255.32/320 req/s、中位 11–19ms、p95 ≤30ms。每次运行 78 个并发请求（时间线 39 + 角色上下文 39），两次运行全部 200，零失败、零超时。较小语料（110 万字）那一轮形状相同但未饱和（时间线 43/87/131ms），且每级样本只有 3/12/24 个，抖动足以翻转读数。
- 契约边界可同时成立但不能同时到满：1000 章与 500,000 字/章各自实测通过，而 20MiB 请求体决定了 1000 章最多约 6,500–7,000 字/章（按 500,000 字/章一次只装得下约 3 章）。`wordCount` 不计空白，500,000 字符正文记为 460,014 字。
- 内存：同一 API 进程 WorkingSet 在 12.0 万字时 105.9MB、60.0 万字时 140.6MB、650 万字时 213.1MB（加满长章并清理数据后 231.1MB），但分批增长那一轮清理后反而降到 133.4MB。**WorkingSet 不是单调量，操作系统会裁剪，这组数字既不能证明泄漏、也不能证明没有泄漏**；能确定的是“每请求把整部正典取进 Node 再 `indexOf`”会让常驻内存随正典体积同量级增长；同一份 700 万字语料在并发轮从 228.8MB 涨到 340.5MB，与“每个在途请求各自持有一份正文”这一实现形状一致（但同样不可严格归因）。V8 不把堆交还操作系统本身也是正常现象。

### 7.3 清理与脚本自身缺陷（如实记录）

脚本按 work/entry 的集合子查询删除临时作品、条目及其事件、审计、outbox 与本会话，并断言各表计数逐项等于压测前基线；四次运行（两组规模 + 两组并发）的 `cleanupDrift` 均为 `{}`，`yunshuo_test` 回到 works=1 / chapters=2 / 账本六表 0 / 事件 3 / 审计 119 / outbox 0 / 会话 0。过程中暴露并修掉三个脚本自身问题，都属于“验收脚本自己会撒谎”一类：

1. 清理语句把 1001 个章节 id 直接拼进 SQL，`docker exec` 在 Windows 抛 `spawnSync docker ENAMETOOLONG`，且**失败发生在数据已导入之后**——按 id 列表拼上千条的写法在本仓库不可用，必须改成与规模无关的子查询。
2. 第一版把 `登录` 写进时间窗起点之后，导致 `auth.login` 审计（`object_id` 为空）与本次会话不在删除范围内，`audit`/`outbox` 计数漂到 120/2；改为先取数据库自己的 `now()` 作为窗口起点，并补上 `index.ledger` outbox（按 `payload->>'entryId'`）的删除。
3. “请求体 MB”最初取的是 `fetch` 响应的字节数，把 0.00MB 的响应报成请求体；改为序列化后自行计数，并补 `sentChars`。

### 7.4 本轮不能宣称的事

并发只做到“同一台机器、同一个 Node 进程、同一个登录会话、每级 3 轮的批量并发读”：**没有多用户与多工作区、没有读写混合（边导入边扫描）、没有恒定到达率与 p99、没有真实小说正文、没有 Studio 容器内测量**；那几轮里 `yunshuo_test` 没有启用的嵌入服务商、worker 未启动，所以 `index_status` 全部 `not_configured`、整轮零模型调用——索引与检索的千章基线由同日另一次实测补上，见 7.5，账本侧的千章索引由同日第三次实测补上，见 7.6。“时间线中位 126ms”“并发 8 吞吐 9.79 req/s”都是这套合成语料、单实例下的读数，不构成性能达标或容量承诺。并发段能支撑的只到方向层面：单实例上“每请求扫描整部正典”这条路加并发不会换来产出（8.85/10.06/9.79 req/s 而延迟 113→628ms），而不读正文的端点随并发正常上升——这把“要不要做增量投影”从猜测变成一个能算的问题，但值不值得做仍要用真实正文与真实并发形态验证。规划文档 15.2 第 5 项已按此口径改写。

### 7.5 补测：千章正典索引排空与检索（同日，真实 worker + 本机嵌入）

缺口关闭的最后一块。`scripts/m6-perf-index.mjs` 与上面两轮用同一份合成 filler、同一个隔离库，差别是这一轮必须有真实 worker 和真实嵌入服务：脚本先探活嵌入服务，**不可达就直接退出，不会降级成“未配置”来把“环境没准备好”读成“索引基线”**。报告落 `docs/m6-perf-index.json`。

- 导入与排空：单事务导入 1000 章 × 600 字（请求体 1,811,900 字节 ≈ 1.73MB，`wordCount` 合计 550,000）用时 4253ms；入队即刻 `index_status` 与 `outbox` 都是 `pending=1000`；worker 排空用时 **2070s（34 分 30 秒）＝ 29.0 章/分钟**，1000 章全部 `ready`，零 `failed`、零 `not_configured`。产出 2000 切块（每章恒 2，min=max=2）与 2000 向量，`vector_chunks=2000 of canon_chunks=2000`，1024 维。
- 模型调用：索引期 1000 次全部成功（`prompt_tokens` 578,143，中位 **2021ms**）；每次调用最多带 16 个切块（`apps/worker/src/pipeline.ts:484`），每章 2 块，所以章数与调用数 1:1。查询向量 12 次全部成功（12 个 `auto` 请求各一次，中位 190ms，`prompt_tokens` 141），服务商合计 1012 次。本机模型输入价填 0，`cost=0.0000 CNY` 只对本机成立。
- 检索：`/api/search?workId=…&limit=8`，4 条查询 × `lexical`/`auto` × 各 3 次取中位。词法 209–413ms、混合 251–465ms；有命中每次 8 条、响应约 4.5KB，零命中约 0.44KB。混合侧带出的向量相似度 0.642 / 0.646（首位由词法通道命中时该项为空，两套分不做跨侧归一）；域外对照“量子色动力学的渐近自由”向量最高 **0.318 < 阈值 0.400**，如实降级为 `mode=lexical` 并写明原因、返回 0 条——降级路径在千章规模成立。
- 内存：worker WorkingSet 首个采样 78.1MB、整轮 88–90MB、末次 89.5MB，没随排队累积；API 从 149.5MB 降到 96.8MB。同 7.2 的口径，WorkingSet 非单调量，两边都既不能证明泄漏也不能证明没有。
- 清理与脚本自纠：清完后 `cleanupDrift = {}`，`chapter_metadata` 手工复验回到 1；这一项当时不在脚本的计数表里（漏掉就看不见漏删），已补进 `COUNTS`，下一轮起由断言覆盖。本轮之前还有三次“脚本自己会撒谎”的修法值得留档：`index_status JOIN chapters` 时裸写 `status` 触发 `column reference "status" is ambiguous`；嵌入成功状态实际写的是 `'ok'` 而不是 `'completed'`，**按 `'completed'` 统计会让一份成功索引 1000 章的报告自称“0 次成功调用”**，第一版报告就带着这个错数落过盘（`docs/m6-perf-smoke.json` 原样保留作为证据，修好后另跑 6 章为 `docs/m6-perf-smoke2.json`，其 `cleanupDrift` 才为 `{}`）；清理少删了一条服务商对象的 `audit_log`，漂移读成 `{"audit":"119 -> 120"}`；脚本的排空超时默认值原本 30 分钟，小于实测 34.5 分钟，**会把一次慢但成功的排空记成“未排空”**，已把默认调到 90 分钟（正式运行当时是显式传 `PERF_INDEX_TIMEOUT_MS=5400000` 跑的）。
- 本轮不能宣称的：29.0 章/分钟的倒数是 2.07s/章，与单次嵌入中位 2021ms 基本相等——**这条吞吐读的是本机嵌入调用的串行节奏，不是索引管线的容量上限，也不能外推到付费服务商**；合成 filler 让切块恒为 2 且命中不具语义难度（词法首位恒为第 1 章），所以检索数值只证明“跑通 + 延迟量级”，**不构成检索质量或排序有效性的证据**；本轮库里没有账本条目，**千章规模的账本索引（`ledger_chunks` / `ledger_index_status`）当时是空白**，同日由 7.6 补上；Studio 容器内、真实正文、读写混合、持续到达率与 p99 同样未测。**还有两条是本节写完当时没意识到的**：①“单 worker 串行”这个归因不成立——本报告自带采样里 `outbox` 同时 `processing` 最多 1000 条，而单个实例一次 `claimOutbox` 只领 10 条并逐条 await（`apps/worker/src/pipeline.ts:1284`、`:1301`），说明当时约 100 个 worker 在领同一张 outbox，成因见 7.6 的环境缺陷一节；② 这一条当时写在正文里而不是由脚本自证，脚本没有采实例形状。`docs/m6-perf-index.json` 的 `caveats` 已按实测改写，并新增 `topology` 与 `reanalysis`（记录改动、保留原始 `samples` 与全部读数）。这些数字仍是单一本机环境的规模基线，不是生产 SLA。

### 7.6 补测：千章账本索引排空与账本通道检索，以及一个把两轮基线都污染的实例缺陷

7.5 留下的最后一块空白是账本侧：那轮千章库里 `ledger_entries` 为 0，`ledger_chunks` / `ledger_index_status` 从来没有在千章规模下被排空过。本轮用 `scripts/m6-perf-ledger-index.mjs` 在同一台机器、同一个 `yunshuo_test`、同一份 filler 上把这句话换成实测，报告 `docs/m6-perf-ledger.json`（runId `b3e15407`）。

- **构造**：先导入 1000 章 × 600 字（单事务 4854ms，请求体 1,861,912 字节 ≈ 1.78MB，`wordCount` 600,000），再发布 1000 条账本条目（设定 500 / 角色 300 / 伏笔 200；作用域 850 `work` / 150 `workspace`），创建中位 26ms、发布中位 24ms，**零失败**。条目规模按“千章作品的上限”构造，不是真实作品的账本形状。
- **两段排空**：正典投影 2117.6s ＝ **28.33 章/分钟**（三等分 28.4 / 28.4 / 28.2，与 7.5 的 29.0 相差 −2.3%，在既有 ±10–15% 抖动内，同机对照成立）；账本投影 2359.9s，窗口内真正需要索引的 978 条 ＝ **24.87 条/分钟**（三等分 28.3 / 19.3 / 27.1，中段下探没有解释，采样是 20s 一次的瞬时值）。**按 1000 条整除会得到 25.4，偏高的读法已改掉**：入队即刻就有 22 条 `ready`，把它们算进分子是拿别人的工作量冒充本轮。
- **投影与调用**：`ledger_chunks` 1914（avg 1.91 / max 4 / min 1；character 2.71、setting 1.80、foreshadowing 1.00），向量 1914/1914 全出、1024 维，`ledger_index_status` 全 `ready`；`attempts_max=1`、无待重试、无错误类型。索引期嵌入调用恰好 2000 次全部成功（正典 1000 + 账本 1000，`prompt_tokens` 1,273,040，中位 2094ms）——调用数与两侧条目数相加吻合，**没有重复嵌入**；查询向量 15 次，服务商合计 2015 次。
- **检索**：词法中位 236–503ms、混合 295–531ms；账本首位命中 `压测设定 0007` / `压测角色 0003`（词法）与 `压测角色 0021`（混合，走别名），混合首位账本向量分 0.6548 / 0.6580 / 0.7063。域外对照两侧 0 命中并如实降级，**账本通道的原因是单独写的**：`ledgerReason` 记“账本向量最高相似度低于阈值 0.400，本次账本仅用词法检索”。这条只证明降级路径与文案在千条规模成立，不证明账本检索质量。
- **清理**：`cleanupDrift = {}`，六张账本表回到 0，测试库逐项回到压测前基线；发布把 `workspaces.settings_version` / `ledger_version` 推到 501 / 523，这两列不在脚本的计数表里、删数据也不会带回，脚本显式还原为 1 / 23 并在报告里留痕——**这是本轮新增的一类残留：不在计数口径内的派生计数器**。

**审计层面真正有价值的发现是下面这条，它同时削弱了 7.5。** 账本阶段采样里同时 `processing` 的任务最多 10 条，而正典阶段最多 **989** 条、7.5 那份正典报告里最高 **1000** 条。`claimOutbox` 一次只领 10 条（`apps/worker/src/pipeline.ts:1284`，`runOutboxTick` 在 `:1301` 用默认参数调用并逐条 await），全仓没有其他把状态写成 `processing` 的路径（只有 `:1277` 的超时回收与 `:1287` 的领取，`outbox` 上也没有触发器）。为把这件事钉死，临时在 `yunshuo_test` 插 1000 条 `index.chapter` 任务后直接调用真实的 `claimOutbox()`：一次恰好把 10 行翻成 `processing`，用完即删。**所以单个 worker 的瞬时 `processing` 上限就是 10，989/1000 只能解释为约 100 个实例在领同一张 outbox。** 现场核查确认成因是进程卫生问题：`TaskStop` 只终止 pnpm 外层包装，不终止它派生的 tsx/node 子进程，于是多次会话里"已停止"的后台 worker 实际一直在跑，其中 4 个还指向开发库（开发库因此累积了 6 小时内的 12 条 `processed` outbox、4 条 `ready` 索引状态与 115 条模型调用记录——非本轮压测产生，也未污染 `yunshuo_test` 的读数）。按 PID 精确清理这些孤儿进程后复验：3101 端口释放、开发 API 不受影响、`yunshuo_test` 的 `outbox=0` 与外部连接 0。同日 4 章 + 8 条的探针运行（`docs/m6-perf-ledger-smoke4.json`）给出了单实例应有的形状：压测前领用连接 1，采样里 `processing` 正典 4 / 账本 5，都在 10 以内。

**由此确立的口径调整**：7.5 与 7.6 的排空速率都是"这台机器上的端到端聚合值、受本机嵌入服务串行处理约束"，**一律不得当作单 worker 吞吐引用**（账本阶段与单实例一致，但那一轮没采压测前实例形状，只能说一致、不能说已证明）。脚本已加三道防护，让下一轮自己带上证据：每采样记录 `pg_stat_activity` 的实例形状、每阶段结束记录 outbox 的 `status/attempts/lockAge` 形状、压测前若发现 >1 个连接最近在领任务就拒绝启动（`PERF_ALLOW_MULTI_WORKER=1` 可显式放行，报告照实记录）。

## 十、章节关联的隔离与归因补测（2026-10-23 追加）

§九 纠正了"零覆盖"这句口径错误，同时留下四个没被任何用例打到的分支：跨工作区、幽灵章节、已归档条目、以及删除时章节 URL 与链接归属不一致。本轮补一条用例把它们一次打穿（`apps/api/src/m6-integration.test.ts`，该文件 9 → 10 个用例）。**这条没有修任何代码，四个分支的实现行为都正确**——它的价值是把"读代码觉得对"换成"跑过并钉住"。

- **隔离一律 404，不是 403**：外部所有者读写本章端点、本区所有者读写幽灵章节，四条都返回 404 `CHAPTER_NOT_FOUND`；本区关联他区条目返回 404 `LEDGER_ENTRY_NOT_FOUND`。三种情况都不区分"存在但对你不可见"与"确实不存在"，所以拿别人的章节 id 或条目 id 探不到存在性。
- **已归档是 409 而不是 404**：同工作区的 `archivedSettingA` 返回 409 `LEDGER_ENTRY_NOT_ACTIVE`——它本来就对本区可见，拒绝理由必须是状态而不是找不到。草稿条目由 §九 提到的既有用例覆盖，本轮补的是归档这一支。
- **失败的尝试既不留行也不留审计**：`loadChapterScope` 与条目查找都在 `writeAudit` 之前返回，所以两次失败的尝试之后 `chapter_ledger_links` 的行数一字不变，`audit_log` 里按 `metadata->>'entryId'` 取这两条的记录数为 0。

## 十四、筛子自己撒了谎：连接测试端点整条零断言（2026-10-23 追加）

## 十八、提交链的四道复核：`targetChapterId` 其实没人读、跨章暂存行被拦两次，以及一条被自己清理吃掉的证据（2026-10-23 追加）

§十七 之后错误码筛子里剩下的、单请求真能打到的干净一族是**提交链自己的四道复核**。`POST /api/chapters/:id/commit` 早就被用例一、二、六调用过（成功路径与 `CONCURRENT_COMMIT`），但那四个拒绝分支——目标章节一致性、暂存行归属、暂存行是否最新、门禁证据的上下文——一个断言都没有。新增 `apps/api/src/m2-workflow.test.ts` 第 8 个用例「提交链的四道复核：目标章节要一致、暂存要属本章且是最新一份、门禁证据的上下文不能变」（`:1499`），一次钉住 **4 个**此前零断言的码（`CONTEXT_CHANGED` 在提交处与暂存处**两个抛出点各钉一次**），**产品代码零改动、零付费调用**。

- **拒绝的账和回滚正好相反，而且这个方向差异是产品语义**：`TARGET_MISMATCH` 排在意图行插入**之前**（`commit-service.ts:74-75`），是提交这一族唯一"连意图行都不留"的拒绝；回滚那边意图行写在所有守卫之前（§十七），所以每次拒绝都留一条。其余三道在事务里，先落意图行、失败由兜底 `catch` 写成 `status='failed', error_code=<码>`，本节账上 **+5 行 `commit_intents` = 3 条失败 + 2 条 committed**。`refused(result, status, code, 'intent' | 'none')`（`:1563`）照 §十七 同一套纪律：钉状态码与码、把整表 `trace()`（版本 / 提交 / `canon_current` / 意图 / 草稿 / 证据 / 暂存 / 租约 / 事件 / 审计 / 状态 / 指针）与上一次快照逐项相等、再按 `'intent'`/`'none'` 断言行数 +1 或不变——**一次拒绝除了自己那条意图什么都不留**。
- **两次成功之外的账全部实测钉住**（不是推的）：正典版本 +2（第 7、8 版）、`commits` +2、`canon_current` 仍每章一行、草稿 +7、门禁证据 +6、暂存 +5、事件与审计各 +14、租约回到 0。末尾那张 `'event:' || event_type` UNION `'audit:' || action` 的分解把 +14 归到 3 次开始修订、5 次暂存、3 次取消暂存、2 次提交、1 次放弃修订，再对一次 `GROUP BY error_code, status` 的意图码账本（`committed:-` 2 条，`CONTEXT_CHANGED`/`STAGED_DRAFT_NOT_FOUND`/`STAGED_DRAFT_STALE` 各 1 条）——事后能分清每一次被拒的原因。
- **`CONTEXT_CHANGED` 是真实用户能走到的一句**，不是靠 `UPDATE` 造出来的：门禁上下文哈希吃的是工作区的 `settings_version`/`ledger_version`（`chapter-data.ts:70-78`），而全项目只有**发布与归档账本条目**会推进它们（`ledger-service.ts:1024-1034`、`:1086-1097`，`kind='setting'` 推 `settings_version`，其余推 `ledger_version`）。用例就在暂存之后**发布一条 `kind='setting'` 的设定条目**，提交立刻被拒「设定或规则版本已变化，请重新跑门禁」；重跑门禁 + 重新暂存就能提交第 8 版。两个抛出点各钉一次：提交处 `commit-service.ts:181`、暂存处 `chapter-service.ts:646`，同一句文案——错误码筛子只数"码有没有被断过"，命中不等于每个抛出点都测过。
- **恢复路径比"重跑门禁"多一步（第一处假设被实测改掉）**：被拒的那次提交**不会替我取消暂存**，而 `stageDraft` 只收 `writing`/`revision`/`commit_failed`（`chapter-service.ts:615-625`）——`staged` 状态下直接重跑门禁再暂存，拿到的是 409 `CHAPTER_NOT_STAGEABLE`，不是新暂存行。真正的恢复是三步：**取消暂存 → 重跑门禁 → 再暂存**。用例里的 `regateAndStage()`（`:1619`）显式做这三步，末尾那 3 次取消暂存就是它留下的账。
- **`targetChapterId` 除了这句一致性检查之外服务端根本不读**：C1 摘掉守卫后，带 `targetChapterId=<另一章>` 的请求返回 **200**——它按**路径里**的章节把正文提交成了正典，请求体那个字段形同装饰。这不是测试问题，是口径问题：客户端以为自己往哪一章提交，服务端只看 URL。
- **跨章的暂存行被拦两次，归属闸不是唯一的门**（C2 的红字把这件事说得很直白）：把 `AND s.chapter_id = ${chapterId}`（`commit-service.ts:153`）摘掉之后，探针（兄弟章节那条**真实**暂存行）并没有提交成功，而是被下一道"是不是本章最新一份"拦成 `STAGED_DRAFT_STALE`——"最新"是按本章算的，别的章节的行 id 永远不可能等于它。**所以这一枪开的不是权限洞，是错误码的可读性与纵深**，和 §十六 C13（取消暂存的旧草稿真能被提交）、§十七 R7（别章豁免真能被本章花掉）那种"少一个 WHERE 就做成"不是一级严重度。探针形状仍照 §十七 ③ 的教训：`commit_intents.staged_draft_id` 是指向 `staged_drafts` 的 RESTRICT 外键（`0000_init.sql:162`），随手编的 uuid 会先崩在意图行插入上、走不到那句 409，所以只能真建一章兄弟章节、走一遍修订→租约→草稿→门禁→暂存。
- **夹具自己也得能被清理（§十七 的教训这次是做进代码里，不只是写进报告）**：共享的 `cleanupChapter()` 原来缺 `staged_drafts`/`gate_evaluations`/`draft_revisions`/`draft_branches` 四张表，也没有 `commit_intents` 的跨章兜底（`target_version_id`、`expected_current_version_id`、`staged_draft_id` 三条 RESTRICT）。第一次跑到中途挂掉之后，**连续三轮都死在同一句 `DELETE FROM canon_versions` 的外键上**，红字和被测守卫毫无关系；同名设定条目又被唯一约束拦成 `LEDGER_NAME_CONFLICT`。补齐之后：跨章意图按目标版本/暂存行清（`:126-149` 里两处 `chapter_id <> ${id}`）、草稿与证据表进清单（`:158-164`）、用例开头按章节标题和条目名称/别名各扫一遍残留（`:1701-1714`）。五枪控制跑完再单独重跑该文件，`test-db-residue.mjs` 回到纯种子形状——**被弄脏的测试库现在能自愈，不需要手工修库**。
- **一处顺序错会把证据读没，红字看起来像产品少写了一行**（如实记）：`cleanupChapter` 的跨章意图兜底顺手删掉了步骤②那条"属于本章、指向兄弟章节暂存行"的意图行。第一版把总账断言放在清理**之后**，测出 `commit_intents` +4 / `failed` +2，与逐次 `refused()` 的 +5/+3 自相矛盾。原因不是产品行为，是**断言读在拆除之后**。改成正先算账、后清理（`:1951` 起），行数与码账本立刻对上。
- **五处反向验证**（逐条禁用守卫，每次 `git checkout --` 还原，最后 `git status --short` 只剩测试文件；每一枪都只有本用例红）：C1 摘 `TARGET_MISMATCH` → 「expected 200 to be 400」（**别的章节被静默忽略，正典照样写**）；C2 暂存查找去掉本章归属 → 「expected 'STAGED_DRAFT_STALE' to be 'STAGED_DRAFT_NOT_FOUND'」；C3 去掉"是不是最新一份"比较 → 「expected 200 to be 409」（被更新的暂存覆盖的旧草稿真能提交）；C4 提交处 `CONTEXT_CHANGED` → 「expected 200 to be 409」（设定已发布、证据过期，正典还是写进去了）；C5 暂存处同一句 → 「expected 200 to be 409」（过期证据能暂存，下一步就走到提交）。**C3+C4 合起来说明提交链真正拦住"过期"的两道就是这两句**，摘掉任何一道都能把不该进正典的正文写成版本。

## 十九、账本域规则的四道拒绝：串作品的来源章节被拦两次、第二次发布先响"没草稿"、回滚的槽位比对排在版本查询之前（2026-10-23 追加）

§十八 之后错误码筛子里剩下 47 个码，账本一族占 5 个，是同一族里唯一还能用单请求真实打到的干净一批。新增 `apps/api/src/m6-foreshadowing.test.ts` 第 7 个用例「账本域规则的拒绝：来源章节串作品、回收早于埋设、无草稿、版本不存在」（`:810`），钉住 **4 个**此前零断言的码，并把第 5 个（`LEDGER_WORK_REQUIRED`）**如实证明它从 HTTP 打不到**——不是漏测。产品代码零改动、零付费调用。

- **一条守卫、两个调用点、三种深度**：`assertSourceChapter`（`ledger-service.ts:298-316`）在 create（`:743`）与草稿保存（`:885`）各跑一次。create 处它排在 `parseAndValidatePayload` 之前，所以"来源章节串作品 + 埋设章节也串作品"这个双违规请求，摘掉守卫后拿到的是 **404 `LEDGER_CHAPTER_NOT_FOUND`（payload 那条）而不是 200**——C1（删掉 create 处的调用）与 C2（把 `:313` 的判定短路）两枪红字完全相同，都是「expected 404 to be 400」：**这一枪开的是错误码归属与深度，不是洞**。草稿处相反：正文不变、只改 `sourceChapterId`，别的东西都拦不住它，C5（删掉 `:885` 的调用）直接 **200**、红字「expected 200 to be 400」——**同一条规则的两个调用点，一个被覆盖、一个是唯一的门**。顺带钉出一条不对称：来源章节在工作区里查不到用的是 `CHAPTER_NOT_FOUND`（`:312`），payload 里的章节越界用的是 `LEDGER_CHAPTER_NOT_FOUND`（`:348`/`:368`），同一个"章节不属于本作品"有两套话术。
- **`LEDGER_PAYOFF_BEFORE_SEED` 两处各打一次，且都配了正控制**：create（`state='paid_off'` + 回收第 1 章 + 埋设第 3 章）与草稿保存各拿一次 400；同一章节对，回收晚于埋设（第 4 章 > 第 2 章）就 200 并真发布成第 2 版。**"过期"从来不是"一律不许"**，正控制是这条断言成立的前提。来源章节同理：同作品 200、跨作品 400、跨工作区 404。
- **域规则排在状态机前面**（顺序断言，不是推的）：`saveLedgerDraft` 里 `parseAndValidatePayload` 在 `:866`、`assertForeshadowingTransition` 在 `:881`。构造一个**同时**违反两条的请求（已 `paid_off` 的条目改回 `planted`，同时窗口 1..2 早于埋设第 3 章），实测拿到 **400 `LEDGER_PAYOFF_WINDOW_BEFORE_SEED`**，不是 409 `LEDGER_FORESHADOWING_TRANSITION`——先算内容对不对，再算状态让不让走。
- **第二次发布先响"没有待发布的草稿"**：发布把 `draft_version_id` 清空（`:1008`），而 `:964` 的空槽位检查排在 `:967` 的槽位比对之前。探针用的是**真实存在过的**第 2 版版本 id（不是编的 uuid），照样 409 `LEDGER_NO_DRAFT`；C3 把 `:964` 短路后同一个请求换成 409 `LEDGER_DRAFT_CONFLICT`，红字「expected 'LEDGER_DRAFT_CONFLICT' to be 'LEDGER_NO_DRAFT'」。这条对应的是界面上"发布完了再点一次发布"的形状。副作用账也钉了：拒绝前后 `ledger_version`/`settings_version` 逐项相等、条目仍是第 2 版且 `draftVersion` 为 null——**一次被拒的发布连草稿槽都不该碰**。

## 二十一、邀请与改密族：一句 400 与一句 414 之间隔着一层路由，行锁把 CAS 的窗口拉成确定性（2026-10-23 追加）

- **"令牌形状不对"由两层分别回答，而且上层那一句我原先写错了**：短于 20 由 `checkedToken`（`routes/identity.ts:26`）回答，400 + 应用形状 `{error:{code:'INVITE_INVALID',message:'邀请链接无效'}}`；**长于 200 那一支从 HTTP 面根本打不到**——Fastify 的 `maxParamLength` 默认 100，路由在进处理器之前就用 **414** 回话，响应体是框架自己的扁平形状 `{error:'Bad Request', code:'FST_ERR_MAX_PARAM_LENGTH', message:"'/api/invites/xxx…' is exceeding the max param length"}`。第一版用例把它当成"会被全局错误处理器归一化成 BAD_REQUEST/请求格式不正确"来断言，实测红在 `expected 414 to be 400`；`setErrorHandler`（`server.ts:34`）只接得到处理器之后的错，接不到路由阶段的拒。两条结论如实写下：① `token.length > 200` 是纵深防御而不是可测分支，除非抬高 `maxParamLength`（那是产品决定）；② 这条 414 的消息**把整条请求路径原样回显**，且前端按 `error.code` 读会拿到 `undefined`——本轮只测量、没改产品代码，要不要归一化交产品定夺。用例现在断的是真实形状（`:710` 的 400 与 `:715-724` 的 414 各一段），并注明"同一个 `INVITE_INVALID` 因此落在两个状态码上：太短 = 这条链接不成其为令牌，够长但查不到 = 令牌不存在（`identity-service.ts:301` 预览 / `:337` 接受）"。
- **守卫顺序是实测出来的，不是读代码读出来的**：接受邀请的路由把 `acceptInviteSchema.parse` 写在 `checkedToken` 之前（`:48` 对 `:49`），所以"坏令牌 + 坏请求体"拿到的是契约的 `VALIDATION` 而不是形状那句 `INVITE_INVALID`；S5 把两句调换顺序，红字直接是「expected 'INVITE_INVALID' to be 'VALIDATION'」。同理，`INVITE_PROFILE_REQUIRED`（`identity-service.ts:377`）那句"请填写称呼和至少 10 位密码"里的**长度**部分不由它管：6 位的相同密码在契约就被拦走。S9 把 `||` 改成 `&&`（只给一项也放行）之后，"只给称呼"这一枪变成 **500**——**这句守卫顺带兜住了 `undefined` 进 `hashPassword`**，它不是一个纯粹的礼貌提示。三种缺项（全缺 / 缺密码 / 缺称呼）落进同一句话，副作用账钉死：邀请 +1、用户 +0。
- **一句 `INVITE_NOT_FOUND` 回答四种撤销失败，但四种失败各自被不同的谓词守着**：谓词是 `UPDATE … WHERE id AND workspace_id AND accepted_at IS NULL AND revoked_at IS NULL`（`:258-264`），四种都只能得到"匹配 0 行"，因此界面上分不出"贴错 id"与"手慢了一步"（`:267`）。第一轮把四种形状写成循环 + 各自 `expectError`，结果 S6/S7/S8 三枪红在**同一行**、说不出去掉的是哪条谓词；改成**按形状名建键再一起比**（`:809-816`）之后，三枪分别点名 `"别的区"` `"已接受"` `"已撤销"` 变成 `200 （成功，没有错误体）`，而"不存在"那一格在三枪下都仍是 404——它由 id 本身守，不由这三条谓词守。顺带钉：四次拒绝一条 `member.invite.revoke` 审计都不留（审计写在 UPDATE 成功之后），作者没有撤销权时 **403 与 404 是两种话**。
- **改密的三道前置有先后，而且先后是要紧的**：没设密码 → `PASSWORD_NOT_SET`（`:74-79`）；验当前密码 → `CURRENT_PASSWORD_INVALID`（`:91`，同时记一次登录失败与**一条 `auth_events` 失败事件**）；最后才比新旧是否相同 → `PASSWORD_UNCHANGED`（`:94`）。当前密码错的时候**即使两个值完全相同也先响"当前密码不正确"**：不先把旧密码验一遍，服务端无从知道"相同"是笔误还是攻击。用例把这条顺序钉住（`:501` 与 `:508` 两种输入各一次），并钉"6 位相同密码连验密码那一步都没走到，所以失败事件数不变"（`:513-521`）。
- **CAS 的窗口是确定性拉出来的**：测试事务先 `SELECT … FOR UPDATE` 锁住用户行（`:568`）→ 发改密请求 → 轮 `pg_stat_activity` 直到出现 `wait_event_type='Lock' AND wait_event='transactionid'` 的那条密码 UPDATE（`:543-553`）——这一行本身就是"旧哈希已读、正等着写"的凭据 → 锁内把密码改成 `NEW_PASSWORD` 并提交 → 请求醒来后 `WHERE … AND password_hash = <旧哈希>`（`:104`）匹配 0 行 → 409 `PASSWORD_CHANGED_CONCURRENTLY`（`:108`）。输的一方一行都不许留下：会话没被撤销（`:112` 的 `DELETE` 随事务回滚）、`password.change` 成功事件为 0、另一个会话仍能 200；赢家作数（旧密码 401、新密码 200）；正控制再改一次 → 200 + 成功事件 1。**第一版栽在凭据上**：我用 `query LIKE 'UPDATE users SET password_hash%'` 前缀匹配，5 秒轮询空转、红在 `expect(...).toBe(true)`。dump 出来才看清 postgres.js 原样发送模板文本——`\n      UPDATE users\n      SET password_hash = $1, password_updated_at = now()\n …`，带换行和 `$n` 占位符，前缀永远不命中。**"轮询等不到"和"守卫没生效"是两种红**：前者必须先把被测对象的真实形状打印出来再定谓词，不能靠放宽超时或塞 sleep 蒙过去。
