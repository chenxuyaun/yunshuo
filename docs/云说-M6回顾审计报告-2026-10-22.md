# 云说 M6 回顾审计报告

方法：逐文件审阅 + 定向数据库核对 + 全量测试与类型检查复跑 + 开发库/测试库残留检查。M6-5 未重新做一轮浏览器验收，M6-4 的浏览器验收证据仍然有效；本次重点是审计、低风险修复、文档与清理。

## 一、结论

未发现高危或中危缺陷。确认并修复 **5 项低风险问题**，均不改变 `dev-v0` 硬门禁结论、权限边界或既有 API 语义：

| 级别 | 问题 | 状态 |
| --- | --- | --- |
| 低 | 归档条目的编辑/发布/回滚错误提示“请先恢复”，但系统没有取消归档功能 | 已修复文案 + 回归覆盖既有错误码 |
| 低 | 工作区级设定的来源章节在索引文本中显示为“未登记章节” | 已修复 + worker 回归测试 |
| 低 | 已回收/已放弃的伏笔仍可能因“处于计划回收窗口”进入门禁提示 | 已修复 + 断言 |
| 低 | 发布或草稿回滚时若并发撞上名称唯一索引，可能返回 500 | 已映射为 409 `LEDGER_NAME_CONFLICT` |
| 低 | 账本尚无索引时，`ledgerReason` 默认暗示“未配置嵌入”，未覆盖仍在排队或失败的情况 | 已改为提示查看索引状态 |

验证结果：`pnpm typecheck` 9/9 workspace 通过；全量测试 **181 项 / 25 个文件**通过（domain 4 + model-gateway 5 + retrieval 20 + gates 8 + API 129 + worker 15）。开发库与测试库的账本、版本、索引块、嵌入、索引状态、章节关联与 `index.ledger` outbox 计数均为 0；测试库临时用户与测试工作区为 0；开发库两个服务商（Atria chat、本机 Ollama embedding）保持启用。

## 二、修复明细

### 2.1 归档提示不再指向不存在的“恢复”

账本归档是终态：README 与界面都明确“当前不提供取消归档”，但服务层三处错误仍写“请先恢复”。用户无法执行这个建议，按恢复操作只会再次失败。

修复位置：

- [ledger-service.ts:830](../apps/api/src/services/ledger-service.ts#L830)（编辑）
- [ledger-service.ts:944](../apps/api/src/services/ledger-service.ts#L944)（发布）
- [ledger-service.ts:1114](../apps/api/src/services/ledger-service.ts#L1114)（回滚）

统一改为“已归档条目不能编辑/发布/回滚；归档不可撤销，请新建条目重新登记”。错误码仍为 409 `LEDGER_ENTRY_ARCHIVED`，既有客户端分支不受影响。

### 2.2 工作区级设定的来源章节可正确标注

worker 原先只加载 `work_id` 等于条目所属作品的章节。工作区级设定（`work_id = NULL`）即使已绑定来源章节，也拿不到章节映射，索引文本会写成“来源章节：未登记章节”。这不会泄露数据，但会让检索命中与 AI 上下文中的来源描述失真。

修复：

- [pipeline.ts:704](../apps/worker/src/pipeline.ts#L704) 新增 `ledgerReferencedChapterIds`，从快照收集来源章节、角色状态章节、伏笔埋设/回收章节 ID。
- [pipeline.ts:1108](../apps/worker/src/pipeline.ts#L1108) 按这些 ID 查询当前工作区内的章节，不再依赖条目自身 `work_id`。

回归：[ledger-pipeline.test.ts:314](../apps/worker/src/ledger-pipeline.test.ts#L314) 创建工作区级设定并绑定第 7 章，断言切块内容包含“来源章节：第 7 章《北门夜雨》”，且不再出现“未登记章节”。

### 2.3 已结束伏笔不再进入“回收窗口”提示

门禁提示的窗口分支原先只看章号区间，不看伏笔状态。已回收或已放弃的伏笔，只要计划窗口覆盖当前章，仍会以“处于计划回收窗口”出现。提示不改变门禁结论，但语义错误。

修复：[ledger-context-service.ts:514](../apps/api/src/services/ledger-context-service.ts#L514) 仅在 `state` 不是 `paid_off`/`abandoned` 时进入窗口提示；“正文提及”“本章埋设”“本章回收”等直接关联分支保持不变。

回归：[m6-integration.test.ts:779](../apps/api/src/m6-integration.test.ts#L779) 创建窗口覆盖当前章、状态为 `paid_off` 的临时伏笔；[m6-integration.test.ts:828](../apps/api/src/m6-integration.test.ts#L828) 断言它不出现在因果提示条目中，同时原有“黑潮预兆”窗口提示仍存在，硬门禁结果仍逐字段等于直接求值。

### 2.4 并发名称唯一冲突映射为 409

创建条目已捕获 PostgreSQL `23505` 并返回 409，但发布与“无当前版本的草稿回滚”还会更新 `ledger_entries.name/aliases`。两个并发请求都通过应用层名称检查时，后提交者会撞上唯一索引并把 500 暴露给客户端。

修复：

- [ledger-service.ts:1002](../apps/api/src/services/ledger-service.ts#L1002) 发布更新捕获唯一冲突。
- [ledger-service.ts:1157](../apps/api/src/services/ledger-service.ts#L1157) 草稿回滚更新捕获唯一冲突。

两处均返回 409 `LEDGER_NAME_CONFLICT`，事务回滚，不会留下半发布状态。该并发窗口未做自动化并发复现，属于代码审查级修复；别名唯一性仍未由数据库约束保证，见第四节。

### 2.5 无索引原因不再默认归咎于嵌入配置

[search-service.ts:844](../apps/api/src/services/search-service.ts#L844) 原先写“配置嵌入服务并重建索引后可在检索中命中”。当索引只是排队中或失败时，这句话会把原因指错方向。现改为“请查看账本索引状态，必要时配置嵌入服务并重建索引”，不声称具体失败原因。

## 四、未修复风险与诚实边界

1. **正典与账本使用不同嵌入模型时不自动双查**：一次检索只生成一个查询向量，向量目标优先取正典模型。若两侧模型/维度不同，账本词法仍可用，但账本向量通道会静默为空；`ledgerCoverage` 会分别展示两侧模型，`ledgerReason` 不额外判断模型差异。需要同时向量检索时应统一嵌入模型并重建索引，而不是指望单次查询覆盖两套向量。
2. **别名唯一性只在应用层校验**：数据库唯一索引只覆盖名称；并发写入仍可能产生重复别名。名称冲突已由数据库兜底并映射 409，别名没有同等保证。
3. **引用级截断未单独标记**：AI 上下文按分区显示 `usedChars/chars` 与 `truncated`，每条引用记录字符数，但不会逐条标记“本条被截断”。预算行为可见，粒度不到单条引用。
4. **没有账本检索质量评估集**：账本复用正典的词法/向量、RRF 与相似度阈值；现有验收只覆盖命中、隔离、权限与降级口径，不能据此宣称召回质量。
5. **归档不可恢复**：这是当前产品选择，不是缺陷；历史版本与审计仍保留，但界面不提供取消归档，操作前需确认。
6. **无前端 E2E 自动化**：M6-4 浏览器验收为人工执行；M6-5 未重复浏览器验收，不能把“测试通过”当成所有 UI 路径已验证。
7. **`dev-v0` 仍是非生产规则集**：门禁提示与账本上下文都不改变硬门禁结论，也不把演示规则提升为生产标准。

## 五、交付结论

M6-0 至 M6-5 已完成。账本可以创建、发布、归档、回滚、检索、注入 AI 上下文并生成非阻断提示；无嵌入服务时如实降级为词法索引；导入章节可人工关联但不产生评估结论。以上能力按“开发/演示可用”交付，不包含生产级检索质量证明、E2E 自动化或公网部署硬化。
