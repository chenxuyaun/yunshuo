未发现高危或中危缺陷。确认并修复 **5 项低风险问题**，均不改变 `dev-v0` 硬门禁结论、权限边界或既有 API 语义：

| 低 | 归档条目的编辑/发布/回滚错误提示“请先恢复”，但系统没有取消归档功能 | 已修复文案 + 回归覆盖既有错误码 |

## 二、修复明细

### 2.1 归档提示不再指向不存在的“恢复”

账本归档是终态：README 与界面都明确“当前不提供取消归档”，但服务层三处错误仍写“请先恢复”。用户无法执行这个建议，按恢复操作只会再次失败。

修复位置：

- [ledger-service.ts:830](../apps/api/src/services/ledger-service.ts#L830)（编辑）
- [ledger-service.ts:951](../apps/api/src/services/ledger-service.ts#L951)（发布）
- [ledger-service.ts:1121](../apps/api/src/services/ledger-service.ts#L1121)（回滚）

统一改为“已归档条目不能编辑/发布/回滚；归档不可撤销，请新建条目重新登记”。错误码仍为 409 `LEDGER_ENTRY_ARCHIVED`，既有客户端分支不受影响。

### 2.2 工作区级设定的来源章节可正确标注

worker 原先只加载 `work_id` 等于条目所属作品的章节。工作区级设定（`work_id = NULL`）即使已绑定来源章节，也拿不到章节映射，索引文本会写成“来源章节：未登记章节”。这不会泄露数据，但会让检索命中与 AI 上下文中的来源描述失真。

修复：

- [pipeline.ts:704](../apps/worker/src/pipeline.ts#L704) 新增 `ledgerReferencedChapterIds`，从快照收集来源章节、角色状态章节、伏笔埋设/回收章节 ID。
- [pipeline.ts:1108](../apps/worker/src/pipeline.ts#L1108) 按这些 ID 查询当前工作区内的章节，不再依赖条目自身 `work_id`。

回归：[ledger-pipeline.test.ts:317](../apps/worker/src/ledger-pipeline.test.ts#L317) 创建工作区级设定并绑定第 7 章，断言切块内容包含“来源章节：第 7 章《北门夜雨》”，且不再出现“未登记章节”。

### 2.3 已结束伏笔不再进入“回收窗口”提示

门禁提示的窗口分支原先只看章号区间，不看伏笔状态。已回收或已放弃的伏笔，只要计划窗口覆盖当前章，仍会以“处于计划回收窗口”出现。提示不改变门禁结论，但语义错误。

修复：[ledger-context-service.ts:514](../apps/api/src/services/ledger-context-service.ts#L514) 仅在 `state` 不是 `paid_off`/`abandoned` 时进入窗口提示；“正文提及”“本章埋设”“本章回收”等直接关联分支保持不变。

回归：[m6-integration.test.ts:914](../apps/api/src/m6-integration.test.ts#L914) 创建窗口覆盖当前章、状态为 `paid_off` 的临时伏笔；[m6-integration.test.ts:967](../apps/api/src/m6-integration.test.ts#L967) 断言它不出现在因果提示条目中，同时原有“黑潮预兆”窗口提示仍存在，硬门禁结果仍逐字段等于直接求值。

### 2.4 并发名称唯一冲突映射为 409

创建条目已捕获 PostgreSQL `23505` 并返回 409，但发布与“无当前版本的草稿回滚”还会更新 `ledger_entries.name/aliases`。两个并发请求都通过应用层名称检查时，后提交者会撞上唯一索引并把 500 暴露给客户端。

修复：

- [ledger-service.ts:1009](../apps/api/src/services/ledger-service.ts#L1009) 发布更新捕获唯一冲突。
- [ledger-service.ts:1164](../apps/api/src/services/ledger-service.ts#L1164) 草稿回滚更新捕获唯一冲突。

两处均返回 409 `LEDGER_NAME_CONFLICT`，事务回滚，不会留下半发布状态。该并发窗口未做自动化并发复现，属于代码审查级修复；别名当时仍未由数据库约束保证，见第四节第一项与第五节 5.2。

### 2.5 无索引原因不再默认归咎于嵌入配置

[search-service.ts:873](../apps/api/src/services/search-service.ts#L873) 原先写“配置嵌入服务并重建索引后可在检索中命中”。当索引只是排队中或失败时，这句话会把原因指错方向。现改为“请查看账本索引状态，必要时配置嵌入服务并重建索引”，不声称具体失败原因。

## 五、残留加固（M6-6，2026-10-22 同日追加）

范围：只处理第四节中可落地的三项，不引入新表语义变更以外的功能。

### 5.1 正典与账本各自解析向量目标

原实现用“正典优先、账本兜底”的单一目标，一次查询只生成一个向量；两侧模型或维度不同时，账本向量通道为空且不说明原因。

- [search-service.ts:680](../apps/api/src/services/search-service.ts#L680) `vectorTargetOf()` 分别从 `coverage` 与 `ledgerCoverage` 解析目标；模型与维度完全一致时共用一次嵌入调用，不同则并行生成两个查询向量，各自服务自己的向量通道。
- 语义原因 `semanticReason` 仍只描述正典通道，保持 M4 既有断言与界面口径不变；账本通道新增独立原因：查询嵌入失败时输出“账本向量通道未执行：…”，账本向量命中全部低于阈值时输出“账本向量最高相似度低于阈值 …，本次账本仅用词法检索”。
- 每次实际使用的模型都写入独立的 `purpose='embedding_query'` 调用与成本记录，不再用一个模型的调用冒充两侧。
- 测试：[m6-integration.test.ts:645](../apps/api/src/m6-integration.test.ts#L645) 用两个不同模型的嵌入桩断言两侧各有向量排名、`embedCalls` 恰好包含两个模型、并按价表分别记账；停用账本侧服务商后断言正典向量命中保留、账本 `vectorRank` 全为 `null` 且 `ledgerReason` 指出模型不一致。

保留边界：两侧模型不同只是“都能向量检索”，不代表两套向量可比；跨侧排序仍不做混合归一。统一模型并重建索引仍是推荐做法。

### 5.2 别名唯一性由数据库兜底

`ledger_entries.aliases` 是 `text[]`，名称唯一索引不覆盖数组元素，并发写入可产生同范围重复别名。

- 新增迁移 [0017_ledger_alias_unique.sql](../packages/db/migrations/0017_ledger_alias_unique.sql)：`ledger_entry_aliases` 存规范化投影（`lower(trim(alias))`、按 `workspace_id / kind / COALESCE(work_id, 零UUID) / alias_key` 建唯一索引），`ledger_entries_sync_aliases` 触发器在增删改时重建投影，归档条目不落投影即释放别名，同条目内重复别名先聚合去重；空别名忽略；迁移末尾回填既有条目。
- 回填使用 `INSERT ... GROUP BY`，**历史重复别名会让迁移显式失败而不是静默丢弃**；本地 `yunshuo` 与 `yunshuo_test` 回填前探测均为 0 条重复，迁移直接通过。
- [ledger-service.ts:912](../apps/api/src/services/ledger-service.ts#L912) 草稿更新同样捕获 `23505`，与创建/发布/回滚一致返回 409 `LEDGER_NAME_CONFLICT`，不再出现 500。
- 测试：[m6-ledger.test.ts:638](../apps/api/src/m6-ledger.test.ts#L638) 并发写入同一别名，断言状态码恰为 200 + 409、失败方 `LEDGER_NAME_CONFLICT`、`ledger_entry_aliases` 只留一条且属于成功方、失败方别名为空，并在清理后按 `alias_key` 断言投影为 0。
- 已验证行为：冲突拒绝、归档释放、大小写与首尾空格归一、空别名忽略、同条目内去重（直接在 `yunshuo_test` 用 SQL 复现）。

保留边界：`ledger_entries.aliases` 仍是权威存储列，投影表只用于约束；触发器不改写用户输入，展示仍以原数组为准。

### 5.3 引用级截断标记

分区级 `truncated` 只能说明“这一区被裁过”，无法指出是哪一条引用被截断。

- 契约 [index.ts:805](../packages/contracts/src/index.ts#L805) `AiLedgerCitationView` 新增 `truncated: boolean`，与既有 `chars`（含截断省略号的实际长度）并列。
- [ledger-context-service.ts:360](../apps/api/src/services/ledger-context-service.ts#L360) 逐条裁剪结果写入 `truncated`；分区级 `usedChars/truncated` 行为不变。
- 界面 [AiProposalPanel.tsx:431](../apps/web/src/components/AiProposalPanel.tsx#L431) 在被截断的引用后追加“· 本条截断”。
- 测试：[m6-integration.test.ts:876](../apps/api/src/m6-integration.test.ts#L876) 发布 900 字详细说明的设定，断言该条引用 `truncated === true` 且 `chars === 701`（700 字预算 + 省略号），同区未超预算的条目 `truncated === false`，分区仍标记截断。

保留边界：**因分区预算耗尽而被整条丢弃的条目不会产生引用**，只在分区级 `truncated` 上体现——引用列表无法列出“没出现的条目”。单条预算仍为设定/伏笔 700 字、角色 900 字，未做调参验证。

### 7.1 环境与口径

独立 API 实例监听 3101，数据库指向 `yunshuo_test`，`AUTOMATION_RUNNER=0`，索引 worker 未启动；该库没有任何启用的服务商（`enabled=0 embedding_enabled=0`），所以整轮**零模型调用、零成本**，`index_status` 全部停在 `not_configured`。正文由 8 句固定 filler 拼接，角色名/别名按构造每 11/17/23 章出现一次——**合成、可重复，但也因此不真实**。单请求段每个端点取 3 次请求的中位数；并发段另算：并发 1/4/8、每级 3 轮，**每轮等全部请求返回才开下一轮（批量并发，不是恒定到达率）**，全部请求复用同一个登录会话、由同一台机器上的同一个 Node 进程发起。报告只留派生计数（出场章数、警告数、条目数、响应字节），不留接口原文。脚本还单独测量 `docker exec psql` 的进程启动开销（156–192ms），避免把客户端启动读成数据库查询耗时。同一配置重复运行的抖动约 ±10–15%（两次分批导入 805/1382/2031ms 与 802/1153/2239ms，时间线 16/21/35ms 与 23/17/30ms），所以十几毫秒级别的差异不构成结论。

### 7.2 数据

- 分批增长（每章约 2000 字）：以 200/300/500 章增量导入，累计正典 12.0/30.0/60.0 万字（请求体 0.34/0.52/0.86MB）单事务 805/1382/2031ms；正典时间线中位 16/21/35ms（出场 200/500/1000 章，警告 0）；再加一章 500,000 字（契约单章上限）后，该章导入 112ms、时间线 45ms。
- 载荷上限（单批 1000 章 × 6500 字 = 送出 6,499,914 字，请求体 18.15MB，路由 `bodyLimit` 20MiB）：单事务 4939ms，同一配置此前两次独立运行分别 4413ms 与 4735ms，三次都没有超时、没有 500；该规模（650 万字）下时间线中位 126ms（样本 126/109/133，出场 1000 章）。
- 不扫描正典的端点几乎不随规模变化：角色上下文 12–16ms、伏笔提醒 15–32ms、伏笔报告 15–17ms、章节列表 15–23ms（响应 59→293KB、202→1002 条）。作为对照，同一时窗 `psql` 直取整部正文、扣掉进程启动后的净耗时为 28/43/73ms（0.3→1.7MB），650 万字那一轮是 167ms / 17.6MB——时间线的那几十毫秒里含“把整部正典搬进 Node”，不只是应用侧 `indexOf`。
- 并发读（最大语料那份：1000 章 + 一个 50 万字长章，正典 7,000,021 字）：扫描整部正典的时间线在并发 1/4/8 下中位 113/347/628ms、p95 128/408/800ms，而吞吐 8.85/10.06/9.79 req/s——**并发买到的是排队，不是产出**；同机同一会话读不扫描正文的角色上下文，同期 83.33/255.32/320 req/s、中位 11–19ms、p95 ≤30ms。每次运行 78 个并发请求（时间线 39 + 角色上下文 39），两次运行全部 200，零失败、零超时。较小语料（110 万字）那一轮形状相同但未饱和（时间线 43/87/131ms），且每级样本只有 3/12/24 个，抖动足以翻转读数。
- 契约边界可同时成立但不能同时到满：1000 章与 500,000 字/章各自实测通过，而 20MiB 请求体决定了 1000 章最多约 6,500–7,000 字/章（按 500,000 字/章一次只装得下约 3 章）。`wordCount` 不计空白，500,000 字符正文记为 460,014 字。
- 内存：同一 API 进程 WorkingSet 在 12.0 万字时 105.9MB、60.0 万字时 140.6MB、650 万字时 213.1MB（加满长章并清理数据后 231.1MB），但分批增长那一轮清理后反而降到 133.4MB。**WorkingSet 不是单调量，操作系统会裁剪，这组数字既不能证明泄漏、也不能证明没有泄漏**；能确定的是“每请求把整部正典取进 Node 再 `indexOf`”会让常驻内存随正典体积同量级增长；同一份 700 万字语料在并发轮从 228.8MB 涨到 340.5MB，与“每个在途请求各自持有一份正文”这一实现形状一致（但同样不可严格归因）。V8 不把堆交还操作系统本身也是正常现象。

### 7.3 清理与脚本自身缺陷（如实记录）

脚本按 work/entry 的集合子查询删除临时作品、条目及其事件、审计、outbox 与本会话，并断言各表计数逐项等于压测前基线；四次运行（两组规模 + 两组并发）的 `cleanupDrift` 均为 `{}`，`yunshuo_test` 回到 works=1 / chapters=2 / 账本六表 0 / 事件 3 / 审计 119 / outbox 0 / 会话 0。过程中暴露并修掉三个脚本自身问题，都属于“验收脚本自己会撒谎”一类：

1. 清理语句把 1001 个章节 id 直接拼进 SQL，`docker exec` 在 Windows 抛 `spawnSync docker ENAMETOOLONG`，且**失败发生在数据已导入之后**——按 id 列表拼上千条的写法在本仓库不可用，必须改成与规模无关的子查询。
2. 第一版把 `登录` 写进时间窗起点之后，导致 `auth.login` 审计（`object_id` 为空）与本次会话不在删除范围内，`audit`/`outbox` 计数漂到 120/2；改为先取数据库自己的 `now()` 作为窗口起点，并补上 `index.ledger` outbox（按 `payload->>'entryId'`）的删除。
3. “请求体 MB”最初取的是 `fetch` 响应的字节数，把 0.00MB 的响应报成请求体；改为序列化后自行计数，并补 `sentChars`。

### 7.4 本轮不能宣称的事

并发只做到“同一台机器、同一个 Node 进程、同一个登录会话、每级 3 轮的批量并发读”：**没有多用户与多工作区、没有读写混合（边导入边扫描）、没有恒定到达率与 p99、没有真实小说正文、没有 Studio 容器内测量**；那几轮里 `yunshuo_test` 没有启用的嵌入服务商、worker 未启动，所以 `index_status` 全部 `not_configured`、整轮零模型调用——索引与检索的千章基线由同日另一次实测补上，见 7.5，补测之后**千章规模的账本索引仍未测**。“时间线中位 126ms”“并发 8 吞吐 9.79 req/s”都是这套合成语料、单实例下的读数，不构成性能达标或容量承诺。并发段能支撑的只到方向层面：单实例上“每请求扫描整部正典”这条路加并发不会换来产出（8.85/10.06/9.79 req/s 而延迟 113→628ms），而不读正文的端点随并发正常上升——这把“要不要做增量投影”从猜测变成一个能算的问题，但值不值得做仍要用真实正文与真实并发形态验证。规划文档 15.2 第 5 项已按此口径改写。

### 7.5 补测：千章正典索引排空与检索（同日，真实 worker + 本机嵌入）

缺口关闭的最后一块。`scripts/m6-perf-index.mjs` 与上面两轮用同一份合成 filler、同一个隔离库，差别是这一轮必须有真实 worker 和真实嵌入服务：脚本先探活嵌入服务，**不可达就直接退出，不会降级成“未配置”来把“环境没准备好”读成“索引基线”**。报告落 `docs/m6-perf-index.json`。

- 导入与排空：单事务导入 1000 章 × 600 字（请求体 1,811,900 字节 ≈ 1.73MB，`wordCount` 合计 550,000）用时 4253ms；入队即刻 `index_status` 与 `outbox` 都是 `pending=1000`；worker 排空用时 **2070s（34 分 30 秒）＝ 29.0 章/分钟**，1000 章全部 `ready`，零 `failed`、零 `not_configured`。产出 2000 切块（每章恒 2，min=max=2）与 2000 向量，`vector_chunks=2000 of canon_chunks=2000`，1024 维。
- 模型调用：索引期 1000 次全部成功（`prompt_tokens` 578,143，中位 **2021ms**）；每次调用最多带 16 个切块（`apps/worker/src/pipeline.ts:484`），每章 2 块，所以章数与调用数 1:1。查询向量 12 次全部成功（12 个 `auto` 请求各一次，中位 190ms，`prompt_tokens` 141），服务商合计 1012 次。本机模型输入价填 0，`cost=0.0000 CNY` 只对本机成立。
- 检索：`/api/search?workId=…&limit=8`，4 条查询 × `lexical`/`auto` × 各 3 次取中位。词法 209–413ms、混合 251–465ms；有命中每次 8 条、响应约 4.5KB，零命中约 0.44KB。混合侧带出的向量相似度 0.642 / 0.646（首位由词法通道命中时该项为空，两套分不做跨侧归一）；域外对照“量子色动力学的渐近自由”向量最高 **0.318 < 阈值 0.400**，如实降级为 `mode=lexical` 并写明原因、返回 0 条——降级路径在千章规模成立。
- 内存：worker WorkingSet 首个采样 78.1MB、整轮 88–90MB、末次 89.5MB，没随排队累积；API 从 149.5MB 降到 96.8MB。同 7.2 的口径，WorkingSet 非单调量，两边都既不能证明泄漏也不能证明没有。
- 清理与脚本自纠：清完后 `cleanupDrift = {}`，`chapter_metadata` 手工复验回到 1；这一项当时不在脚本的计数表里（漏掉就看不见漏删），已补进 `COUNTS`，下一轮起由断言覆盖。本轮之前还有三次“脚本自己会撒谎”的修法值得留档：`index_status JOIN chapters` 时裸写 `status` 触发 `column reference "status" is ambiguous`；嵌入成功状态实际写的是 `'ok'` 而不是 `'completed'`，**按 `'completed'` 统计会让一份成功索引 1000 章的报告自称“0 次成功调用”**，第一版报告就带着这个错数落过盘（`docs/m6-perf-smoke.json` 原样保留作为证据，修好后另跑 6 章为 `docs/m6-perf-smoke2.json`，其 `cleanupDrift` 才为 `{}`）；清理少删了一条服务商对象的 `audit_log`，漂移读成 `{"audit":"119 -> 120"}`；脚本的排空超时默认值原本 30 分钟，小于实测 34.5 分钟，**会把一次慢但成功的排空记成“未排空”**，已把默认调到 90 分钟（正式运行当时是显式传 `PERF_INDEX_TIMEOUT_MS=5400000` 跑的）。
- 本轮不能宣称的：29.0 章/分钟的倒数是 2.07s/章，与单次嵌入中位 2021ms 基本相等——**这条吞吐读的是“单 worker 串行 × 本机模型延迟”，不是索引管线的容量上限，也不能外推到付费服务商**；合成 filler 让切块恒为 2 且命中不具语义难度（词法首位恒为第 1 章），所以检索数值只证明“跑通 + 延迟量级”，**不构成检索质量或排序有效性的证据**；本轮库里没有账本条目，**千章规模的账本索引（`ledger_chunks` / `ledger_index_status`）仍是空白**；Studio 容器内、真实正文、多 worker、读写混合、持续到达率与 p99 同样未测。这些数字仍是单一本机环境的规模基线，不是生产 SLA。
