## 二、第一轮高危：并发所有者降级可让所有者归零

**证据**：`updateMemberRole` 与 `removeMember` 原实现只锁目标成员关系，再统计所有者数量。两个事务在 READ COMMITTED 下都看不到对方尚未提交的降级：

```text
txA sees owners = 2 | txB sees owners = 2
txA demotes owner A -> committed
txB demotes owner B -> committed
final owners = 0
```

复现使用两事务错峰执行（临时脚本，已删除），稳定得到 `final owners = 0`。工作区一旦没有所有者，成员管理与后续授权都会失去合法操作者。

**修复**：在事务内先锁工作区行，再锁目标成员关系，使所有会改变所有者数量的操作串行化：

- [identity-service.ts:420](../apps/api/src/services/identity-service.ts#L420)（改角色）
- [identity-service.ts:469](../apps/api/src/services/identity-service.ts#L469)（移除成员）

锁顺序统一为“工作区行 → 成员关系”，避免两者以相反顺序加锁。修复后同样的错峰执行变为第二个事务等待，最终 `owners = 1`。

**回归**：[m5-identity.test.ts:513](../apps/api/src/m5-identity.test.ts#L513) 创建含两名所有者的临时工作区，并发互相降级，断言结果为 `[200, 409]`、失败码 `LAST_OWNER`、最终所有者数为 1；工作区在 `afterAll` 清理。

## 三、第一轮中危：并发唯一冲突未映射，接口落成 500

### 3.1 并发创建同邮箱邀请

**现象**：临时 API 脚本对同一工作区、同一邮箱并发创建邀请，首轮 `201 | 409`，后续多轮出现 `500 INTERNAL`。原因是应用层先查“是否已有待接受邀请”，并发窗口内两个请求都通过检查，随后部分唯一索引 `workspace_invites_pending_email` 抛出 PostgreSQL `23505`，没有被映射。

**修复**：[identity-service.ts:179](../apps/api/src/services/identity-service.ts#L179) 在事务外层捕获唯一冲突，返回 409 `INVITE_PENDING`；其他数据库错误继续上抛，不吞异常。

**回归**：[m5-identity.test.ts:434](../apps/api/src/m5-identity.test.ts#L434) 用大小写不同的同一邮箱并发创建，断言状态为 `[201, 409]`、失败码 `INVITE_PENDING`，数据库中只有一条待接受记录。

### 3.2 并发接受同一新邮箱的两份邀请

**现象**：同一新邮箱分别收到工作区 A、B 的邀请，两个无会话请求并发接受，实测 `500 INTERNAL | 200 OK`。两份邀请都通过了“账号不存在”检查，`users_email_lower_key` 在插入时抛 `23505`。

**修复**：

- [identity-service.ts:339](../apps/api/src/services/identity-service.ts#L339) 捕获用户邮箱唯一冲突，返回 409 `ACCOUNT_EXISTS`。
- [identity-service.ts:362](../apps/api/src/services/identity-service.ts#L362) 捕获成员主键冲突，返回 409 `ALREADY_MEMBER`，覆盖“账号刚被另一请求建好”的窗口。

两处都在事务内抛出，事务回滚，不会留下半个账号或半条成员关系。接口错误映射保持与既有 409 语义一致。

**第二轮语义修正**：加入“已有账号可用密码直接接受邀请”后，第二个并发请求如果密码相同，会验证刚创建账号的密码并成功加入另一个工作区，因此 `[200, 200]` 是合法结果，不再必然是 409。回归测试现在允许 `[200, 409]` 或 `[200, 200]`，但断言：

- 该邮箱只存在一个账号；
- 若出现 409，错误码只能是 `ACCOUNT_EXISTS`；
- 成员关系为 1–2 条，且都指向同一账号。

这不是权限绕过：两个请求都证明了同一密码；第二个请求只是在另一个工作区建立成员关系。见 [m5-identity.test.ts:355](../apps/api/src/m5-identity.test.ts#L355)。

### 3.3 scrypt 在邀请校验之前执行

**现象**：`acceptInvite` 原先把密码哈希提到事务与邀请状态校验之前。任何人只要拿到一个已失效或伪造的令牌，就能让服务端执行一次 N=16384 的 scrypt；无效令牌越多，CPU/内存消耗越大，且没有任何业务进展。

**修复**：哈希移入事务，在邀请存在、状态有效、邮箱无既有账号等检查都通过之后才执行（[identity-service.ts:320](../apps/api/src/services/identity-service.ts#L320) 之后）。无效令牌在进入 scrypt 前即返回 409/410。

### 3.4 登录限流键表无上限

**现象**：键为 `email|ip`，任意构造邮箱即可持续新增条目；窗口过期后旧键也不会主动删除，长期运行会累积。

**修复**：[login-rate-limit.ts:5](../apps/api/src/login-rate-limit.ts#L5) 设 `MAX_ENTRIES = 10_000`；写入前先清理过期项，仍满则按插入顺序淘汰最旧键（[login-rate-limit.ts:39](../apps/api/src/login-rate-limit.ts#L39)）。限流仍是单进程内存实现，重启清空、多实例不共享，这一点没有改变，也不应被误读为生产级限流。

### 3.5 生产环境未强制关闭开发登录

**现象**：`devAuth` 只检查 `DEV_AUTH === '1'`。若生产部署误设该变量，`/api/dev/users` 与无密码开发登录会实际可用，违反“开发登录仅限本机”的约束；此前只靠文档提醒。

**修复**：[env.ts:30](../apps/api/src/env.ts#L30) 改为 `!isProduction && process.env.DEV_AUTH === '1'`。生产环境无论变量如何设置都关闭开发身份；缺少 `SESSION_SECRET` 仍会在启动时直接失败。

说明：该组合（`NODE_ENV=production` + `DEV_AUTH=1`）没有新增子进程级自动化测试，属于代码审查级验证。

## 五、第二轮高危：被移出全部工作区的账号无法重新接受邀请

### 5.1 复现

用临时脚本（已删除）在测试库复现：

```text
owner 移除目标成员 -> 200
owner 重新邀请同一邮箱 -> 201
目标账号用正确密码登录 -> 401 UNAUTHENTICATED
```

原因是 `createSessionForUser` 要求账号至少属于一个工作区（[auth.ts:101](../apps/api/src/auth.ts#L101)）。账号被移出全部工作区后，登录被拒；而邀请页的“已有账号”分支原先调用“先登录、再接受”，因此形成死路：没有会话不能接受邀请，想登录又因为没有工作区被拒。

### 5.2 修复

- `acceptInvite` 的无会话分支现在区分两种情况：
  - **账号不存在**：要求称呼 + 至少 10 位密码，创建账号；
  - **账号已存在**：要求密码，并在邀请事务内 `verifyPassword`；密码错误统一返回 401 `LOGIN_FAILED`（未知账号仍执行 dummy scrypt）。验证通过后直接使用该账号建立邀请工作区的成员关系与会话，不再要求先登录。
- 未提供密码时返回 409 `ACCOUNT_EXISTS`，提示“请先登录后再打开邀请链接”；这覆盖仍有其他工作区、可以正常登录的账号。
- 由于这条路径涉及密码校验，路由层新增限流：[routes/identity.ts:52](../apps/api/src/routes/identity.ts#L52) 使用 `invite-accept|token|ip` 作为键，复用 8 次失败/10 分钟窗口；成功接受清空失败记录。限流只作用于“无会话且带密码”的尝试，已登录接受不受影响。
- 前端 [InviteAcceptScreen.tsx:195](../apps/web/src/components/InviteAcceptScreen.tsx#L195) 的“该邮箱已有账号”表单改为把密码直接提交给接受接口，不再先调用登录接口；成功后会话直接绑定到邀请工作区。
- 登录页的“无工作区”提示改为“该账号不属于任何工作区，请使用邀请链接加入”（[auth.ts:101](../apps/api/src/auth.ts#L101)），状态码仍为 401 `UNAUTHENTICATED`。

### 5.3 回归与浏览器验收

- 新用例 [m5-identity.test.ts:313](../apps/api/src/m5-identity.test.ts#L313)：账号被移出全部工作区后，用错误密码连续尝试 8 次均返回 401；第 9 次即使密码正确也返回 429 `LOGIN_RATE_LIMITED`；随后用另一份邀请携带正确密码接受成功，角色为 author，`/api/me` 可用，数据库中该邮箱只有一个账号。
- 浏览器验收（独立 API `3101` + 独立 Vite `5176`，均指向 `yunshuo_test`；未触碰 `3100/5173/5174/5175`）：
  1. 创建临时工作区、临时所有者与孤儿账号，移除成员后重新发邀请；
  2. 打开邀请链接，页面显示“该邮箱已有账号”，输入错误密码 → 显示“邮箱或密码不正确。”，按钮恢复可用；
  3. 输入正确密码 → 跳转写作台，页头显示该账号与“作者”角色，工作区为临时工作区；
  4. 验收后删除临时工作区、账号、邀请与会话，停止并确认 3101/5176 释放；临时 Vite 配置已删除。

## 六、第二轮中危：畸形 JSON 请求体返回 500

**证据**：对运行中的 API 发送 `POST /api/auth/login`，请求体为 `{bad`，返回 500 `INTERNAL`。Fastify 的 JSON 解析错误带有 `statusCode=400`，但全局错误处理器只识别 `AppError`，把其余错误统一落成 500。

**修复**：[server.ts:50](../apps/api/src/server.ts#L50) 在全局错误处理器中识别 Fastify 的 4xx `statusCode`，映射为：

- 413 → `PAYLOAD_TOO_LARGE`
- 415 → `UNSUPPORTED_MEDIA_TYPE`
- 其他 4xx → `BAD_REQUEST`

并返回中文可读文案，不再误报服务器内部错误。

**回归**：[http-errors.test.ts:18](../apps/api/src/http-errors.test.ts#L18) 断言畸形 JSON 返回 400 `BAD_REQUEST`；[http-errors.test.ts:29](../apps/api/src/http-errors.test.ts#L29) 断言未知路由仍为 404 `NOT_FOUND`。

文案已改为可操作的“该账号不属于任何工作区，请使用邀请链接加入”。状态码仍是 401 `UNAUTHENTICATED`，没有改成 403 `NO_WORKSPACE`；这是本轮明确保留的低风险语义问题：只有掌握正确密码者能看到该提示，且文案已不再误导为“请先登录”。

## 八、已复核但不构成缺陷

- **团队面板查询键未带工作区**：`['members']` / `['invites']` 看似可跨工作区复用，但每次切换工作区都会 `queryClient.clear()` 并关闭团队面板（[App.tsx:112](../apps/web/src/App.tsx#L112)、[App.tsx:139](../apps/web/src/App.tsx#L139)）。当前流程不存在旧工作区数据串入的路径。若未来改成局部失效而非清空缓存，需要再补工作区维度。
- **所有者被降级后邀请角色的本地状态**：`handleSessionRefresh` 在角色不再是所有者/主笔时会关闭团队面板（[App.tsx:139](../apps/web/src/App.tsx#L139)），正常单页流程下不会停留在失效表单；仅多标签页并发操作存在极窄窗口。
- **邀请预览返回“账号是否存在”**：预览需要持有 256 位随机令牌，令牌即授权凭证；不存在可枚举路径。未对预览单独限流，属可接受的加固空白。
- **并发接受同新邮箱可以两个都成功**：第二个请求必须提供与刚创建账号相同的密码，等价于一次正常登录并接受邀请；不是绕过邮箱所有权。真正需要防止的是“同一邮箱出现两个账号”，唯一索引已保证。
- **邀请接受限流会把持有令牌的合法用户短暂锁住**：攻击者需要先拿到令牌；令牌本身就是授权凭证，且 8 次/10 分钟后自动恢复。它防的是在线猜密码，不是令牌泄露后的接管。

## 九、保留的风险与未修复项

1. **前端没有自动化测试**：登录、邀请、团队、工作区切换只有类型检查与人工浏览器验收。第二轮已实际浏览器复验孤儿账号接受流程，但没有可重复的 CI 保护。这是 M5-A 最明显的覆盖缺口。
2. **限流是单进程内存实现**：重启清空、多实例不共享；10,000 键上限只防本进程内存无界增长。生产部署必须替换为共享存储，并补充告警。
3. **无 CSRF 令牌**：会话 Cookie 为 `SameSite=Lax` 且 httpOnly，跨站 POST 默认不带 Cookie，但未做 Origin/CSRF 双保险；当前是 `dev-v0` 本地部署。
4. **无工作区登录仍返回 401 `UNAUTHENTICATED`**：文案已修正，状态码语义仍不够精确；不影响安全。
5. **开发库保留历史验收数据**：191 条 `model_calls`、5 条 AI 提案与 2 个真实服务商仍在开发库；它们不是 mock，保留作为验收记录。演示会话与 `auth.login` 审计已清理。
6. **测试库是共享可变库**：守卫只保证库名是 `yunshuo_test`，不保证迁移/种子是最新；测试仍会真实写入并清理。建议在 CI 中每次重建测试库。
7. **未实现**：OIDC/SSO、密码重置/修改、邀请邮件投递、计费归属、数据库级 RLS、MFA、会话吊销列表、Studio 部署。
